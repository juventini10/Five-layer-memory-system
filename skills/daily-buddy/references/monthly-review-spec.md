### 格式铁律

**序号规范**：
- 大模块：`1️⃣、2️⃣、3️⃣...🔟`
- 子项目：`①、②、③`（避免和大模块序号撞车）

**标题规则**：
- 3月总结 → `## 9️⃣ 🚀 四月3件事`（自动换算为下个月）

**存储路径**：`{{OBSIDIAN_VAULT}}/1-每日计划/03-月报/YYYY-MM-月总结.md`

### 🚀 下月3件事格式规范（v2.1新增）

> **设计意图**：周报的「月目标对齐」模块从本表读取数据。每条目标必须包含「周分解建议」列，让周报AI可以直接分解到每周，不需要自己猜。

| 序号 | 目标 | 周分解建议 | 策略 | 番茄估算 | 风险预防 | 验收标准 |
|------|------|-----------|------|----------|---------|---------|
| 1 | 目标描述 | **每周应交付XX**（可量化、可验证） | 策略 | X🍅 | 预防措施 | 验收标准 |
| 2 | 目标描述 | **每周应交付XX** | 策略 | X🍅 | 预防措施 | 验收标准 |
| 3 | 目标描述 | **每周应交付XX** | 策略 | X🍅 | 预防措施 | 验收标准 |

**周分解建议写法原则**：
- 必须可量化：「每周1期」而不是「尽量多做」
- 必须可验证：周报复盘时一眼能看出做到没做到
- 必须合理：月度目标÷4周，不能超出每周实际承载量

### ❖ 日记质量评估细则

**定位**：数据源健康检查。在所有下游分析（睡眠/番茄/账号等）之前执行，评估本月日记作为数据源的可靠性。

**评估维度**（全部从日记原文统计，不凭记忆）：

⚠️ **铁律**：S级日记必须从YAML frontmatter `rating: S` 提取。rating字段为空 → 标注"数据缺失"。**禁止凭事件重要性推断评级。**

**提取方式**（所有维度通过前台扫描）：
```bash
# 含金量评级 — 从YAML frontmatter提取
grep -l "^rating: S" YYYY-MM/*.md  # S级日记列表
for f in YYYY-MM/*.md; do grep "^rating:" "$f" | head -1; done  # 全量评级
```

| 维度 | 指标 | 数据来源 |
|------|------|---------|
| ① 完整率 | 写了X天/总天数，断更天数，最长连续断更 | 当月日记文件列表 |
| ② Section完整率 | 含齐12个SECTION的日记比例，缺Section频次分布 | 各日记`<!-- SECTION: -->`标签扫描 |
| ③ 含金量评级分布 | S/A/B/C/N各X篇，异常评级（低含金量却高评级） | 各日记YAML `rating:` 字段统计 |
| ④ 感悟深度 | 空感悟N篇/一句话≤20字N篇/中等N篇/深度N篇 | `<!-- SECTION: INSIGHTS -->`内容量 |
| ⑤ 数据准确性 | 番茄总和≠各任务加总的篇数，睡眠数据缺失篇数 | 日记数据段与累加交叉验证 |

## 2. 数据铁律

- ⛔DO NOT凭记忆或推测补数据——原因是AI记忆可能过时或幻觉，必须逐行读取日记源文件
- ⛔DO NOT凭记忆编写系统建设模块——原因是必须读取当月系统日志提取
- 统计流程：**读取全部日记 → 按统一口径分类 → 交叉验证 → 自查一致性**
- **系统建设模块（7️⃣）**：数据来源为系统日志（`[记忆共享中心]/工作日志/系统日志/系统日志_YYYY-MM-DD.md`），提取Skill开发、工具链搭建、流程优化等条目

## 3. 读写分离三阶段执行规范

> 问题背景：月总结需读30个日记+多个系统日志，边读边写容易漏数据、交叉污染。
> 设计哲学：借鉴 Claude Code toolOrchestration.ts 的分区策略——读批量执行、写严格串行。

```
┌─────────────────────────────────────────────────────┐
│  阶段1：只读（BATCH READ）                            │
│  ─────────────────────────────────────────────────  │
│  ① 逐行读取当月所有日记文件（约30篇）                  │
│     → 提取：番茄数/睡眠/能量/完成度/账号进展          │
│     → 额外提取：Section完整性/含金量评级/感悟字数    │
│  ② 逐行读取当月所有系统日志文件                       │
│     → 提取：系统建设条目                              │
│  ③ 禁止在此阶段写任何内容！                           │
│  ④ 所有数据暂存于"数据草稿区"（内存/临时笔记）          │
├─────────────────────────────────────────────────────┤
│  阶段2：只算（COMPUTE）                               │
│  ─────────────────────────────────────────────────  │
│  ⑤ 基于阶段1原始数据进行计算                          │
│     → 汇总统计（总数=各分类之和，否则报错）            │
│     → 占比计算、趋势判断、根因分析                    │
│  ⑥ 交叉验证：                                      │
│     → 日记番茄总和 = 各日番茄累加？                   │
│     → 系统日志条目 = 实际读取到的？                   │
│  ⑦ 禁止在此阶段读取新文件！                           │
├─────────────────────────────────────────────────────┤
│  阶段3：只写（WRITE ONCE）                            │
│  ─────────────────────────────────────────────────  │
│  ⑧ 基于阶段2计算结果，一次性输出完整报告             │
│  ⑨ 十大模块按顺序输出，不回跳、不补充                │
│  ⑩ 输出后运行钩子脚本确认成就检测                     │
│  ⑪ 禁止在输出后发现"漏了"而回头补写！               │
│      （如果漏了，从阶段1重来）                         │
└─────────────────────────────────────────────────────┘
```

### 违规示例（禁止）
```
❌ 写到第5模块发现睡眠数据不够 → 回去读第12天的日记
❌ 边读日记边写模块3（数据可能不完整）
❌ 凭记忆补"大概20多个番茄"
```

### 正确做法（必须）
```
✅ 先把30篇日记全部读完，数据整理成表格
✅ 表格数据验算通过后再开始写第一个字
✅ 发现数据不足时，标记为"待核实"，不回去补
```

## 4. 根因分析与伙伴建议

### 根因分析排版

- 每个根源观点独立一行，不挤在同一行
- 格式：`① **小标题**——具体说明`
- 禁止用分号串联多个观点
- **必须跟"落地动作"表**：没有落地动作的根因分析等于没分析

格式：`| 根源 | 动作 | 怎么执行 |`

### 伙伴建议角度

- 不重复1️⃣高光时刻的内容
- 从数据中发现用户自己没注意到的成长或模式
- 可用子模块"我看到的你没看见的东西"补充

### 哲学框架运用原则

- 哲学框架（斯多葛/存在主义/实用主义/分析哲学/唯物辩证法）和38本笔记知识库是分析工具
- 自然内化在洞察中，不贴标签
- 经典理论（如第一性原理、二八法则、反馈回路）可标注书名和概念，方便回溯
