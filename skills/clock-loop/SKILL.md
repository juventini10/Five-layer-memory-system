**✅DO - 功能聚焦:本Skill只处理有明确检查清单的任务(审核/生成/分析/修复/评估/学习)。⛔DO NOT在一个Loop里混合两个不同意图的任务--原因是:功能膨胀=定位模糊=用户不知道这个Skill能干什么。每轮Loop只做一件事,做完了再决定下一件。**

## 📋 Alternatives Considered

| 设计决策 | 选择 | 替代方案 | 为什么不选替代 |
|:---------|:-----|:---------|:--------------|
| 循环结构 | 每轮=执行→自查→审查 | 仅自查无子Agent | 自己改自己查=循环断链,子Agent提供独立视角 |
| 评分方式 | 多维度加权评分 | 二元通过/不通过 | 二元评估丢失改进方向信息,多维评分能定位短板 |
| 知识来源 | 评估知识库+second-brain联动 | 仅靠模型内化知识 | 模型知识有截止日期且不可审计,知识库可更新可追溯 |
| 标准存储 | task-standards.json持久化 | 每次问用户 | 同类任务反复问标准=用户疲劳,持久化后自动复用 |
| 哲学评估 | 固化引用references/philosophical-evaluation.md(来源:meta-aletheia) | 自行定义哲学立场 | AI无权定义哲学立场,标准来源必须可追溯 |
| 三明智嵌入 | L1拆解+L2自检 | 仅L1或仅L2 | L1保证理解再评分,L2保证评分可信,缺一不可 |
| 卡死判定 | 子Agent反馈为主依据 | 量化指标为主 | 量化指标无法覆盖所有任务类型,子Agent反馈更通用 |
| 最大轮次限制 | 硬性安全限制3轮内部循环 | 无限循环 | Token成本失控是Loop工程最大的坑 |

## 功能定位

本Skill做一件事:**把"你一句我一句"的交互模式,切换成"你说一次,我在后台闭环跑到达标"的模式。** v2.0升级后,不只是"重复跑",而是站在反方向审视:质疑、拆解、验证、迭代--而且用专业规范矩阵+知识网络+哲学维度+三明智方法论来审视,不靠模型直觉。

你只需要参与两个环节:
1. **首次某类任务时**给标准(我给选项让你选,一次性的)
2. **结尾收结果**(看一眼执行履历,ok就过)

中间所有"执行→多维评分→子Agent审查→修正→再检查"的循环,都在后台自动跑。

**v2.0评估示例:**
```
循环 评估这个Skill
→ 阶段1:收集标准(任务类型=评估Skill/检查清单/严格度/轮次)
→ 阶段1.5:加载skill_patterns.yaml + current_weights.yaml
→ 阶段2:
  L1拆解:核心功能/依赖/输出/核心矛盾
  逐维度评分(6个宏观维度→19个微观检查项，详见skill_eval.py的MACRO_DIMENSIONS映射表):
    开发规范19%+指令准确性18%+逻辑一致性27%+文档完整性14%+测试覆盖12%+哲学评估10%
    [v2.8.8]宏观声明权重=下属微观维度WEIGHTS之和/100，由verify_dimension_consistency()启动时自检
    [v3.0.0]置信度分层标注——每个维度标注🔧脚本确定性/🧠AI判断（见下表）
  L2自检:锚点对立面/证据链/假设验证/结论块门禁锁
→ 阶段3:交付结果+执行履历+评分表
```

**置信度分层标注表（v3.0.0新增·B2/Q4-2修复）:**

> 评估结果必须区分"脚本确定性检查"（可复现、不漂移）与"AI语义判断"（会漂移、有偏差风险）。交付物中每个维度须标注置信度层级。

| 置信度 | 含义 | 包含的微观检查项 | 可靠性 |
|:------:|:-----|:-----|:------:|
| 🔧 脚本确定性 | 纯算术/字符串/文件系统状态，可复现不漂移 | version_single_source, version_uniform, single_number_source, cross_file_consistency, internal_links, file_clutter, token_budget, eval_set_gate, path_safety, backup_gate, fuse_mechanism, layering, attack_surface, l1_l2_substance | 🟢高 |
| 🧠 AI判断 | 需语义理解，会受上下文/模型版本影响 | yaml_required(字段语义), causal_chain(原因质量), poka_yoke(设计质量), binary_annotations(标注合理性), t5_adversarial(声明实效), mechanism_selection(选配合理性), 哲学评估, Alternatives质量 | 🟡中 |

✅DO 在评分表每行末尾标注 `🔧` 或 `🧠`。⛔DO NOT 把AI判断项与脚本确定性项混在一起不加区分——原因是用户需要知道哪些分数可靠、哪些有偏差风险。

**v1.x执行示例:**
```
循环 审这篇文案
→ 阶段1:收集标准(任务类型=审核文案/检查清单/严格度/轮次)
→ 阶段2:执行→自查→子Agent审查→修正→再检查(后台自动)
→ 阶段3:交付结果+执行履历
```

## 🔒 防跳步机制 `[Poka-Yoke防误层]`

**接触法**:步骤产出物锁(每步📦)--物理验证,产出物缺失=立即露馅
**定值法**:内部循环最多3次(固定值)--防自查死循环消耗Token;最大轮次由用户选定(固定值)--防无限循环
**步序法**:阶段0→1→Phase X(评估路径)→1.5→2→3→4强依赖--A未完成不可进B;Read回验progress.md确认上轮状态

- ✅ 步骤产出物锁(每步📦)- 接触法
- ✅ 思考检查点(关键节点🧠)
- ✅ 熔断器(外部调用🔌)
- ✅ 完整性锁(输出前🔒)
- ✅ 卡死检测(产出无实质进步时自动终止)
- ✅ 文件异常恢复(JSON损坏→重新收集标准;progress丢失→从头开始标记为第1轮)
- ✅ v2.0新增:多维评分门禁锁(评分前必出L1拆解+评分后必出L2自检)
- ✅ **v2.8.0新增:Phase X脚本增强检查+步序法物理阻断；v2.7.0新增:Phase X验证⑭⑮ T5防御声明检查(开源发布质量门禁)；v2.3新增:Phase X机检锁(评估路径必走机械验证,产出物缺失=违规,退回补验)**

## 执行流程

### 阶段0:前置判定

📦 产出物:判定结果 + 路径声明

用户说话时,判定是否以"循环""loop"开头:
- **是** → 进入Loop模式,输出 `Loop Engineering Loop模式已启动`

### 阶段2:循环执行(闭环核心)

📦 产出物:progress.md + 本轮产出 + 多维评分表

> **📋 progress.md**:每次Loop运行时自动创建,记录每一轮做了什么、子Agent发现了哪些问题、本轮修正了哪些。存储路径:`[记忆共享中心]/评估知识库/test_results/{对象类型}_tests/progress_{对象名}_{YYYY-MM-DD}.md`。评估完成后自动归档为评估报告(同目录),progress.md不残留在Skill目录。模板见 `references/progress-template.md`。

循环结构如下--每一轮自动执行,你全程不在场。每轮迭代的边界是:**子Agent给出审查结果**。

```
【第N轮】从执行开始,到子Agent给出审查结论结束

  │
  ├─ 1 读进度记录
  │    读取 progress.md(第一轮不存在则跳过)
  │    对上轮反馈的问题逐条确认,防止遗漏
  │
  ├─ 2 执行本轮工作
  │    ├─ 第1轮:按你给的标准从头做
  │    └─ 第N轮(N>1):基于上轮子Agent的反馈修正
 │        修正前先备份:确定本次要修改的文件清单 → 逐一执行
 │          `cp {文件路径} [记忆共享中心]/记忆琥珀/技能升级备份/{文件名}_{YYMMDD_HHMM}.bak`
 │        --原因是:修改不可逆,备份是安全网。只有只读评估(不修文件)可跳过此步。
 │        如果触发过"策略切换"(反疲劳标志位=ON):换方法修
  │
  ├─ 3 自查:多维度专业评分(v2.0升级)
  │    Read references/evaluation-framework.md → 执行以下流程:
  │
  │    a) L0 结构画像(防回声,v2.1.2新增)
  │       触发条件:当前Session中已评估≥1个对象时必做
  │       目的:打断"上次修的=这次也要修"模板套用惯性
  │       三问(3秒,不深究):
  │       - 这个对象最独特的设计是什么?(一句话)
  │       - 它和上一个评估对象结构上最大的不同是什么?
  │       - 上一个对象修过的问题 → 哪些不适用于本次对象?
  │       → 输出L0防回声清单(适用于/不适用于),指导后续打分避免假阳性
  │
  │    b) L1拆解(评分前必做,Read references/triwich-integration.md L1段)
  │       核心功能是什么?依赖什么?输出什么?核心矛盾是什么?
  │       → 拆解结果写入评分表前言
  │
  │    c) 逐维度评分
  │       对每个维度:读取check_items → 逐项核对产出物 → 标注✅/❌/⚠️ → 维度得分=通过/总数
  │       维度来源:阶段1.5加载的patterns文件
  │
  │    d) 加权汇总
  │       总分 = Σ(维度得分 × 权重)
  │       权重来源:阶段1.5加载的weights文件
  │
  │    e) 哲学评估嵌入(对象类型为skill时,Read references/philosophical-evaluation.md)
  │       Read references/philosophical-evaluation.md → 七项哲学检查逐项评分
  │       v2.1.2新增规则：检查项先找显式声明→无则查功能层等价级联锁/人在回路/定值法=功能层实装
  │       v2.2.0新增规则：哲学评估总分≥85%→判定"哲学及格"，该维度按15%权重满分计入；<85%→判定"哲学不及格"，该维度按15%权重零分计入。不再逐项加分，消除虚假区分度。
      │
  │    f) L2自检(评分后必做,Read references/triwich-integration.md L2段)
  │       锚点对立面?证据链完整?假设验证?结论块门禁锁?
  │
  │    评分门禁(固定值):
  │    ├─ ≥85% → ✅通过 → 强制进入4(子Agent审查),不可跳过
  │    ├─ 70-84% → 🟡部分通过 → 备份目标文件 → 修正→重评(内部循环,不占外部轮次)
  │    └─ <70% → ❌不通过 → 记录→跳子Agent审查
  │
  │    ⛔DO NOT将自查≥85%视为可交付--自查通过≠交付条件,4审查通过才是。跳过4直接进入阶段3交付=步骤缺失=交付无效。
  │
  │    内部循环最多3次(固定值--防自查死循环消耗Token)
  │    → 仍不过 → 实情记录 → 跳子Agent审查
  │
  ├─ 4 审查(子Agent可用时spawn,不可用时自检替代)
  │    v2.2.0新增：子Agent审查前必须执行L0防回声（与③a相同的L0三问），确保审查者不从自评者的判断框架出发
  │    子Agent指令:
  │      "你是一个独立的审查Agent,只读不可修改。
  │       **首先执行L0防回声**：
  │       Q1. 这个对象最独特的设计是什么？（一句话）
  │       Q2. 它的结构和常见同类对象最大的不同是什么？

  │       严格度:[用户选的] | 检查清单:[用户选的] | 成功标准:[用户第5问]
  │       找茬视角:假设这个产出要发布,你会找出什么问题?

  │       1. 格式套用惯性：把上个对象的格式修补清单当通用模板
  │       2. 评分模式惯性：评分维度权重照搬上个对象
  │       3. 框架套用惯性：用上个对象的设计框架评判本对象
  │       4. 问题锚定惯性：聚焦自评者已发现的问题，忽略独立发现
  │       5. 修复路径惯性：默认自评者的修复方向正确，只审查修得好不好
  │       6. 维度偏好惯性：对自评者重视的维度更严格，忽视自评者忽略的维度
  │       7. 结论趋同惯性：倾向于给出和自评者相近的总分"
  │    ├─ 审查通过（含回声自检无命中或命中已标注） → 本轮达标,准备终止交付
  │    └─ 审查不通过 → 分析反馈 → 记录进下一步
  │        ⚠️ 审查不通过后修正的产出必须进入下一轮重新审查
  │        ⚠️ 回声命中≥3条 → 标记本次审查为低置信度，要求重审
  │
  ├─ 5 反疲劳判定
  │    ├─ 首次不过 → 正常修正策略 → 反疲劳标志位=OFF
  │    └─ 同一问题连续两次不过 → 策略切换(换方法修)→ 反疲劳标志位=ON
  │
  ├─ 6 写入执行日志 → progress.md
  │    ├─ 本轮做了什么
  │    ├─ 多维评分表(v2.0:替换原"自查通过/未通过"为完整评分表)
  │    ├─ 子Agent发现了哪些问题
  │    ├─ 本次修正了哪些
  │    └─ 反疲劳标志位状态 + 本轮进步置信度
  │
  └─ 7 🧠 思考检查点(每轮终结点)
        本轮Token预估消耗 | 子Agent反馈质量评估 | 反疲劳触发状态 | 预算可控?
```

|:---:|---------|--------|

**v2.2.0新增：触顶判定（交付时自动计算）**

> 触顶 = 文档侧修复空间耗尽，继续修文档只能获得1-2pp提升，无实质改进意义。

| 指标 | 计算方式 | 触顶阈值 |
|------|---------|:---:|
| 维度饱和度 | 得分≥90%的维度数 / 总维度数 | ≥16/19 → 触顶 |
| 剩余可修复空间比率 | (100% - 各维度得分)之和 / 维度数 | <8% → 触顶 |

🔒 阶段4 收尾门禁（交付定义 · v2.5.3新增）

> 设计依据：L3沉淀/悬置区探针/对话冲突检测三机制原定义为"交付后自动检查/✅DO"，无硬门禁→实测休眠（test_results 10份报告零 L3_沉淀 产物、evolution stub 未填）。根因=触发器挂在 AI 自觉 + post-delivery SHOULD 级，跳过零代价。本门禁将"自进步"从"交付后的建议"变为"交付完成的定义本身"——不跑完三步不许说"✅ 交付完成"。

**🔴 以下四步为交付门禁——未执行且未记录跳过原因，禁止输出"✅ 交付完成"声明：**

| 步 | 机制 | 触发 | 执行 | 门禁验证（确定性） |
|----|------|------|------|-------------------|
| ⓪ | **评估报告存在性（v3.0.4新增·防T0漏写）** | 每次交付前 | ✅DO Glob `test_results/skill_tests/{对象名}_*评估报告*` 验证文件存在——不存在=交付未完成，退回补写。⛔DO NOT在报告文件确认存在前输出交付声明——原因是对话里的评分≠文件级归档，文件是跨周期检索的唯一锚点 | Glob 返回至少1个匹配文件 |
| ① | 悬置区探针 | 每次归档后 | 按残差五类逐条扫描；有→写悬置区.md，无→输出 `🌀 本轮无残差信号` | 悬置区.md有新条目 或 已记录"无残差信号" |
| ② | 对话冲突检测管道 | 每次归档后 | Phase 0 `load_claim_index.py` → Layer1提取 → Layer2 `append_claim.py` | 脚本已执行（台账追加 或 记录"本轮无新断言"） |
| ③ | L3跨周期沉淀 + 双盲审计到期检测 | 评估报告数达5的倍数（L3）/ 10的倍数（双盲） | 先跑 `scripts/check_selfimprove_gate.py` 取 `l3_required` 和 `double_blind_due`；l3_required=true→扫全部报告提取共性模式→写 `evolution/L3_沉淀_{日期}.md`→**立即跑「反哺派生」**；double_blind_due=true→提示用户"双盲审计到期，建议启动异构模型+跨Skill审查+人类终审三路径" | `L3_沉淀_{日期}.md` 存在 + 交付总结含🔄反哺报告 + 双盲到期已提示 |
| ④ | L1/L2实质内容验证（v3.0.0新增·B2修复） | 每次评估后 | `python3 scripts/skill_eval.py --check-l1l2 {评估报告路径}` → 检测L1非空非模板+L2含锚点对立面信号 | 脚本 `passed: true` 或 已记录"L1/L2缺陷已补正" |

- ✅DO：四步按①→②→③→④顺序在"提交交付物"前完成
- ✅DO：L3触发决策以 `check_selfimprove_gate.py` 的 `l3_required` 字段为准（确定性计数，不靠AI数文件）
- 🛡️ 正面建模：交付声明的充要条件是"四步均执行（或合法跳过已记录）+ 门禁验证通过"；任一未过→退回补跑，不输出交付完成
- ⛔DO NOT：以"看起来该跑了"或"AI记得跑过"替代门禁验证——原因是 post-delivery 步骤最易被跳，只有产物存在=真跑了
- ⛔DO NOT：L3在 `l3_required=false` 时运行——仅在5的倍数触发（5/10/15…），其余次数跳过
- 🔍 备选未选（Alternatives Considered）：①外部调度器(cron)强制每月→违背用户"不要后台静默自动"立场，弃；②仅 prose 升级为 ⛔DO NOT 级标注却不验证→AI仍可漏跑，弃；③试点单机制→门禁为共享基础设施，试点不验证其余二者集成，弃（用户定：全做）

## 判断标准

| 状态 | 定义 | 怎么做 |
|:---:|------|--------|
| ✅ 正常 | 子Agent通过 + 评分≥85% | 正常交付 |
| 🟡 警告 | 子Agent未启动→NoAgent模式,或策略切换触发,或评分70-84% | 执行履历中如实记录降级/切换情况 |
| 🔴 错误 | 审查连续失败且轮次用尽,或评分<70% | 交付时标注"审查精度受限"并说明未通过项 |

## 禁止行为

| # | 禁止 | 原因 |
|---|------|------|
| 1 | ⛔DO NOT跳过阶段1直接进入执行 | 没标准=闭环没有检查清单=无法判断达标 |
| 2 | ⛔DO NOT让用户参与自查或子Agent审查环节 | 用户只在开头定标准和结尾收结果 |
| 3 | ⛔DO NOT在子Agent审查不通过时不分析直接重跑 | 盲目重跑=碰运气,要分析反馈后精准修正 |
| 4 | ⛔DO NOT设置无限最大轮次 | Token成本失控是Loop工程最大的坑 |
| 5 | ⛔DO NOT默认处理新任务类型时不问标准 | 没标准=闭环没有检查清单 |
| 6 | ⛔DO NOT在未读progress.md的情况下开始新一轮 | 不知道上轮做了什么,可能重复或遗漏 |
| 7 | ⛔DO NOT在子Agent不通过后修正产出不重新审查就交付 | 修正后直接交=自己改自己查=循环断链 |
| 8 | ⛔DO NOT跳过阶段1.5知识网络构建直接执行 | 没知识网络=多维评分没有依据=退回凭感觉打分 |
| 9 | ⛔DO NOT在多维评分中跳过L1拆解直接打分 | "凭感觉打分"是评估最大陷阱,L1拆解强制先理解再评分 |
| 10 | ⛔DO NOT在多维评分完成后跳过L2自检 | 高分可能是锚定效应,L2自检是评分可信度的最后保障 |
| 11 | ⛔DO NOT在未备份的情况下修改被评估文件--原因是:修改不可逆,无备份=改崩了无法还原。✅DO先将目标文件备份到 `[记忆共享中心]/记忆琥珀/技能升级备份/{文件名}_{YYMMDD_HHMM}.bak` 再执行修改。 | 防误层;备份=修改前置条件 |
| 12 | ⛔DO NOT将评估报告或progress.md存放在Skill目录 | Skill目录只放Skill自身文件,评估产物残留在Skill目录会污染纯粹性且导致目录膨胀 |
| 13 | ⛔DO NOT在自评估时使用 `[clock-loop专属]` 检查项——原因是：自著考卷=自指偏差（Q3-3）。✅DO clock-loop自评估只用通用6项标准，专属8项仅供外部审计（双盲+人类锚）使用，详见 task-standards.json 的 `external_audit_checklist` 字段 | 自评估回避制·v3.0.0新增 |
