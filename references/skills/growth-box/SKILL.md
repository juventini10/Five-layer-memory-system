## 🛡️ Poka-Yoke防误层（S级）

> 三道物理级防错，每道独立阻断。防误层是设计端约束——不依赖AI自觉，靠定值/接触强制阻断错误路径。

| 防误机制 | Poka-Yoke方法 | 防什么错 | 强度 |
|:---------|:-------------|:---------|:-----|
| 错误分类固定5级 | 定值法 | 分类泛滥 | 最强（非5级=阻断） |
| 晋升次数定值3次 | 定值法 | 阈值漂移 | 最强（非3次=阻断） |
| 归档格式Schema | 接触法 | 字段缺失 | 最强（缺字段=拒绝） |

### 1. 错误分类固定5级（定值式防错）

- **防什么**：AI自创错误分类标签，导致分类泛滥、无法统计聚合。
- **机制**：错误必须归入5个固定分类之一（流程/验证/身份认知/技术实现/其他），不可自创分类。5级 = 定值，少一级或多一级 = 阻断。
- **阻断条件**：错误类型不在5级范围内 → 阻断写入，要求用户/AI重新归类到合法分类。
- **对应步骤**：流程A步骤A1（判断错误类型）。

### 2. 晋升次数定值3次（定值式防错）

- **防什么**：AI自行调整晋升阈值（如2次就晋升或5次才提醒），导致阈值漂移、晋升机制失效。
- **机制**：错误必须重复出现3次才触发蒸馏晋升。3次 = 定值，不可由AI自行调整阈值。状态标注固定为 `pending(N/3)`，N<3不晋升，N≥3才进入晋升检查。
- **阻断条件**：N<3 的模式被输出为"待晋升" → 阻断，回退筛选；N≥3 但未提醒 → 回退步骤B2补全。
- **对应步骤**：流程B步骤B2（筛选pending模式）。

### 3. 错误归档格式Schema（接触式防错）

- **防什么**：错误归档字段缺失，导致错误记录无法追溯根因和修复方案。
- **机制**：错误归档必须包含固定字段——编号/名称、日期、类型（5级之一）、描述、根因、修复方案、状态、认知象限。字段缺失 = 物理拒绝写入。
- **阻断条件**：必填字段缺失或为空 → 阻断写入，回到步骤A2按模板补齐字段后再写入。
- **对应步骤**：流程A步骤A2（按格式写入）。

### 3.1 认知象限必填（接触式防错·四维认知轴 step③）

- **防什么**：错误条目缺「认知象限」字段，导致四象限设计哲学·认知轴第二象限（已知未知）无法在成长箱落地、统计断裂。
- **机制**：每条错误归档必须含 `认知象限` 字段，取值为 `已知未知（收集中）` 或 `已知已知（已解决）`。默认 `已知未知（收集中）`（记录时知道有错、在收集模式确认）；Status=resolved/promoted 时须标 `已知已知（已解决/已蒸馏）`（错误已澄清→晋升为已知已知）。
- **阻断条件**：认知象限字段缺失/为空/取值非法 → 与 Schema 其他字段同条件阻断写入，回到步骤A2按 `references/错误记录模板.md` 补齐后再写入。
- **对应步骤**：流程A步骤A2（按格式写入）+ 流程B步骤B4（晋升时同步将认知象限由"已知未知"改为"已知已知"）。

## 功能定位

**不是"单向错误记录器"**，是**"双向成长引擎"**。做四件事：
1. **错误记录**：用户说"记到成长箱/记入错误/计入成长箱/计入错误"时，按格式写入对应文件
2. **晋升检查**：检查pending(N/3)且N≥3的模式，提醒用户晋升
3. **错误蒸馏**：从错误积累中提取洞察（4步：扫描→提取→合并→呈现决策）
4. **经验反哺**：用户说"执行反哺工作/反哺追加/正反哺"时，走反哺写入分支——按反哺 Schema 追加到成长箱/experience/规范反哺日志.md，更新总追踪表+待整合队列，设置事件驱动验证提醒

## 🔒 产出物级联锁（防跳步机制）

步序法（动作步序）—— Step0→Step1→Step2→Step3 强依赖，上步未完成不可执行下步。产出物锁缺失→退回上步重产→仍不可达→中止，不可自行跳过或降级执行。每个刷新流程均按强依赖顺序执行：错误记录→晋升检查→蒸馏→反哺，上步产出物未完成则不可启动下步，阻断条件=产出物空或文件不存在=回到步骤补全。

| 机制 | 原理 |
|------|------|
| **步骤产出物锁** | 每步定义必须产出的具体产物，后续步骤依赖前序产物 |
| **上步校验锁** | 在蒸馏报告生成前、晋升确认前，先读取上一步的产出物文件。产出物缺失或不完整→回溯执行，补齐后再继续 |
| **报告完整性锁** | 蒸馏报告含必填字段清单（详见 references/蒸馏报告模板.md），缺字段=任务未完成 |

**执行规则**：每步开始前声明产出物→执行后确认产出物已生成→跳步=引用断裂=回溯执行。

2. **详细条目**：在当天日期分区下追加完整反哺条目（13字段 Schema，含🔧反哺工具+🧬反哺层级+🔍验证状态+🔍验证触发场景）
3. **待整合队列**（仅当状态=🔴待整合时）：在待整合队列追加一行

#### 步骤 E7：设置验证提醒（事件驱动）

> **v1.6.0变更**：废除30天固定有效期，改为事件驱动验证。依据：成长箱设计哲学§六。

- 反哺整合进规范后，✅DO在`🔍验证触发场景`字段描述触发条件
- **事件驱动验证**：相关场景发生时触发验证（如"设计跨实例协作机制时"→验证跨实例协作相关规则）
- **主动扫描验证**：季度Skill维护时，主动扫描所有待验证反哺条目，检查规则是否被遵循/是否有新僵尸功能
- 验证标准（三态判定）：
  - ✅适用：规则在场景中被遵循，且阻止了错误发生
  - ⚠️需修正：规则被使用但部分不适用，需修正后重新整合
  - ❌不适用：规则在场景中无法遵循或未阻止错误，回退到流程E重新反哺

#### 步骤 E8：补写系统日志

反哺写入完成后，调用系统日志记录"执行了反哺工作"——确保双本账齐全。

#### 步骤 E9：沉淀到规则文件（v1.7.0新增·CAPA第5-6步对标）

> **v1.7.0新增**：反哺日志→规则文件的沉淀机制。解决v1.6.x反哺日志堆积不沉淀的问题。依据：成长箱设计哲学§5.5。
> **业界锚点**：CAPA第5步"制定计划"（AI自动备料）+第6步"执行计划"（用户确认写入）。 [$TRAE_REF](http://m.163.com/dy/article/KD8SQL7B0516900F.html)
> **核心原则**：规则文件写入需要人确认 ≠ 沉淀流程需要人触发——AI主动备料，用户只做确认。

📦 **产出物**：规则文件已更新 + 反哺日志状态改为✅已整合

##### 重要度判定（E4写入后立即执行）

| 重要度 | 判定条件（满足任一） | 路径 |
|:------:|-------------------|------|
| **高** | ①不沉淀会导致正在犯或即将犯同样的错 ②同类反哺≥2次（模式性） | → E9.1立即备料 → E9.2写入 |
| **低** | 不满足"高"的条件 | → 队列等待 → 兜底机制触发时批量备料 |

##### 步骤 E9.1：备料（AI自动·CAPA第5步对标）

✅DO自动执行以下操作——⛔DO NOT等用户指令才备料，原因是AI备料是主动服务，用户只做确认。

1. 按建议落点读取目标规则文件（Read全文）
2. 草拟条文——确定写入哪一节、格式对齐、内容精炼
3. 准备来源标注：`[来源: 成长箱反哺 | 日期: {date} | 反哺标题: {title}]`
4. 呈现给用户："已备好沉淀物料，确认写入[规则文件·章节]吗？"附草拟条文预览

🔌 熔断器
├─ 成功条件：草拟条文+预览呈现给用户
├─ 失败处理：降级——对话输出草拟条文，不阻塞
├─ 可修正参数：目标规则文件路径 → 检查建议落点是否正确
├─ 重试次数：1
└─ 降级方案：对话输出"⚠️ 备料失败，请手动整合"

##### 步骤 E9.2：写入（用户确认后·CAPA第6步对标）

✅DO在用户确认后执行写入。⛔DO NOT未经用户确认直接写入规则文件——原因是规则文件是人的底线约束，AI不能替人做这个决定。

| 用户的响应 | AI动作 |
|---------|--------|
| ✅确认写入 | ①SearchReplace写入规则文件 ②附加来源标注 ③更新反哺日志条目状态：🔴待整合→✅已整合 ④更新总追踪表状态 |
| ❌拒绝写入 | 标记📌独立落地，记录拒绝原因（如"已过时""与现有规范重复"） |
| 🔄要求修改 | 按用户反馈修改草拟条文，重新呈现确认 |

🔌 熔断器
├─ 成功条件：规则文件写入 + 反哺日志状态更新
├─ 失败处理：重试
├─ 可修正参数：写入内容 → 检查格式对齐
├─ 重试次数：1
└─ 降级方案：回退补写

##### 兜底机制（4目标百分百闭环）

| 触发条件 | AI动作 | 闭环目标 |
|---------|--------|---------|
| 重要度=高 | E9.1立即备料 | 重要经验立即沉淀 |
| 低重要度累计≥10条 | E9.1批量备料（按落点分组） | 反哺日志不堆积 |
| 季度Skill维护时 | 主动扫描所有🔴待整合→批量备料 | 兜底 |
| 唤醒Skill启动时 | 扫描🔴待整合数量→提醒 | 检测 |

|------|------|----------|
| 文件读取成功 | 内容已加载到上下文 | ✅DO继续工作 |
| 文件不存在 | 路径错误或文件被删除 | 🔴 报告缺失，不阻塞，告知用户 |
| 无pending模式 | 无达到晋升条件的错误 | ✅DO输出"无待晋升模式" |

| 蒸馏发现critical错误 | Priority=critical但出现<3次 | MAY推荐提前晋升，✅DO用户确认后执行 |
| 无反哺候选 | 用户问"有没有反哺"→AI判断无候选 | ✅DO输出"暂无需要反哺的发现"，终止流程E |
| 重要度=高 | E4写入后判定为高重要度 | ✅DO立即触发E9.1备料，不等用户指令 |

## 禁止行为

| # | 禁止 | 原因 |
|---|------|------|
| 1 | ⛔DO NOT跳过产出物锁直接执行下一步 | 写作链路断裂——后续步骤引用空缺 |
| 2 | ⛔DO NOT未经用户确认直接晋升写入规则文件 | 规则文件是人的底线约束——AI不能替人做这个决定 |
| 3 | ⛔DO NOT蒸馏时修改源文件（LEARNINGS/ERRORS） | 蒸馏是提取洞察——源文件只能标记状态不能动内容 |
| 4 | ⛔DO NOT晋升后不更新INDEX.md | INDEX是唯一的状态总览——不同步=数据漂移 |
| 5 | ⛔DO NOT反哺写入后不补写系统日志（流程E步骤E8必执行） | 双本账少一本=反哺动作无系统记录可追溯 |
| 6 | ⛔DO NOT跳过E3.5质量门禁直接进入E4写入 | 跳过门禁=杂质可能进规范=反哺起反向作用——质量门禁是反哺的物理约束 |
| 7 | ⛔DO NOT未经用户确认直接写入规则文件（E9.2） | 规则文件是人的底线约束——AI不能替人做这个决定，AI只备料不执行 |
| 8 | ⛔DO NOT重要度=高时不立即备料 | 高重要度=不沉淀会正在犯或即将犯同样的错——拖延=放任错误发生 |
