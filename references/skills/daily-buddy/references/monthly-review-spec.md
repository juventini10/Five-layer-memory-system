### 📌 模块排序铁律（v2.1新增·用户2026-08-01明确指令）

> **核心要求**：下月风险预警(8️⃣) / 下月3件事(9️⃣) / 伙伴建议(🔟) 是「下月行动指令」，✅DO 在月报中**置底输出**——排在 📖阅读分析、🔧Skill健康度、🔄月度校准记录、📋1.5校准报告、1.6悬置显形、层级回流总览**全部之后**。

⛔DO NOT 将这3个模块排在审计类模块之前——原因是"最重要的置底才看得清"，置中会被阅读分析/Skill健康等长内容淹没（2026-07月报实测：3模块埋在第7模块与审计模块之间，用户在对话框内未被提醒即漏看）。

> **⚓ 北极星对齐位置**：不进入置底序列。置于「本月目标完成度」dashboard 之后、1️⃣高光槽点之前，作为战略指南针先于所有分析模块出现（纠正"战略层<战术层"倒置：周报已有独立90天对齐，月报此前缺）。

**完整输出顺序（强制）**：
`1️⃣高光槽点 → ❖质量评估 → 2️⃣核心概览 → 3️⃣时间分配 → 4️⃣睡眠 → 5️⃣账号 → 6️⃣阅读 → 7️⃣系统建设 → 📖阅读分析 → 🔧Skill健康 → 🔄校准记录 → 📋1.5校准 → 1.6悬置 → 层级回流 → 【8️⃣风险预警 → 9️⃣3件事 → 🔟伙伴建议】`

**周分解建议写法原则**：
- 必须可量化：「每周1期」而不是「尽量多做」

### ❖ 日记质量评估细则

**定位**：数据源健康检查。在所有下游分析（睡眠/番茄/账号等）之前执行，评估本月日记作为数据源的可靠性。

**评估维度**（全部从日记原文统计，不凭记忆）：

⚠️ **铁律**：S级日记必须从YAML frontmatter `rating: S` 提取。rating字段为空 → 标注"数据缺失"。**禁止凭事件重要性推断评级。**

**提取方式**（所有维度通过前台扫描）：
```bash
# 含金量评级 — 从YAML frontmatter提取
grep -l "^rating: S" YYYY-MM/*.md  # S级日记列表
for f in YYYY-MM/*.md; do grep "^rating:" "$f" | head -1; done  # 全量评级
```

| 维度 | 指标 | 数据来源 |
|------|------|---------|
| ① 完整率 | 写了X天/总天数，断更天数，最长连续断更 | 当月日记文件列表 |
| ② Section完整率 | 含齐12个SECTION的日记比例，缺Section频次分布 | 各日记`<!-- SECTION: -->`标签扫描 |
| ③ 含金量评级分布 | S/A/B/C/N各X篇，异常评级（低含金量却高评级） | 各日记YAML `rating:` 字段统计 |

### ⚓ 北极星对齐模块规范（v2.3新增 · 用户2026-08-01明确指令）

> **定位**：月报=战略复盘层。"如何用AI变现"是90天北极星。本模块把北极星进度从"下月三件事/伙伴建议的脚注级token"提升为**战略指南针**——置于 dashboard 之后、高光槽点之前，作为整月战略方向的显式锚点。
> **设计意图**：纠正"战略层<战术层"倒置——周报已有独立「4️⃣ 90天目标对齐」模块，月报（战略层）此前反而无独立北极星模块，"90天"一词0次出现。质性改变：让北极星在月报里"看得见、能量得、能判断净位移"。

**三腿模型（北极星=如何用AI变现）**：
- 腿1 能力积累：AI/系统能力建设（视频流水线、Skill、自动化…）
- 腿2 载体落地：视频发布 / 账号真实增长（作品出街，非备料）
- 腿3 数据闭环：真实数据回流 / 变现信号（抖音真实指标、收入…）

> 三条腿全满=北极星达成；仅腿1满=能力溢出但未住进房子（战略原地踏步）。

**输出格式（插于「本月目标完成度」dashboard 之后、1️⃣高光槽点之前）**：

## 2. 数据铁律

- ⛔DO NOT凭记忆或推测补数据——原因是AI记忆可能过时或幻觉，必须逐行读取日记源文件
- ⛔DO NOT凭记忆编写系统建设模块——原因是必须读取当月系统日志提取
- 统计流程：**读取全部日记 → 按统一口径分类 → 交叉验证 → 自查一致性**
- **系统建设模块（7️⃣）**：数据来源为系统日志（`[记忆共享中心]/工作日志/系统日志/系统日志_YYYY-MM-DD.md`），提取Skill开发、工具链搭建、流程优化等条目

## 3. 读写分离三阶段执行规范

> 问题背景：月总结需读30个日记+多个系统日志，边读边写容易漏数据、交叉污染。
> 设计哲学：借鉴 Claude Code toolOrchestration.ts 的分区策略——读批量执行、写严格串行。

```
┌─────────────────────────────────────────────────────┐
│  阶段1：只读（BATCH READ）                            │
│  ─────────────────────────────────────────────────  │
│  ① 逐行读取当月所有日记文件（约30篇）                  │
│     → 提取：番茄数/睡眠/能量/完成度/账号进展          │
│     → 额外提取：Section完整性/含金量评级/感悟字数    │
│  ② 逐行读取当月所有系统日志文件                       │
│     → 提取：系统建设条目                              │
│  ③ 禁止在此阶段写任何内容！                           │
│  ④ 所有数据暂存于"数据草稿区"（内存/临时笔记）          │
├─────────────────────────────────────────────────────┤
│  阶段2：只算（COMPUTE）                               │
│  ─────────────────────────────────────────────────  │
│  ⑤ 基于阶段1原始数据进行计算                          │
│     → 汇总统计（总数=各分类之和，否则报错）            │
│     → 占比计算、趋势判断、根因分析                    │
│  ⑥ 交叉验证：                                      │
│     → 日记番茄总和 = 各日番茄累加？                   │
│     → 系统日志条目 = 实际读取到的？                   │
│  ⑦ 禁止在此阶段读取新文件！                           │
├─────────────────────────────────────────────────────┤
│  阶段3：只写（WRITE ONCE）                            │
│  ─────────────────────────────────────────────────  │
│  ⑧ 基于阶段2计算结果，一次性输出完整报告             │
│  ⑨ 十大模块按顺序输出，不回跳、不补充                │
│  ⑩ 输出后运行钩子脚本确认成就检测                     │
│  ⑪ 禁止在输出后发现"漏了"而回头补写！               │
│      （如果漏了，从阶段1重来）                         │
└─────────────────────────────────────────────────────┘
```

### 违规示例（禁止）
```
❌ 写到第5模块发现睡眠数据不够 → 回去读第12天的日记
❌ 边读日记边写模块3（数据可能不完整）
❌ 凭记忆补"大概20多个番茄"
```

### 正确做法（必须）
```
✅ 先把30篇日记全部读完，数据整理成表格
✅ 表格数据验算通过后再开始写第一个字
✅ 发现数据不足时，标记为"待核实"，不回去补
```

## 4. 根因分析与伙伴建议

### 根因分析排版

- 每个根源观点独立一行，不挤在同一行
- 格式：`① **小标题**——具体说明`
- 禁止用分号串联多个观点
- **必须跟"落地动作"表**：没有落地动作的根因分析等于没分析

格式：`| 根源 | 动作 | 怎么执行 |`

### 伙伴建议角度

- 不重复1️⃣高光时刻的内容
- 从数据中发现用户自己没注意到的成长或模式
- 可用子模块"我看到的你没看见的东西"补充

### 哲学框架运用原则

- 哲学框架（斯多葛/存在主义/实用主义/分析哲学/唯物辩证法）和38本笔记知识库是分析工具
- 自然内化在洞察中，不贴标签
- 经典理论（如第一性原理、二八法则、反馈回路）可标注书名和概念，方便回溯

## 5. 报告呈现规范（双声部 · 本月快照 · 进度条 · YAML）

> 来源：用户 2026-08-01 双声部排版决策（F2–F9）· 对齐文件格式规范 v2.0.0
> 设计意图：月报定位为"我的月报"——人读为主、客观为辅；一份文件内用双声部共存，不用文件级分离。

### 5.1 文件格式铁律（强制 · 对齐文件格式规范 v2.2.0 分层）

- ✅DO 月总结报告文件**必须含 YAML Frontmatter**（分层·检索必留 + 合规建议 + 按特性）：
  - 必留（检索+合规）：`type` / `date` / `summary` / `source` / `complies_with: 文件格式规范 v2.2.0` / `author: 皮叔`（默认，⛔DO NOT 写「你」）
  - 按特性保留（月报有迭代史/修订可能）：`title` / `status`（active）/ `version`（语义版本·校准回流迭代）/ `tags`
  - 可省（已查无消费者）：`area` / `related`
  - ⛔DO NOT 正文数据塞 YAML——YAML 是检索索引非内容副本（正文已有评级依据/统计不重复入 YAML=双本账教训）
  - `type` 默认 `reference`（月报主性质=当月记录/洞察，AI 稳定读取）；若强调下月行动可改 `plan`（需用户确认）
  - `date` = 报告实质生成日（ISO `YYYY-MM-DD`）；`summary` ≤40字首因锚点
  - `source` = 本报告权威路径（`{{OBSIDIAN_VAULT}}/1-每日计划/03-月报/YYYY-MM-月总结.md`），防 AI 读非权威副本
