## §一 L3沉淀执行步骤（13步完整清单）

L3沉淀执行步骤:
1. ✅DO: 扫描test_results/下所有评估报告,提取共性模式
2. ✅DO: 识别跨Skill重复出现的问题(如“宪法声明缺失”“版本号不一致”等)
3. ✅DO: 识别评分分布(各等级占比、维度强弱分布)
4. ✅DO: 将提取结果写入 ~/[记忆共享中心]/评估知识库/evolution/L3_沉淀_{YYYY-MM-DD}.md
5. ✅DO: 在交付总结后追加一句提示:"📊 已累计{N}次评估,L3沉淀已生成,路径:evolution/L3_沉淀_{日期}.md"
6. ⛔DO NOT: 在L3沉淀中编造报告中不存在的问题
7. ⛔DO NOT: 每次评估都触发L3沉淀--仅在自上次L3沉淀以来新增报告数≥5时触发（check_selfimprove_gate.py 的 l3_required 判定）
  ⏱️ 时效闸门（v2.5.5新增 · L1自动反哺·来自L3_沉淀_2026-07-08 第六节时效复核）
  > 来源：L3_沉淀_2026-07-08 实测——提取的L2待办（anchor.md缺失 / daily-buddy路径硬编码 / chrold硬编码）经Glob核验全不成立（anchor.md已于Jul6修复、daily-buddy全`~/`合规、chrold非硬编码），沉淀文件记了3条过期假阳性待办。根因=提取待办后未核验文件当前状态即落盘。本闸门在「写待办」前加一道Glob验真，只写仍成立的项，避免误导后续反哺。
  - ✅DO：L3沉淀提取跨Skill待办/问题后、落盘前，对每条涉及具体文件/路径的待办→用Glob核验该文件当前是否存在及状态
  - ✅DO：核验结果分流——①文件已存在/已修复→标记「已解决（核验于{日期}）」，不写入开放待办；②文件仍缺失/状态仍违规→保留为开放待办，标注「当前仍成立（Glob核验于{日期}）」
  - ✅DO：纯机制/非文件类待办（如维度权重设计、触发逻辑缺陷）→跳过核验，直接保留
  - ✅DO：时效闸门与step8反哺派生同门禁——L2挂起待办须经此闸门后才写入evolution第四节
  - ⛔DO NOT：不核验就落盘待办——原因是提取时点的快照≠当前时点，沉淀记过期问题会污染后续反哺决策（皮叔2026-07-08「修跟扫」实测暴露）
  - 🛡️ 正面建模：待办落盘的充要条件是「Glob核验当前仍成立（文件类）或直接保留（机制类）」；过期项标已解决，不占开放待办位
  - 🔍 备选未选（Alternatives Considered）：①落盘后再人工复核→回到「等你提醒」老路，弃；②不记待办只记模式→丢失可行动信号，弃；③写前Glob验真（当前）=兼顾「不靠提醒」与「不记假阳性」
8. ✅DO: L3沉淀生成后**立即执行「反哺派生」**（与提取同门禁闭环，不靠对话触发）——逐条扫描本次沉淀的模式，判断能否转化为评估清单检查项：
   - **可转（L1·纯增强clock-loop自身评估能力·低风险可逆）**：模式A单一数字源 / 模式C被引用文件存在性 / 模式F结构画像防回声 等 → 自动生成候选检查项 + 直接写入Phase X机械验证清单（见验证⑩⑪⑫），同步§6.6备份 + 版本升
   - **不可转/高风险（L2·动具体Skill文件）**：anchor.md缺失 / 拆行数超标 等 → 经⏱️时效闸门核验仍成立→产出挂起待办清单，交付时主动列出等你拍板范围
9. ✅DO: 在交付总结中**主动报告**反哺结果——"🔄 本次L3沉淀自动反哺{N}项检查项（路径：SKILL.md Phase X验证⑩⑪⑫）" 或 "🔄 本次沉淀派生{M}条待办（需你授权范围），见evolution/L3_沉淀_{日期}.md 第四节"
10. ⛔DO NOT: 把反哺留作"等你问才做"——原因是L3沉淀的下游（提取→应用）必须同门禁闭环，否则经验只是死仓库（皮叔2026-07-08指正：为何要提醒才反哺）
11. ⛔DO NOT: 对L2高风险反哺擅自写入具体Skill文件——原因是改主人文件须主人授权，越权即违规
12. 🛡️ 正面建模：反哺分级——L1低风险（纯增强评估器）自动做+主动报告；L2高风险（动具体Skill）产挂起待办+主动列，由你拍板范围
13. 🔍 备选未选（Alternatives Considered）：①反哺全自动化（含改具体Skill）→ AI擅自改主人文件越权，弃；②反哺全人工（等你逐条确认）→ 回到"靠你提醒"老路，弃；③仅L1自动+L2挂起=当前方案，兼顾"不靠提醒"与"不越权"

## §三 对话冲突检测管道·完整细则

> 来源:未知未知前置容器改造(L3深度评估最终方案)。#1探针只在单次评估内扫描T2,本管道补"跨周期记忆"——让评估能比对历史断言。
> 设计哲学:职责分层——AI在提取层按schema输出结构化断言(输入结构化/输出结构化),脚本在判定层做字段比对(可grep可复现),不靠AI主观裁决。判定不是"判断矛盾",是**检测不一致信号**——脚本只输出"潜在冲突"标记,归因留月报。

**硬伤修复(来自三明智L3 Agent B审查):**
- 修复#4(台账加载链路):Phase 0由脚本确定性加载,不靠"AI记得去看"
- 修复#1("先查台账"空心规则):脚本grep校验议题名命中,不靠AI自觉
- 修复#3(#1/#2双触发):#1已处理的议题本周期不重复触发,信号汇总同一面板

**执行步骤(确定性·grep锚定):**

**Phase 0 台账加载(脚本做·修复#4)**
- ✅DO:评估归档后运行 `scripts/load_claim_index.py`
  ```
  python3 scripts/load_claim_index.py
  ```
- ✅DO:脚本输出JSON `{topics: [...], active_entries: N}`——这是已有议题名列表,**强制注入下方Layer 1提取prompt的不可协商区块**
- ⛔DO NOT:跳过Phase 0直接让AI"凭记忆"提取断言——原因是这违背铁律精神(空洞加载=不执行)

**Layer 1 信号采集(AI做·注入式·修复#1)**
- ✅DO:扫描本轮评估过程(评分表+子Agent反馈+progress.md),提取关键断言
- ✅DO:议题名**优先复用Phase 0注入的列表中的已有名称**(确定性,非AI自觉)
- ✅DO:每条断言按schema输出:`议题 / 立场 / 来源(对话|日记|复盘|探针) / 日期`
- ⛔DO NOT:凭空造新议题名而不查注入列表——脚本会grep校验命中,造名=无效

**Layer 2 立场比对+台账写入(脚本做·修复#3)**
- ✅DO:对每条提取的断言调用 `scripts/append_claim.py`
  ```
  python3 scripts/append_claim.py \
    --topic "议题名" --stance "立场陈述" --source 对话 --date YYYY-MM-DD
  ```
- ✅DO:脚本自动做三件事(零AI主观):
  1. grep校验议题名是否命中已有列表 → 命中则复用,不重复造名
  2. 同议题名下不同立场 → 输出 `⚠️ T2冲突信号` + 旧/新立场对比
  3. 追加断言到 `~/[记忆共享中心]/未知未知/断言台账.md`
- ✅DO:脚本输出 `⚠️ T2冲突信号` 时,按悬置区.md §1.6 schema写入 `~/[记忆共享中心]/未知未知/悬置区.md`(T2触发+归属标签双主体判定)
- ✅DO:#1探针已处理的议题,本周期不再由#2重复触发(去重规则——避免双触发噪声)
- ⛔DO NOT:在脚本输出T2信号时做归因——只冻现象,归因留月报显形回看

**监控层(双轨触发·修复#2)**
- 规模触发:月报回看统计断言台账`活跃`条目数(区分累计/活跃),>100条 → 评估引入embedding归并层(扩展接口已预留:议题字段)
- 质量触发:月报回看时注入N条已知冲突样本测recall,recall<90% → 提前引入embedding归并层(与规模解耦——真实失效模式是议题名不一致,与规模无关)
- 📎 承接机制:`daily-buddy/references/monthly-review-sop.md` 第1.6步第4项(断言台账监控回看)——规模统计用`load_claim_index.py`输出`active_entries`,质量抽样用`append_claim.py --dry-run`构造冲突样本测T2信号,均不污染台账
- 阈值(100条)标注为可调参数,随实测废弃率修正(活跃数≠累计数)
