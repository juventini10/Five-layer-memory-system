# 版本命名规范固化引用（判级核心）

> **来源**：版本命名规范 v3.2
> **源头路径**：`~/[记忆共享中心]/记忆蓝图/03_开发规范/版本命名规范.md`
> **引用模式**：固化引用（reference）——clock-loop评估Skill版本判级合理性时读本文件，不每次Read源规范
> **版本检查**：sync_guard.py 固化引用扫描自动比对本文件版本号与源规范版本号
> **固化背景**：2026-07-26你发起"改Skill脱离规范"通用检查改造——三规范此前只固化两份，判级标准在Loop评估维度中缺位

## 一、X.Y.Z 判级语义（源§1）

| 位 | 名称 | 递增条件 |
|:--:|------|---------|
| X | 基底版本号 | 创世基底级变更（底层架构重构） |
| Y | 功能版本号 | 能力拓展级变更（新增核心实用功能） |
| Z | 微调版本号 | 微调优化级变更（细节修复/体验迭代/数据规整） |

## 二A、创世基底级（X位）升级条件（源§2.1·满足任一即X+1·Y/Z归零）

- 记忆系统核心架构发生不兼容变更（如六层→五层、层定义整体重排）
- 底层思维框架整体更迭（第一性/抽象建模/批判验证基座被替换或结构性改写）

> ⛔DO NOT：换主名号已作废（2026-09-01），不凭名号变更进位X

## 二A-b、Skill 级 X.0 判据（源§2.1-b·补款·2026-09-17 你批准落地）

§二A 两条机械触发为**主包/系统口径**。对源§6 适用范围中的 **Skill 文件**，其 X.0 判据映射为：

- **该 Skill 自身核心架构发生不兼容变更**——具体指：**工作流骨架**（主流程步骤结构被推翻/重排）/ **SSOT 模板结构**（中心模板 schema 不兼容变更）/ **触发模型**（触发条件与行为约束规则不兼容反转）三者任一命中即 Skill 侧 X.0 进位，Y/Z 归零。
- **仅新增功能/优化不命中**（归 §2.2 Y 级）——即使改动量大，只要核心架构（上述三者）未发生不兼容变更，不算 X.0。

> 📌 判定先例：awaken-memory-system v7.32 懒加载（行为约束"轻量禁写→可更新自有快照"反转=触发模型不兼容变更）按本条款命中 X.0；v7.35 历史债回填（新增工作流·未推翻骨架）不命中。

## 二B、能力拓展级（Y位）升级条件（源§2.2·满足任一即Y+1·Z归零）

- 新增独立核心功能模块（如脚本体系=路由引擎+铁律硬墙+守卫/自检）
- 新增协议或规则体系（如新增一类机械路由协议）
- 性能显著提升（量级级、可量化）

## 二、微调优化级（Z位）升级条件（源§2.3·满足任一即升Z）

- 修复 bug
- 文档更新（不含新功能）
- 文件同步
- 小的非核心改动
- 配置调整

**判级红线**：改动含**新功能/新步骤/新机制/新检查项** → ⛔DO NOT 只升Z——原因是功能级变更用微调号=版本语义失真=下游依赖方（CHANGELOG审计/发布包/多端同步）误判变更量级。应升Y并归零Z。

## 三、边界判定口诀（源§3）

```
换底层架构 → 升X（创世基底级）
加核心实用功能 → 升Y（能力拓展级）
修细节优化体验 → 只升Z（微调优化级）
```

## 四、Skill判级评估应用（clock-loop消费）

| 检查点 | 判定 | 结果 |
|--------|------|------|
| CHANGELOG最新条目含功能词（新增/新功能/新步骤/新机制/Phase/工作流）但版本相对上一条仅Z++ | 疑似判级偏低 | ⚠️ advisory提示（不计分·人终判） |
| CHANGELOG最新条目仅含修复词（修复/修正/补/同步/typo/漂移）但版本升了Y或X | 疑似判级偏高 | ⚠️ advisory提示（不计分·人终判） |
| 版本判级=半语义判断 | 脚本只做粗筛 | ⛔DO NOT 让脚本自动改版本号——原因是功能词匹配有假阳性（如"新增说明文字"是文档更新），终判权在人 |
| Skill 级判级（源§2.1-b·v3.1） | 工作流骨架/SSOT 模板结构/触发模型任一不兼容变更 | Skill 侧 X.0；仅新增功能/优化→Y 级（判例：awaken v7.32 命中/v7.35 不命中） |
