# MEMORY 设计通用规范 v1.0

> **版本**：v1.0 | **日期**：2026-07-10 | **作者**：皮叔（五层记忆系统·布洛陀版）
> **适用范围**：以 WorkBuddy 为参考实现（本包仅含 WorkBuddy 实例），设计原理从多端实践抽象，可扩展到 Trae Work / Qoder 等平台
> **定位**：MEMORY 设计哲学的宪法级通用规范。各平台 MEMORY 设计哲学文件按本规范执行，结合自身注入机制做适配。平台特有实测与适配见 `02-MEMORY设计实例/`。

## 一、问题起源：为什么需要重新审视 MEMORY.md

### 1.1 通用动机

用户可编辑的系统文件中，谁能排在第一/前二顺位，谁就获得最高的注意力权重——这是 LLM 注意力机制的结构性事实，不依赖具体平台。当 MEMORY.md 被放置在前二顺位时，它承载"快速读我"信息和路径索引的效率远高于其他位置。

> 触发契机（平台实例）：WorkBuddy 端在 2026-06-15 排查回复格式不稳定时发现此问题；Trae 端在 2026-06-16 跟进验证。详见各平台实例文件。

### 1.2 核心假设

> "如果文件在注入链条中排得靠前，LLM 注意力权重更高，执行率就会更高。"

为验证这一假设，需要先回答：**用户可编辑的系统文件里，谁排第一？**

## 二、学术基础：位置即命运——LLM 的注意力分配规律

### 2.1 "Lost in the Middle"：U 型注意力曲线

**论文**：Liu, N.F. et al. *"Lost in the Middle: How Language Models Use Long Contexts."* TACL 2024.（斯坦福/UC Berkeley/OpenAI 联合研究）🟢 同行评审

**核心发现**：语言模型对开头和结尾的信息回忆最好，对中间信息回忆最差——形成 U 型性能曲线。

| 位置 | 性能 | 对注入文件设计的启示 |
|------|------|---------------------|
| 🥇 开头 | 最高 | MEMORY.md 第一/前二顺位 = 天然优势 |
| 🥈 结尾 | 高 | user_query 最近位置 = 天然优势 |
| ❌ 中间 | 显著衰减 | 长文件中部内容容易被"迷失" |

### 2.2 首因效应和近因效应

**来源**：*"LLM Position Bias: Primacy and Recency Effects in Prompts"*（IntuitionLabs, 2025）🟢 引用实证研究

- **首因效应（Primacy）**：因果注意力掩码导致深层网络固有偏向更早 token；早期 token 被反复"过度语境化"，产生累积性巨大影响。
- **近因效应（Recency）**：相对位置编码（如 RoPE）施加基于距离的注意力衰减，天然偏重最近 token。

**核心推论**：MEMORY.md 同时受益于首因效应（排在用户文件最前）+ SOUL.md 受益于"虽不在最前也不在最后"。关键是 MEMORY.md 处于 U 型曲线左端高点。

### 2.3 "Position is Power"：系统提示的特殊地位

**论文**：Neumann, A. et al. *"Position is Power: System Prompts as a Mechanism of Bias in Large Language Models."* ACM FAccT 2025 🟢 顶级会议

**核心发现**：系统提示在文本处理和生成中**优先于用户输入**发挥作用，构成结构性注意力偏好。所有用户可编辑注入文件（MEMORY / SOUL / 自定义指令）都处于"系统提示层"，享有相对于 user_query 的优先级；而 MEMORY.md 在该特权层中常排第一/前二——是**特权中的特权**。

### 2.4 Anthropic 上下文工程指南

**来源**：*"Effective Context Engineering for AI Agents"*（Anthropic 官方工程博客，2025.09）🟢 官方

- **注意力预算**（attention budget）：每个 token 消耗注意力，需精心策划而非堆砌。
- **Goldilocks zone**：不过于硬编码（脆弱），不过于模糊（无引导）。
- **预检索 vs 即时加载**：静态上下文预加载（≈MEMORY.md），动态信息即时检索（≈路径索引）。

## 三、跨产品对比：行业内的注入与记忆机制

### 3.1 五大产品对比

| 维度 | WorkBuddy（实测🟢） | Trae（实测🟢） | Claude Code | ChatGPT | Cursor |
|------|---------------------|----------------|-------------|---------|--------|
| 用户级记忆文件 | `~/.workbuddy/MEMORY.md` | `~/.trae/rules/MEMORY.md` | CLAUDE.md | 云端 Dreaming 记忆 | .cursorrules |
| 注入顺序 | MEMORY→SOUL/IDENTITY→自定义 | IDENTITY→MEMORY→SOUL/USER→PR | 递归加载 CLAUDE.md | 不详（封闭） | 递归加载 .cursorrules |
| 注入通道 | `<user_memory>` 系统原生块 | `alwaysApply` 平台统一注入 | 预加载到上下文 | Dreaming V3 自动提取 | IDE 插件层 |
| 独立记忆通道 | ✅ 有 | ❌ 无 | ❌ 无 | ❌ 无 | ❌ 无 |
| 文件形式 | 单一 Markdown | 单一 Markdown（+frontmatter） | 递归 Markdown | 无文件形式 | 多级 .cursorrules |
| 可编程性 | 🔴 高 | 🔴 高 | 🟡 高 | 🔢 低 | 🟡 中 |
| 透明度 | 🔴 高 | 🔴 高 | 🟡 高 | 🔢 低 | 🟡 中 |
| MEMORY 顺位 | 🥇 第1 | 🥈 第2 | N/A | N/A | N/A |

### 3.2 行业启示

1. **独立注入通道 > 平台统一注入 > 普通上下文加载**：WorkBuddy 的 `<user_memory>` 最强，Trae 的 `alwaysApply` 次之，Claude Code 工具调用最弱。
2. **身份确认优先于记忆导航**（Trae 端视角）：IDENTITY→MEMORY 顺序可能比 WorkBuddy 的 MEMORY→IDENTITY 更符合认知逻辑。
3. **透明度是竞争力**：ChatGPT 封闭，WorkBuddy/Trae 开放——可实测、验证、迭代。
4. **单一文件 > 递归多文件**：递归加载增加不确定性，单一文件可预测。
5. **`alwaysApply` 是 Trae 核心注入机制**：所有常驻文件都通过它注入，无例外。

## 四、战略定位：MEMORY.md = 跨项目系统导航仪

### 4.1 核心定位

> **跨项目系统导航仪——利用第一/前二顺位 + U 型曲线左端高点的注意力优势，承载"快速读我"信息和路径索引，让 AI 在任何项目中都能第一时间了解用户是谁、底线在哪、信息在哪。**

### 4.2 两层模型

| 层 | 内容 | 性质 |
|---|------|------|
| 记忆层 | 跨项目长期偏好、核心身份摘要、项目约定 | 信息性的——"我是谁、我有什么习惯" |
| 指针层 | 路径索引（各系统文件完整路径）、触发开关 | 导航性的——"去哪找更多" |

### 4.3 不放的内容（关键边界）

| 不放 | 原因 | 应该在哪 |
|------|------|---------|
| 完整格式模板 | 格式是品格的行为出口，放 MEMORY 会导致格式劈两半 | → SOUL.md「我怎么产出」段 |
| Skill 自动运行指令 | 软建议，AI 自己判断是否执行，大半不跑 | → 删除或放在 Skill 自身触发条件 |
| 完整铁律/规则 | 太长，重复注入浪费注意力（Anthropic 注意力预算） | → 铁律版按需读取 |
| 动态状态 | 过时快，维护成本高 | → 唤醒 Skill 周期刷新 |

### 4.4 与三大文件的配合（通用）

```
MEMORY.md ← 第一/前二顺位，U型曲线左端高点，跨项目导航
  ├─ 快速读我：核心身份摘要
  ├─ 路径索引：去哪找
  └─ 触发开关：关键行为提醒
      ↓ 指向
SOUL.md ← 品格引擎（完整回复格式在 SOUL.md「我怎么产出」段）
      ↓ 指向
IDENTITY.md + USER.md ← 身份锚点 + 用户档案
      ↓ 指向
自定义指令 ← 执行准则
      ↓ 指向
铁律版 ← 按需读取（MEMORY.md 硬路牌仅放铁律骨架）
```

### 4.5 核心层信息投影策略

CORE.md（L1 核心层）通常无独立常驻注入通道。MEMORY.md 承担核心层信息的**摘要投影**：
- **强调**：将核心身份压成一行摘要。
- **补齐**：核心层装不下的信息（五层记忆系统路径、写入自检原则）。
- **不复制**：不重复 SOUL/IDENTITY/USER 已有内容。

## 五、第一顺位的实际效应与验证

### 5.1 首因效应的实证支持

U 型曲线左端是 MEMORY.md 的天然阵地。两端实测（WorkBuddy 第1、Trae 第2）均落在左端高点，回忆准确率最高。

### 5.2 硬指令 vs 软指令

| 类型 | 示例 | 执行效果 | 学术原理 |
|------|------|---------|---------|
| 硬指令 | "意图分类跳过=回复不完整" | 前二顺位 + 硬指令 = 最强 ✅ | 首因效应 + 无判断空间 |
| 软指令 | "自动运行 skill-lookup" | 判断权在 AI，大半不跑 ⚠️ | 首因不足以覆盖自主判断 |

### 5.3 为什么格式提醒（意图分类、产出签名）不放 MEMORY

**"不拆格式"是架构原则，压倒位置优化。**

| 考虑 | 结论 |
|------|------|
| 注意力权重 | MEMORY 前二顺位 > SOUL 后位 ✅ |
| 语义完整性 | 格式一个源 > 格式劈两半 ✅ |
| 维护成本 | 一个文件改一次 > 两个文件改两次 ✅ |

**最终决策**：格式完整性优先于位置优化。MEMORY.md 只放引用指针不放格式碎片。

## 六、Design Principles

| # | 原则 | 学术/实践依据 |
|---|------|-------------|
| 1 | 职责单一 | Anthropic 注意力预算 + 实测"多源分裂"教训 |
| 2 | U型曲线优先 | Liu et al. (2023) — 关键信息放两端 |
| 3 | 硬指令优先 | 首因效应对无判断空间的内容最有效 |
| 4 | 不拆格式 | 语义完整性 > 位置优化 |
| 5 | 指路不堆货 | Anthropic 预检索 vs 即时加载策略 |
| 6 | 定期巡检 | MEMORY.md 为 AI 可读写文件，需定期检查准确性 |
| 7 | 高透明度 | 开放架构优势——可实测、验证、迭代 |
| 8 | 跨平台一致 | 同类文件百分百一致，平台差异仅在注入机制和路径（来源：Trae 端设计哲学 v1.0） |

## 八、研究局限与后续工作

**局限性**：
1. 注入标志法实测会话次数不足（未做 ≥3 次独立新会话复测）。
2. 缺乏对照实验（A/B 测试待执行）。
3. 学术文献集中于位置偏见领域，未涉更广 LLM memory 机制（如 RAG 注入策略、Agent memory architecture 综述）。
4. 版本依赖性：注入顺序可能随平台版本更新改变。
5. 模型差异：不同平台底层模型注意力分配机制可能有差异。

**后续方向**：
1. 跨会话复测（≥3 次独立新会话）。
2. A/B 对照实验执行（两端联合）。
3. 跨平台验证（Trae / QClaw / QoderWork 等）。
4. 核心身份摘要颗粒度实测。
5. RAG Memory 与静态 MEMORY.md 互补机制研究。
