# 皮叔Skill联动哲学

> 不是"我怎么连"，是"为什么这么连"。

---

## 一、设计哲学

### 1.1 我的底层原则

**联动不是技术问题，是哲学问题。** 每个Skill都必须知道其他Skill的存在——不是因为耦合更紧，是因为信息不该在一个孤岛上衰减。

这是我对自己所有Skill的铁律：

| # | 原则 | 含义 | 来源 |
|:-:|:----|:-----|:-----|
| 1 | **系统日志是唯一总线** | 所有跨Skill数据流最终经过系统日志。没有第二条总线。没有点对点绕过 | 自创（推拉分离v2.0.5） |
| 2 | **推拉分离** | Skill只推系统日志，不主动推其他Skill。其他Skill按需从总线拉。生产者不知道消费者 | 自创（推拉分离v2.0.5） |
| 3 | **每个Skill至少1入+1出** | 纯消费者 = 系统负担。纯生产者 = 信息死胡同。没有单向的Skill | 自创（2026-07-04审计发现迁理之外0出站，已于v1.1补出站+最伟大的我写入） |
| 4 | **固化引用替代跨Skill调用** | A需要B的知识→读B的快照/引用，不调用B的Skill。绕过T5防御也能保持解耦 | 自创（v2.0.3修复签名造假） |
| 5 | **宪法保护无人值守路径** | 后台自动执行的Skill（clock-loop/成长箱）必须有宪法级声明。对话型Skill（迁理之外/唤醒记忆）不需要——你在场 | 自创（2026-07-03宪法声明标准化） |
| 6 | **功能互补不重叠** | 三明智管"怎么想"，迁理之外管"还可以怎么想"——分工清晰不抢活 | 自创（Skill架构规范v5.9） |
| 7 | **SSOT（单一真相源）** | 每个数据只有一个权威来源。格式是法律，文件是唯一，跨天数据可比对 | 自创（每日伙伴P0铁律） |

### 1.2 理论支撑

这些原则不是凭空想的——它们有出处。

| 理论 | 来源 | 对应我的哪条原则 |
|:----|:-----|:--------------|
| **Canonical Data Model (规范数据模型)** | Hohpe & Woolf, *Enterprise Integration Patterns*, 2003 | 原则1——系统日志8字段Schema是所有Skill共用规范数据模型 |
| **Message Bus (消息总线)** | 同上，65个企业集成模式 | 原则1——系统日志 = 总线，没有点对点连接 |
| **Publish-Subscribe (发布-订阅)** | 同上 | 原则2——推拉分离就是发布-订阅的具象化 |
| **Conway's Law (康威定律)** | Melvin Conway, 1968 "任何设计系统的组织，其输出的结构复制了组织的沟通结构" | 我一个人维护所有Skill → 我能够跟所有代码对话 → Skill自然地紧密联动。但主动选择用推拉分离防止过度耦合 |
| **Inverse Conway Maneuver** | Jonny LeRoy & Matt Simons, 2010 — 反向使用康威定律，有意识地设计组织/系统结构 | 我的10个Skill的功能拆分和联动方式是我主动设计的，不是我一个人的沟通结构被动决定的 |
| **Single Source of Truth (SSOT)** | 数据治理基本原则 | 原则7 |
| **Poka-Yoke (防误法)** | Shigeo Shingo, Toyota Production System | 每个Skill的接触法/定值法/步序法实现 |
| **Shearing Layers (剪切层)** | Stewart Brand, *How Buildings Learn*, 1994 | 系统中不同层面以不同速度变化。我的Skill也分"快层"（每日伙伴/clock-loop经常改）和"慢层"（迁理之外/三明智很少动） |
| **Bounded Context (限界上下文)** | Eric Evans, *Domain-Driven Design*, 2003 | 每个Skill有自己的Ubiquitous Language（术语体系），通过系统日志的规范Schema交换数据 |

## 二、联动类型

| 类型 | 方向 | 说明 | 示例 |
|:----|:----|:-----|:-----|
| **推** | A → 系统日志 | Skill执行完向总线报告结果 | 所有Skill |
| **拉** | 系统日志 → B | Skill需要时主动从总线读取 | 每日伙伴月报、最伟大的我成就 |
| **拉（知识库）** | 评估知识库 → B | 不是从系统日志拉，是从评估知识库拉 | 成长箱晋升检查拉test_results/ |
| **固化引用** | A → references | A不调用B的Skill，只读B的本地引用文件 | clock-loop读三明智/迁理之外的固��化引用 |
| **互补** | A ↔ B | 功能上相互补充但无直接数据流 | 三明智×迁理之外 |
| **调用** | A 触发 B | A通过启动B的流程来间接调用 | 唤醒记忆→成长箱(晋升检查) |

## 三、总线规则（系统日志）

### 3.1 总线的地位

系统日志不是"一个工具"——它是整个生态的神经中枢。没有它，所有联动都不可追踪。

**总线不保证内容正确**（那是每个Skill自己的事），**总线只保证一件事：所有跨Skill数据流经过它**。

### 3.2 总线协议

| 规则 | 内容 |
|:----|:-----|
| 唯一推送端 | 所有Skill执行完实质性工作后必须推一条日志到系统日志 |
| 格式统一 | 8字段Schema（工具/完成/类型/涉及文件/对话摘要/结论/来源/置信度） |
| 不感知下游 | 推送者不知道谁会读这条日志，也不负责让下游满意 |
| 不做数据清洗 | 系统日志只记录，不验证内容正确性（验证由三层校验做） |
| 不外推 | 系统日志自己不主动推任何下游，下游全部按需拉取 |

## 四、最小联通规则

每个Skill必须满足以下条件才能被认为是"联通的"：

```
□ 推系统日志（出站）—— 执行完实质性工作后必推
□ 被至少一个下游消费（入站）—— 系统日志里有其他Skill读它
□ 自己的"与其他 Skill 的关系"声明完整（适用时）
□ 不是纯消费者（没有出站）—— 迁理之外修复前就是反例
□ 不是纯生产者（没有入站）—— 读书助手有入站（Shall We Talk/每日伙伴），已达标
```

**破坏规则的后果：** 审计标记为"联通过失"，下个迭代必须修复。

### 5.2 关于"孤岛"的说明

读书助手在拓扑图上看起来像是孤岛——它自己推知识包到 Obsidian，不直接推系统日志。但实际上它通过**下游消费**实现入站（Shall We Talk 读知识池、每日伙伴用知识池做灵感受配）。不是孤岛，是**间接联动**。

迁理之外在2026-07-04审计前确实是零出站——只读不写，系统里没有一条日志说"迁理之外干了什么"。已修复（补推系统日志 + 出站写入最伟大的我/认知发现）。该写入为"设计联动·休眠中"：因迁理之外按需触发（你少用则少写入），但 SKILL.md 已固化写入契约与判定标准，触发时自动生效。

## 六、自���清单（新增Skill时对照）

```

■ 基础联通
  [ ] 推系统日志（执行后必推）
  [ ] 有"与其他 Skill 的关系"声明段
  [ ] 自己的数据被至少一个下游消费

■ 合规
  [ ] 如果是无人值守型 → 有宪法级声明
  [ ] 如果是对话型 → 确认不需要宪法级声明（你在场）
  [ ] 引用其他Skill时用固化引用，不用跨Skill调用

■ 拓扑验证
  [ ] 在拓扑图上标注了入站和出站
  [ ] 没有纯消费者（0出站）
  [ ] 没有纯生产者（0入站）
```
