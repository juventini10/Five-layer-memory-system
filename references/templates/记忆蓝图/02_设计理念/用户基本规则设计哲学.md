# 用户基本规则设计哲学 — S级架构文件

> 本文档是用户基本规则体系的最高设计哲学。记录"为什么这样做"，不重复"怎么做"。
> 版本：v1.6 | 创建日期：2026-06-22 | 来源：v1.5→v1.6 五级标注体系对齐指令编写规范v3.5（§4.4系统级NEVER/MUST→DO NOT/DO/SHOULD NOT+新增§4.4.1五级标注体系说明+§2.2/§2.4历史引用更新）

## 一、文档定位

用户基本规则是布洛陀五层记忆系统的**行为约束层**——它不存储知识（那是CORE/SHADOW的职责），不定义流程（那是Skill的职责），只定义**AI在所有场景下不可逾越的行为底线**。

三个文件的关系：

```
摘要版 (≤80行) ──→ alwaysApply注入（源文件 frontmatter: true → WorkBuddy 平台层保证每次注入，非依赖 MEMORY 入口链）
铁律版 (≤220行) ──→ 按需读取（12条铁律全文 + 加载时机索引表 + 执行规范。2026-06-25裁剪：删交互风格/触发命令/路由表/指令优先级，补010/011/012，Skill版本号全移除）
详解存档 (~240行) ──→ 边缘情况按需读取（规则冲突/修改/深度解释。2026-06-25裁剪：删附录空标题）
```

## 二、设计溯源：四路权威理论

### 2.1 Anthropic Constitutional AI (Bai et al., 2022)

**核心主张**：用少量自然语言原则替代大规模人类反馈标签，通过"批判-修订"循环将原则转化为监督信号。

| CAI原则 | 布洛陀映射 | 说明 |
|---------|-----------|------|
| 宪法是少数可读原则（16条） | 12条铁律 | 数字接近，Anthropic 的 16 条来自临时迭代，我们的 12 条来自实际使用蒸馏 |
| 批判-修订循环 | 成长箱蒸馏 | CAI 用 AI 批判 AI → 我们用人（用户）批判 AI，写入成长箱 → 3次触发后晋升铁律 |
| 原则多样性 > 单一原则 | 铁律-008/009 强启动 + 其余按需 | 不是 12 条全部强启动，而是核心 2 条强启动 + 10 条按需——注意力预算最优分配 |
| 透明可读 | 三层分离 | 摘要版一眼扫完，铁律版完整可读，详解存档可审计 |

**关键差异**：CAI 的宪法是训练时的监督信号，我们的铁律是推理时的行为约束。前者改模型参数，后者改模型行为——两者互补但不互替。

---

### 2.2 Instruction Hierarchy (Wallace et al., 2024, OpenAI)

**核心主张**：LLM 应像操作系统一样建立指令优先级——System > User > Tool Output，低优先级指令冲突时忽略或拒绝。

| 指令层级原则 | 布洛陀映射 | 说明 |
|-------------|-----------|------|
| System > User > Tool | MEMORY.md(系统注入) > 铁律版(用户规则) > 外部数据 | 铁律版虽由用户编写，但在系统注入层面处于"用户规则"层 |
| Context Ignorance 训练 | 铁律-002 实事求是 | "未验证标⚠️"是推理时模拟 Context Ignorance——不确定时不瞎编 |
| 对齐/不对齐指令区分 | 铁律-008 意图分类 | 每轮先分类再回答——本质是判断"当前指令是否与规则对齐" |
| 系统消息保护 | MEMORY.md 禁止行为 | "⛔DO NOT 复制格式模板"（v7.8.1已从NEVER升级为五级标注）防止上下文冗余稀释核心约束 |

**关键启示**：AIAvatarOS 的 S/C/I 分类本质上是把 Instruction Hierarchy 的 System/User/Tool 映射到了规则文件内部——S 类规则相当于 System Level，C 类相当于 User Level，I 类相当于 Tool Level。我们的三层文件结构（摘要/铁律/详解）是按**注入频率**而非**优先级**分层——这是两种不同的分层逻辑，各有合理性。

---

### 2.3 Context Engineering (Anthropic, 2025)

**核心主张**：上下文是有限资源（注意力预算），应通过"渐进式披露"让 Agent 在运行时逐层发现信息。

| Context Engineering 原则 | 布洛陀映射 | 说明 |
|-------------------------|-----------|------|
| 注意力预算（n²关系稀释） | MEMORY.md ≤4,000字符 | 上下文长度增加→关系捕获能力下降→只放触发开关不放全文 |
| 渐进式披露（Progressive Disclosure） | 三层文件结构 | 摘要版(首层轻量) → 铁律版(中层按需) → 详解存档(深层边缘) |
| 最小高信号令牌集 | 铁律骨架 ~185字符 | MEMORY.md 的铁律骨架只是"文件名+口诀"，细则按需 Read |
| 系统提示只放稳定高信号指令 | 硬路牌段 | 意图分类、产出签名、铁律骨架——全场景必用，永不变化 |
| 按需加载是扩展模式 | Skill 加载 | 不加载全部 Skill，只在触发时按名加载 |

**关键矛盾**：AIAvatarOS 的单文件宪法（~80行）把这套逻辑内化到了一个文件里——头部轻量区(每轮读) + 底部详情(按需)。我们的三层文件结构更激进——三个独立文件，完全物理隔离。两者都解决了注意力预算问题，但解法不同：
- 单文件 = 一个文件两段式（GC 友好，但耦合）
- 三文件 = 三个文件独立维护（解耦友好，但同步成本高）

---

### 2.4 Agent Constitution (GitHub/dakshjain-1616, 2026)

**核心主张**：将 Agent 的行为规则声明为 YAML 配置文件，包含规则名、触发条件（condition 字段）、动作（block/notify）、严重级别（severity），运行时通过 AST 评估执行。

| Agent Constitution 原则 | 布洛陀映射 | 说明 |
|------------------------|-----------|------|
| YAML 声明的 condition 字段 | AIAvatarOS 的"加载时机"字段 | 两者都是规则自带的触发条件描述——这是关键创新点 |
| AST 安全评估（无 eval） | AI 自然语言匹配 | 我们不执行代码级评估，用 LLM 做自然语言条件匹配 |
| block/notify 动作分类 | 铁律的硬指令 vs 软建议 | 铁律版原用硬指令（NEVER/MUST），v7.8.1已升级为五级标注（DO NOT/DO/SHOULD NOT）——区分真红线与强建议 |
| PII 检测 | 无 | 布洛陀不处理外部用户数据，不需要 |
| 审计日志 | 系统日志 + 变更日志 | 已有日志体系，不需要额外审计层 |

**关键启示**：Agent Constitution 的 `condition` 字段和 AIAvatarOS 的"加载时机"字段是同一件事的两种实现——前者是程序化条件（`tool_name in ['rm', 'unlink']`），后者是自然语言条件（"创建或修改任何 SKILL 时必须执行"）。我们的铁律版当前两者都没有——这是核心优化方向。

## 三、标杆对标：AIAvatarOS co_mechanism

### 3.1 对方的核心创新

```
co_mechanism.md (~80行)
├── 头部轻量区（每轮必读）
│   ├── 执行流程4步（不可跳过声明）
│   └── S类规则索引（7条，含加载时机）
│
├── S类规则详细（7条，每条约50-100行）← 按需Read
├── C类规则（外引文件）← 按需加载
└── I类规则（子系统调用）← 按需加载
```

| 创新点 | 具体实现 | 理论依据 |
|--------|---------|---------|
| 加载时机字段 | 每条S类规则配一句完整触发条件 | 解决"AI怎么知道何时读"的自举悖论 |
| 不可跳过声明 | "这不是建议，是硬约束。不可跳过。" | Instruction Hierarchy 的 privileged instruction 训练 |
| S/C/I 三级分类 | 按优先级的垂直分层 | Instruction Hierarchy 的 System/User/Tool 映射 |
| 单文件宪法 | 所有规则在一个文件内 | 降低维护成本，但增加单文件复杂度 |
| 远程升级 | `remote_upgrade_version` 字段 | Agent 自我更新能力 |

### 3.2 双方对标矩阵

| 维度 | AIAvatarOS | 布洛陀（当前） | 布洛陀（优化后·本文目标） |
|------|:----------:|:------------:|:---------------------:|
| 入口文件 | 单文件 co_mechanism.md | MEMORY.md（路径索引） | 不变——MEMORY.md 是五层入口 |
| 规则组织 | S/C/I 三级（同一文件） | 摘要/铁律/详解（三文件） | 不变——三文件是已稳定架构 |
| 触发机制 | ✅ 加载时机（条件句） | ⚠️ 关键词列表（MEMORY.md内） | → 加载时机（铁律版内） |
| 强制程度 | 🔴 "不可跳过" | 🟡 硬路牌（偏软） | → 强化为"硬约束" |
| 加载方式 | 每轮读头部 → 匹配加载时机 | 每次注入 MEMORY → 关键词匹配 | → 注入 MEMORY → 扫描铁律版加载时机 |
| 规模 | ~80行单文件 | 摘要70行+铁律246行+详解89K | 不变 |
| 远程升级 | ✅ | ❌ | 暂不引入（六端同步复杂） |

### 3.3 关键差异分析：单文件 vs 三文件

| 维度 | 单文件宪法 | 三文件分层 |
|------|----------|-----------|
| 维护成本 | 低（一个文件改一处） | 中（改规则需同步三处版本号） |
| 读取效率 | 低（读头部70行就够了，但同文件） | 高（摘要版独立注入，铁律版按需 Read） |
| 扩展性 | 弱（80行后结构拥挤） | 强（详解存档89K不挤占轻量入口） |
| 规则发现 | 强（加载时机在规则旁边） | 弱（当前触发词在 MEMORY，不在铁律版） |
| 注意力预算 | 优（头部 ~30行 → 匹配 → 读详细） | 优（摘要版 ~70行注入 → 匹配 → 读铁律版） |

**结论**：三文件结构在规模上更优（详解存档89K不可能塞进一个文件），但触达效率弱于单文件。优化方向是**借鉴单文件的自描述触发**——把加载时机放到铁律版自身，而不是依赖 MEMORY.md 的中间层。

## 四、布洛陀规则设计哲学

### 4.1 核心设计原则

#### 原则一：注意力预算优先

> 规则的注入必须服从上下文窗口的稀缺性。只注入"触发开关"（路径+触发条件），不注入"执行手册"（完整细则）。
>
> — 来源：Anthropic Context Engineering；映射：MEMORY.md ≤4,000字符的铁律骨架

#### 原则二：触发条件自描述

> 每条规则自身携带"我何时生效"的触发条件。AI不是"判断自己需要什么规则"，而是"扫描所有规则的触发条件，匹配→加载"。
>
> — 来源：AIAvatarOS 加载时机 + Agent Constitution condition；映射：铁律版加载时机列

#### 原则三：渐进式三层披露

> 第一层（摘要版）：高频场景的速查表 → 第二层（铁律版）：12条铁律的完整行为约束 → 第三层（详解存档）：边缘情况和深度解释。
>
> — 来源：Context Engineering 渐进式披露；映射：三文件物理隔离

#### 原则四：单点触发、单向依赖

> MEMORY.md 是唯一的规则入口。铁律版不反向引用 MEMORY.md。摘要版不反向引用铁律版。依赖箭头永远单向：MEMORY → 铁律 → 详解。
>
> — 来源：§6.1 单一来源原则；映射：不存在循环引用

#### 原则五：硬约束优于软建议

> 规则的强制性声明必须在规则自身，而非外部注释。"不可跳过"是规则的一部分，不是使用说明的一部分。
>
> — 来源：Instruction Hierarchy privileged instruction；映射：铁律版头部声明

### 4.2 三层分离的设计理由

| 为什么不是单文件？ | 理由 |
|------------------|------|
| 详解存档 89K | 塞进一个文件 → 每轮注入 89K → 注意力预算爆炸 |
| 摘要版 70行 | 高频 Q&A 需要独立快速扫描——混在铁律版里干扰铁律细节 |
| 铁律版 246行 | 12条完整铁律 + 路由表需要独立完整性——混在摘要版里丢失细节 |
| 版本同步 | 三层共享版本号——改一处升三处，这是同步成本，也是完整性保证 |

| 为什么不能只留铁律版？ | 理由 |
|----------------------|------|
| 摘要版的 Q&A | 认知层（Q8-Q17）和行为层（Q18-Q23）不是铁律——它们描述用户是谁、不是规定 AI 怎么做。混入铁律版会导致"铁律"语义污染 |
| 详解存档 | 边缘情况解释、为什么这样设计——不是行为约束，是知识库。混入铁律版会让铁律版膨胀到不可维护 |

**三层分离不是过度设计，是语义隔离**：摘要版回答"用户是谁"，铁律版规定"AI怎么做"，详解存档解释"为什么"。

### 4.3 加载时机 vs 关键词匹配

**当前方案的问题**（MEMORY.md 硬路牌第15-18行）：

```
其余场景触发时→Read铁律版
001先看清|002实事求是|003灵感验证|...
```

三个缺陷：
1. **自举悖论**：AI需要匹配"场景"→但不知道铁律有哪些，"匹配"无从谈起
2. **维护分裂**：触发锚点在 MEMORY.md，细则在铁律版，加新铁律要改两个文件
3. **信息损失**："001先看清"是4个字的口诀，不足以让 AI 精确判断"当前是否触发001"

**优化方案（借鉴AIAvatarOS + Agent Constitution）**：

| 当前（关键词） | 优化后（加载时机） |
|-------------|-----------------|
| `001先看清` | `加载时机：收到任何任务指令时，未理解清楚前不得开始执行` |
| `002实事求是` | `加载时机：输出涉及数据/引用/事实断言时，无可靠来源标注⚠️` |
| `005删除防护` | `加载时机：操作涉及删除/移动/覆盖/批量修改文件时` |
| `位置：MEMORY.md` | `位置：铁律版自身（索引表）` |

MEMORY.md 硬路牌改为：

```
- **铁律骨架**：008/009已内置。其余→先扫描铁律版头部索引表的「加载时机」列→匹配则Read细则。
  细则见：`[记忆共享中心]/记忆规则/用户基本规则-铁律版.md`
```

**关键变化**：触发逻辑完全在铁律版内部，MEMORY 只存一条指向指令。加新铁律→只在铁律版加一行索引，不碰 MEMORY。

### 4.4 强制程度的分级

| 级别 | 声明方式 | 适用范围 | 来源 |
|:----:|---------|---------|------|
| 🔴 宪法级 | "不是建议，是硬约束。不可跳过" | 铁律-001~012 全文 | AIAvatarOS co_mechanism |
| 🔴 系统级 | ⛔DO NOT / ✅DO / ☑SHOULD NOT（v7.8.1对齐指令编写规范v3.5五级标注） | 单条铁律的具体禁止/强制行为 | 现有铁律版 |
| 🟡 路由级 | "触发时→Read" | 铁律索引表的加载时机 | 新增 |

> **v1.6更新**（2026-06-29）：系统级标注从旧版"NEVER"/"MUST"两极升级为五级标注（DO/SHOULD/MAY/SHOULD NOT/DO NOT），对齐指令编写规范v3.5+Skill架构规范v5.0。详见§4.4.1五级标注体系说明。

### 4.4.1 五级标注体系（v1.6新增）

> **来源**：指令编写规范v3.5 §1.1 + Skill架构规范v5.0
> **变更原因**：12处NEVER导致"NEVER通货膨胀"——所有规则都"绝对禁止"等于没有重点。五级标注让AI区分真红线（DO NOT）和强建议（SHOULD NOT）。

| 标注 | 含义 | 例外 | 对应旧版 |
|:----:|:-----|:-----|:---------|
| ✅ **DO** | 必须采纳 | 需例外须事先说明理由 | MUST |
| ☑ **SHOULD** | 强烈建议 | 有合理理由时可例外 | — |
| **MAY** | 可选 | 自由判断 | — |
| ☑ **SHOULD NOT** | 强烈不建议 | 有合理理由时可例外 | — |
| ⛔ **DO NOT** | 禁止采纳 | 需例外须事先说明理由 | NEVER |

宪法级的声明放在铁律版文件头部（第3-4行），在每条细则之上。它回答的问题是：**"这个文件的规则是建议还是强制？"** ——答案是强制，且必须在第一眼就看到。

## 五、架构决策记录

### ADR-001：三层分离而非单文件

- **日期**：2026-05-24（v7.7.0 基线）
- **决策**：用户基本规则分为三个独立文件（摘要/铁律/详解），而非单文件宪法
- **理由**：详解存档 89K 无法塞入单文件；摘要版的认知层 Q&A 与铁律的行为约束语义不同；三文件物理隔离符合渐进式披露原则
- **代价**：版本同步成本（三层共享版本号，改一处升三处）
- **替代方案被拒绝**：单文件二段式（头部+底部）在详解存档 89K 的场景下不成立

### ADR-002：MEMORY.md 是最小入口而非完整规则

- **日期**：2026-06-04（MEMORY.md v3.0→v3.3 期间）
- **决策**：MEMORY.md 只存路径索引和触发开关，不存完整规则
- **理由**：注意力预算 ≤4,000字符；MEMORY.md 的职责是"让 AI 知道去哪找"，不是"让 AI 记住规则"
- **代价**：需要额外的 Read 操作

### ADR-003：铁律骨架改为铁律版自带加载时机（已完成·2026-06-22）

- **日期**：2026-06-22
- **决策**：铁律骨架（12条口诀）从 MEMORY.md 移除，改为铁律版头部加载时机索引表；MEMORY.md 只留指向指令
- **理由**：解决自举悖论 + 维护分裂问题；触发条件应属于规则本身，不属于入口文件

### 8.1 加载时机列完整草稿

基于铁律版 v7.7.0 12条铁律全文，逐条撰写加载时机：

| 编号 | 名称 | 加载时机（触发条件句） | 口诀 |
|:----:|------|------------------------|------|
| 001 | 先看清，再动手 | 接收到涉及文件修改/创建/删除/移动/覆盖/批量操作的任务指令时，必须在执行前先 Grep/Read 确认现状 | 分析→呈现→确认→执行 |
| 002 | 实事求是底线 | 输出内容涉及数据断言、数字（行数/字数/百分比/版本号）、事实引用、文件路径、代码模式、"记忆中说"的内容、**写入记忆或 MEMORY.md 时** | 未验证标⚠️，没读过不编 |

| 005 | 删除防护 | 操作涉及文件/目录删除、文件移动（mv）、文件覆盖、批量修改≥5文件时 | trash不用rm→软链接必查→commit再改→原始先备份 |
| 006 | 深度模式结构化 | 用户明确要求"全面/深度/严谨/合理评估/分析"或触发三明智Skill时 | 见三明智Skill |
| 007 | 批判验证优先 | 输出重要结论、评估性判断、推荐建议时；回答"靠谱吗/风险/证据/验证"类问题时 | 先批判自己，再批判外部 |

**编写原则**（why 而非 what）：
- 每条加载时机是一句**完整自然语言条件**，AI 做的是 `if 用户输入 contains 加载时机关键词 → Read对应细则`
- 008/009 标注"已内置"而非省略——保留完整行让索引表不丢条目，但明确这两条不需要额外 Read
- 加载时机描述的是**场景**而非**操作**——"收到请求时"而非"执行 Read 后"——因为 Read 动作是评估结果，条件本身不应该嵌套自引用

### 8.2 嵌入位置决策

**二选一：①头部集中索引 vs ②散入每条细则正文**

| 维度 | ① 头部集中（推荐） | ② 散入细则 |
|------|:--:|:--:|
| AI 扫描效率 | ✅ 读前 30 行 → 匹配 → 跳转到细则 | ⚠️ 需扫描完整 246 行才能集齐 12 条条件 |
| 维护便利 | ✅ 12 条加载时机一眼看到，改一处不改细则 | ⚠️ 加载时机和细则物理分离，改了细则可能忘改条件 |
| 对标 AIAvatarOS | ✅ 一致——对方也是头部索引表 | ⚠️ 不一致 |
| 对细则正文侵入性 | ✅ 零侵入——细则正文不改一字 | ⚠️ 每条细则头部需加"加载时机"字段 |
| 版本升级路径 | ✅ 铁律版正文可保持不变 | ⚠️ 改 12 处细则正文 |

**决策：选①头部集中**。理由三条：
1. AIAvatarOS 已验证此模式的可用性（S 类规则索引表在文件头部）
2. 细则正文不动——本次改造最小化原则，只加索引表，不改 12 条细则的正文
3. 索引表本身就是"轻量区"——每次触发时 AI 只需 Read 铁律版的前 30 行即可完成匹配

**插入位置**：铁律版第 12 行 `---`（分隔线）之前，第 3-11 行文件头注释之后。即在 `## 📐 回复格式` 之前的位置。

```
[文件头注释 3-11行] ← 不动
[新增加载时机索引表] ← 插在这里
--- ← 原有分隔线
## 📐 回复格式 ← 以下全文不动
```

## 十、规则TTL（时效管理）（2026-06-23 新增）

> **设计来源**：Tian Pan《知识半衰期问题》(2026.5)——73% 的部署在 90 天内因知识过期出现准确率下滑 + Beefed.ai《知识库维护与审计最佳实践》——knowledge SLA 治理框架
> **理论依据**：不同类别的内容以根本不同的速率衰减。规则亦然——不是所有规则需要同样的有效期。

### 10.1 三层TTL模型

三层规则文件高度联动——改一层必然波及另外两层。因此TTL不应各层独立设置，而是**三层统一采用 90d（季度审视）**，同时审视、同时更新、同时升级版本号。

| 层级 | 对应文件 | TTL | 过期处理 |
|:----:|---------|:---:|---------|
| 铁律版 | 底线原则（变动极少） | **90d** | 统一审视，有冲突时更新版本号 |
| 摘要版 | 用户速查（习惯漂移） | **90d** | 统一审视，习惯漂移时更新 |
| 详解版 | 边缘细则（随使用变化） | **90d** | 统一审视，过期规则归档至记忆琥珀 |

### 10.2 TTL标注格式

三个规则文件头部采用统一格式，过期日期三文件同步设置：

```
> TTL: 90d 🔥 | 写入：{YYYY-MM-DD} | 过期：{YYYY-MM-DD}
```

- 三个文件使用同一套写入日期和过期日期
- 到期后一起审视、一起更新版本号
- 版本号升到 v7.9.0 或 v7.8.1 取决于改动大小（见版本命名规范）

### 10.3 执行机制

| 执行者 | 动作 | 触发时机 |
|--------|------|---------|
| 每日伙伴·月报生成（工作流F） | 扫描三个文件头部过期日期。如果 **过期日期 ≤ 当月报日期 + 30天**（即过期将在下次月报前到来或已过期），标记为"TTL即将到期"，列入月报待处理清单 | 每月月报生成时 |
| 成长箱·晋升流程 | 晋升时标注TTL=90d+过期日期（与三层文件同步） | 晋升写入前 |

**TTL扫描规则：**
- 只检查头部过期日期，不逐条扫描内容
- 如果即将过期→月报输出提醒："三个规则文件TTL将于{YYYY-MM-DD}到期，请在过期前审视"
- 审视完成后按实际修改情况更新版本号，重置三个文件的写入日期和过期日期

### 10.4 归档策略：失效但不丢弃

归档至记忆琥珀的规则保留以下信息：
- 原规则内容 + 失效日期
- 失效原因（超过审视周期未触发/被新规则取代）
- 来源文件 + 晋升来源（如适用）

> **原则**：旧事实不覆盖，只关闭。与时间知识图谱的"invalidate but don't discard"一致。
  - 记忆规则目录清理：36→25文件
  - changelog 剥离：三文件头只留当前版本+来源
- **验证**：三项工程原则（最小披露/单一职责/连贯性最大化）独立验证了最终的三层三角结构——命令层(铁律) / 上下文层(摘要) / 裁决层(详解)——三者职责无重叠、单向依赖、规模最优化

### 9.5 三层分离的工程原则（三项独立来源交叉验证）

| 原则 | 来源 | 对三层设计的约束 |
|------|------|----------------|
| **最小充分披露** | Anthropic Context Engineering (2025)："系统提示只放稳定高信号指令"——文件越大，每多一行 AI 越可能迷失在细节里 | 详解版必须从 ~1450行瘦到只为 AI 边缘执行服务的规模 |
| **单一职责（AI 版本）** | Zylos Research (2026)：Claude Code 的 110+ 条件注入串证明了——每段注入只有一个清晰目的时执行最可靠 | 铁律版=命令层、摘要版=上下文层、详解版=裁决层——三者职责不能有重叠 |
| **连贯性最大化** | Anthropic (2025)：Agent 在多步任务中准确率从 90%+ 跌到 10-15%，根因是上下文污染——AI 读了无关内容后失去了对核心任务的"锚" | 详解版只能保留"AI 碰到铁律不够用时才会翻"的内容——不能让 AI 读到含铁律正文/摘要内容的冗余段落 |

> 三项原则从不同角度独立论证了同一结论：三文件必须职责不重叠、各自最小化、单向依赖。任何违反—层膨胀、内容重复、或 AI 在污染上下文里迷失—都会破坏整个规则触达系统。

## 十一、WB 平台物理约束下的规则加载模型（2026-07-17 新增）

> **来源**：讨论"用户基本规则能否自动让系统读取"→查阅权威资料→发现 WB 平台物理天花板
> **理论依据**：CodeBuddy CLI 团队指南（MEMORY.md前200行注入） + DeepWiki phuetz/code-buddy（BootstrapLoader源码分析） + juejin 实测报告（压缩机制·无豁免）

### 11.1 三层物理约束

用户基本规则要"系统级自动加载"，不可绕过以下三层物理天花板：

```
Layer 1: BootstrapLoader 系统注入
├── 每次对话启动时自动执行
├── 加载文件：SOUL.md + IDENTITY.md + USER.md + MEMORY.md(前200行)
├── 预算上限：20,000 字符（四文件共池）
└── 不可跳过——WB 平台层保证

Layer 2: MEMORY.md 硬路牌触发
├── 随 Layer1 注入（前200行以内）
├── 条件触发：「规则场景时」→ Read 铁律版索引表 → 匹配铁律
└── 可被上下文压缩影响

Layer 3: Context Compression 天花板
├── 10% 触发轻量压缩（重述对话、精简工具输出）
├── 70-92% 触发深度压缩（旧信息压为摘要）
├── 无豁免——系统注入和对话内容一视同仁
└── 压缩后规则可能只剩摘要中的半句话
```

**核心推论**：用户基本规则要"系统级自动加载"，只能抢占 MEMORY.md 前 200 行内的黄金位置。Layer2 和 Layer3 的不可靠性意味着——规则要么在 Layer1 注入时自带进来，要么就可能在所有对话中不可达。

### 11.2 版本校验：「自动系统读取」的最高形态

在 WB 物理约束下，"规则全文自动注入每次对话上下文"是不可行的（BootstrapLoader 20K 池已满 + 压缩无豁免）。最高可靠形态是**启动级版本校验**：

```
每次对话启动 → Read 铁律版头部版本号（前15行）
  ├─ 版本号 ≠ 记忆中版本号 → Read 铁律版全文 + 更新记忆版本
  └─ 版本号 = 记忆中版本号 → 信任当前规则，仅按需触发铁律
```

- **落点**：MEMORY.md 铁律骨架段（前 200 行以内，BootstrapLoader 自动注入）
- **成本**：Read 铁律版头部 15 行（~1KB），可忽略
- **本质**：不是"规则全文注入"，而是"每次对话先确认规则没变"——自动读取+比对即在此实现
- **落地日期**：2026-07-17（MEMORY.md 铁律骨架段已追加版本校验行）

### 11.3 规则设计的反推原则

从三层物理约束反推规则文件的设计原则：

| 约束 | 反推原则 |
|------|---------|
| 前 200 行 = 金矿 | 核心约束（版本校验、硬路牌、关键路径）必须优先占用此位置 |
| 20K 字符共池 | 不在 MEMORY.md 放非紧急内容——占用的是 SOUL/IDENTITY/USER 的预算 |
| 压缩无豁免 | 规则触发逻辑必须具备 fallback——"若上下文压缩导致索引表不可达，默认按 001+002+005 覆盖" |
| Layer1 不可跳过 | 版本校验借 Layer1 注入 → 自动执行，不依赖 agent 记性 |

### 11.4 ADR-008：规则加载机制从"被动条件触发"升级为"启动级版本校验+条件触发兜底"

- **日期**：2026-07-17
- **决策**：在 MEMORY.md 铁律骨架段追加版本校验行，每次对话启动时自动 Read 铁律版头部版本号比对。版本一致→信任规则仅按需触发；不一致→Read全文更新。
- **理由**：查阅 WB 平台权威资料后确认——MEMORY.md 前 200 行由 BootstrapLoader 自动注入（不可跳过），但 Context Compression 对系统文件无豁免。规则全文注入不可行，版本校验是物理约束下的最高可靠形态。
- **实施**：MEMORY.md 铁律骨架段追加 3 行（在 200 行以内）；版本号位置——铁律版 frontmatter `version:` 字段（前 15 行）。
- **代价**：每次对话多一次 Read（头部 15 行 ~1KB），token 代价可忽略。
- **验证期**：2026-07-17 → 2026-08-16（30 天，观察是否有效减少规则漂移）

### 11.5 与现有设计哲学的互补

本节（§十一）与 §四（布洛陀规则设计哲学）互补：
- **§四** 讲的是"规则内部如何组织"——注意力预算、渐进披露、三层分离、自描述触发
- **§十一** 讲的是"规则外部如何被加载"——BootstrapLoader 物理约束、压缩天花板、版本校验作为最高形态

两者联合回答同一问题：**用户基本规则如何可靠地触达 AI**——前者管设计，后者管物理。
