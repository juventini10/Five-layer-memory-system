# 记忆琥珀设计哲学 — 物理级文件哨兵的认知基础

> 本文档是布洛陀五层记忆系统**记忆琥珀子系统的顶层设计哲学**。记录"为什么用 fswatch 物理监听、内容哈希去重、机制代替意志力"，不重复"amber-backup.sh 怎么装怎么跑"（那是操作手册的职责）。
>
> 与代码的关系：**哲学是宪法，代码必须符合宪法，而非宪法去适配代码**。

---

## 一、文档定位

记忆琥珀是布洛陀五层记忆系统的**时间胶囊层**——它不定义规则（那是铁律/SKILL.md 的职责），不存储运行时状态（那是状态层/情境层的职责），不做跨文件同步（那是派生镜像机制的职责），只做一件事：**文件被修改时自动留底，让任何破坏性操作都可以回滚到上一个可用版本**。

### 三份文件的关系

```
记忆琥珀设计哲学.md（本文）──→ 宪法级：为什么这样设计，不可违反的原则
        ↓
amber-backup.sh + amber-fswatch-wrapper.sh ──→ 实现层：代码必须符合哲学
        ↓
记忆琥珀系统文档.md ──→ 操作层：怎么用、怎么排查、怎么管理
```

### 本文约束的范围

- 记忆琥珀的定位与边界
- 物理级监听 vs 行为级约束的选择逻辑
- 内容哈希去重的设计依据
- 清理策略的三段式原则
- 与派生镜像机制、成就系统、铁律的互动边界

### 本文不涵盖

- `amber-backup.sh` 的安装步骤和内部实现（那是操作手册的职责）
- 每次改完 Skill 后的备份操作（那是机制自动触发的，不需要人记）
- 白名单的具体文件列表（那是 `amber-whitelist.txt` 的职责，会随系统演进）

## 二、为什么需要记忆琥珀

任何由 AI 持续修改的文件系统都面临一个根本问题：**破坏性操作不可逆**。

2026-04-11 到 2026-04-13 期间，QClaw 连续犯下日记操作错误——找不到原文件就新建、写错路径、覆盖已有灵感闪现、把晨间灵感闪现覆盖掉。每次错误后都无法回滚到修改前的状态，因为根本没留底。

这不是 AI 不够聪明的问题——是**机制缺位**的问题。任何依赖"AI 记得先备份"的方案，本质都是在靠意志力抵抗熵增。意志力会波动，机制不会。

> **核心判断**：备份不应该是一个"步骤"，而应该是一个"物理事实"——文件被改，就有备份存在，无论改的人记不记得。

## 三、设计溯源：四路权威理论

### 3.1 3-2-1 备份原则（Veeam, 行业标准）

**核心主张**：数据安全需要至少 3 份副本、2 种不同介质、1 份离线存储。

| 3-2-1 原则 | 记忆琥珀映射 | 说明 |
|:----------|:------------|:-----|
| **至少 3 份副本** | 原文件 + 记忆琥珀备份 + Time Machine（系统级） | 记忆琥珀是第二份，不是唯一备份 |
| **2 种不同介质** | 本地磁盘（记忆琥珀）+ 系统级备份（Time Machine） | 不依赖单一介质 |
| **1 份离线** | 记忆琥珀在同盘，Time Machine 在外置盘 | 满足离线要求 |

**关键差异**：3-2-1 是灾备原则，记忆琥珀不是灾备——它是**版本快照**。灾备解决"硬盘坏了怎么办"，版本快照解决"改崩了怎么回滚"。两者互补，不替代。

---

### 3.2 SSOT 原则（Single Source of Truth）

**核心主张**：每个数据只在一个地方是权威的，其他地方是派生投影。

| SSOT 原则 | 记忆琥珀映射 | 说明 |
|:----------|:------------|:-----|
| **权威源唯一** | 原文件是权威源，备份是快照 | 备份不是第二个权威源，是时间维度的投影 |
| **派生不可反向写入** | 备份文件永远只读 | ✅DO 从备份复制回原文件（回滚），⛔DO NOT 直接编辑备份文件 |
| **版本号唯一性** | 时间戳 + 内容哈希 = 全局唯一版本号 | 不依赖文件内字段，防止字段被改后版本号失真 |

**与派生镜像机制的关系**：派生镜像管**空间维度**的一致性（README 与 SKILL.md 同步），记忆琥珀管**时间维度**的一致性（今天的版本与昨天的版本可追溯）。两者共享 SSOT 原则，但作用维度正交。

---

### 3.3 Content-Addressable Storage（CAS，内容寻址存储）

**核心主张**：用内容的哈希值作为唯一标识，内容相同则标识相同。

| CAS 原则 | 记忆琥珀映射 | 说明 |
|:---------|:------------|:-----|
| **内容即身份** | 文件名包含 SHA-256 前 6 位 | 改了一个字，哈希就变，就是新版本 |
| **去重** | 内容未变 → 哈希相同 → 跳过备份 | 防止 touch 等无关操作触发无效备份 |
| **完整性验证** | 回滚时可重新计算哈希验证 | 确认备份没被篡改 |

**关键设计选择**：用前 6 位（1600 万种可能）而非完整哈希——同一文件不太可能哈希前 6 位冲突，文件名更短可读。这是工程权衡，不是理论妥协。

---

### 3.4 熵增定律与机制代替意志力（热力学第二定律 · 信息论视角）

**核心主张**：任何系统如果不持续输入能量（维护），就会自发趋向无序。

| 熵增原理 | 记忆琥珀映射 | 说明 |
|:---------|:------------|:-----|
| **系统自发无序** | 文件越改越多，版本越来越乱 | 不加机制 = 熵增必然发生 |
| **维护需要持续能量** | 靠人记得备份 = 消耗意志力 | 意志力是有限资源，会耗尽 |
| **机制代替意志力** | fswatch 物理监听 = 不消耗意志力 | 文件被改就备份，与人是否记得无关 |

**与派生镜像机制的共鸣**：派生镜像 §六 同样提出"机制代替意志力"——把同步从"人跑命令"改为"AI 自动跑"。记忆琥珀走得更远——连"AI 记得跑"都不依赖，直接用操作系统级的文件监听（fswatch + launchd），从物理层兜底。

> **递进关系**：
> - 派生镜像：AI 行为规则触发同步（执规-008）——依赖 AI 自觉
> - 记忆琥珀 v1.0：fswatch 物理监听触发备份——不依赖 AI 自觉
>
> 记忆琥珀是"机制代替意志力"的终极形态——把可靠性交给物理法则。

---

## 四、宪法级原则

> 以下原则是记忆琥珀的宪法底线。代码实现如果违反了这些原则，是代码错了，不是原则错了。

### §4.1 物理级监听，不依赖 AI 自觉

记忆琥珀**✅DO** 使用操作系统级文件监听触发备份（macOS: fswatch + launchd；Windows: FileSystemWatcher + Task Scheduler）。
记忆琥珀**⛔DO NOT** 依赖 AI 记得"改完文件后跑备份脚本"——原因是 AI 的行为规则会被上下文压缩、会被跳过、会被遗忘，物理监听不会。

```
✅ 允许：文件变化 → OS 级监听触发 → debounce 3秒 → 自动备份
✅ 允许：macOS 用 fswatch，Windows 用 FileSystemWatcher——哲学等价，实现各自原生
❌ 禁止：AI 在 SKILL.md 里写"改完文件后记得跑 amber-backup"
❌ 禁止：依赖 AI 的执规-X 来触发备份
```

**理论依据**：熵增定律 §3.4——意志力是有限资源，物理机制不是。

**例外**：手动触发备份（`bash amber-backup.sh` / `pwsh -File amber-backup.ps1`）仍然允许——作为灾备演练和主动快照手段，但不是日常依赖路径。

---

### §4.2 内容哈希去重，跳过未变文件

记忆琥珀**✅DO** 在备份前计算源文件 SHA-256，与最新备份的哈希对比。
记忆琥珀**⛔DO NOT** 在内容未变时创建新备份——原因是 touch、chmod、文件系统元数据变化都会触发 fswatch，但文件内容没变，盲目备份会产生大量无效副本。

```
✅ 允许：哈希不同 → 创建新备份
✅ 允许：哈希相同 → 跳过，日志记录"跳过-内容未变"
❌ 禁止：不对比哈希直接备份
```

**理论依据**：CAS §3.3——内容即身份，内容未变 = 身份未变 = 不需要新版本。

---

### §4.3 版本号 = 时间戳 + 内容哈希前 6 位

记忆琥珀**✅DO** 使用 `{父目录}_{文件名}_{YYYYMMDD-HHMMSS}_{哈希前6位}.bak` 作为备份文件名。
记忆琥珀**⛔DO NOT** 使用文件内字段（如 version、date）作为版本号——原因是文件内字段可能被改、可能缺失、可能格式不统一，文件名是物理事实不可篡改。

```
✅ 允许：workspace_SOUL_20260715-043450_227202.bak
❌ 禁止：SOUL_v1.0.bak（依赖文件内 version 字段）
❌ 禁止：SOUL_最新.bak（不可追溯，会覆盖）
```

**设计依据**：SSOT §3.2——版本号唯一性由物理事实（时间 + 内容）保证，不由文件内声明保证。

**为什么用父目录名 + 文件名**：不同目录下可能有同名文件（如 WorkBuddy 和 QClaw 都有 SOUL.md），父目录名消歧。

---

### §4.4 清理策略三段式

记忆琥珀**✅DO** 遵循三段式清理策略：
1. **同日只留 1 份**——同一文件同一天多次备份，只保留最新的
2. **7 天保留**——超过 7 天的非 major 备份自动删除
3. **major 永久**——文件名含 `_major_` 的备份永不删除

记忆琥珀**⛔DO NOT** 删除今天的备份——原因是刚创建的备份可能正在被回滚操作使用，删除会造成数据丢失。清理只处理 1 天前的备份。

```
✅ 允许：3 天前的日常备份 → 删除（已过保留期）
✅ 允许：同日第二次备份 → 删除上一次（只留最新）
✅ 允许：major 备份 → 永久保留
❌ 禁止：删除今天的任何备份
❌ 禁止：删除 major 备份（即使超过 7 天）
```

**设计依据**：

| 策略 | 第一性原理 | 解决的问题 |
|:-----|:---------|:----------|
| 同日只留 1 份 | 一天内多次修改的中间版本无回滚价值——只需回到"今天开始前的状态" | 防止同日 10 次修改产生 10 个备份 |
| 7 天保留 | 回滚需求的时间窗口通常 ≤ 7 天——超过 7 天的版本基本不会被回滚 | 控制磁盘占用 |
| major 永久 | 大版本升级前的手动快照具有历史归档价值 | 保留关键里程碑 |

---

### §4.5 幂等性

记忆琥珀**✅DO** 保证连续运行多次结果相同——内容未变时跳过，内容变化时备份。
记忆琥珀**⛔DO NOT** 产生"同一次修改触发多次备份"的情况——debounce 3 秒机制确保连续修改只触发一次备份。

```
✅ 允许：文件改了 1 次 → 备份 1 次
✅ 允许：文件改了 10 次（3 秒内）→ 备份 1 次（debounce 合并）
✅ 允许：文件没改 → 跳过
❌ 禁止：同一次修改触发 2 次备份
```

**理论依据**：与派生镜像原则 4（幂等）同源——连跑两次结果一致，才是可信赖的机制。

---

### §4.6 白名单制，非全量监听

记忆琥珀**✅DO** 只监听白名单中的文件——身份根、核心文件、Skill 的 SKILL.md、成就脚本。
记忆琥珀**⛔DO NOT** 监听整个个人 AI 档案目录——原因是日志、临时文件、缓存等高频变化文件无回滚价值，全量监听会产生备份风暴。

```
✅ 允许：SOUL.md 改了 → 备份
✅ 允许：SKILL.md 改了 → 备份
❌ 禁止：每日日志改了 → 备份（日志是追加型，无回滚价值）
❌ 禁止：缓存文件改了 → 备份（可重建，无归档价值）
```

**白名单的入选标准**：

| 标准 | 说明 |
|:-----|:-----|
| **不可重建** | 文件丢了无法从其他地方恢复 |
| **高价值** | 文件内容代表系统状态或个人认知 |
| **低频修改** | 修改频率 < 每日 1 次（高频修改的文件不适合版本快照） |

---

### §4.7 哨兵自愈合，杜绝静默死锁

记忆琥珀 **✅DO** 让守护在启动时主动清空自身的 debounce 锁（如 `rm -f "$LOCK_FILE"`），确保进程即便在"锁持有期"被重启，新进程也能立即恢复监听、重新触发备份。

记忆琥珀 **⛔DO NOT** 把"守护进程在跑"误判为"备份机制在工作"——fswatch 进程可能存活，却因上一次运行遗留的孤儿锁而**永久跳过所有事件**（静默死锁）。这种"进程在、机制死"的状态比进程崩溃更隐蔽：崩溃会被 launchd KeepAlive 拉起，死锁却不会，且 `launchctl list` 仍显示 running，极具迷惑性。

```
✅ 允许：守护启动即清锁 → 重启后自动恢复监听
✅ 允许：诊断"不触发"时先查锁文件 + amber.log 最后备份时间戳，再判断配置
❌ 禁止：用"launchctl list 显示 running"当作"备份在跑"的证据
❌ 禁止：用后台子 shell 释放 debounce 锁却不在启动时兜底（进程退出即失效）
```

**理论依据**：§4.1 递进信任模型 Level 3 假设 launchd KeepAlive 能兜底可靠性——但 KeepAlive 只保证"进程存活"，不保证"进程在干活"。自愈合锁把可靠性从"进程存活"提升到"机制有效"。这也是 §4.5 幂等性（debounce 3 秒合并连续修改）的实现底线：debounce 的锁必须由启动兜底，否则合并机制本身会成为死锁源。

---

### §4.8 修盘上 ≠ 修运行——守护改动必须手动 reload

对记忆琥珀 engine 脚本（`amber-fswatch-wrapper.sh` / `amber-backup.sh` / `amber-whitelist.txt`）的任何修改落地到磁盘后，**不会自动被正在运行的守护进程加载**。launchd 在 load 时读一次脚本副本，其 KeepAlive 重启的也是"内存里的旧副本"，不是盘上的新文件。

记忆琥珀 ✅DO 修改 engine 脚本后，在真实终端执行一次 reload：
```bash
launchctl unload ~/Library/LaunchAgents/com.memoryamber.backup.plist
launchctl load ~/Library/LaunchAgents/com.memoryamber.backup.plist
```

记忆琥珀 ⛔DO NOT 在 `pgrep` 看到 `amber-fswatch-wrapper.sh` 进程后，假设"盘上新已生效"——必须验证实际 `fswatch` 进程的命令行参数是否已反映改动。验证方法：重载后跑 `pgrep -fl fswatch` 看完整命令行。

记忆琥珀 ⛔DO NOT 依赖 WorkBuddy/Qclaw 等 AI 工具的 Bash 沙箱做 reload——沙箱域 `launchctl load` 不传播到真实登录会话（§3.1 操作环境约束），必须由用户在自己的真实终端执行。

**历史教训**（2026-07-16）：7/15 修复 `amber-fswatch-wrapper.sh` 后删掉了 `--event Updated/Created/MovedTo` 窄过滤，但未 reload 守护。次日（7/16）真机 `pgrep -fl fswatch` 发现运行中的 fswatch 命令行**仍带** `--event` 窄过滤——盘上新、内存旧，修了等于没修。跑完 unload+load 后才生效。

---

### §4.9 心跳只读检测——绕沙箱进程隔离

AI agent（WorkBuddy/Qclaw 等）的 Bash 运行在隔离的 launchd 沙箱域——其 `launchctl list`、`pgrep` 等进程查询无法触及真实登录会话守护。直接查进程 = 假阴性。心跳检测绕过此限制：**守护主动写盘、 Skill 被动读盘——不碰进程，只读文件**。

记忆琥珀 ✅DO 在守护 wrapper 中维持每 30 秒一次的心跳时间戳写入（`date +%s > /tmp/guard-heartbeat-memoryamber.txt`），供唤醒记忆系统 Skill（轻量/全量模式）在每次触发时读取并判定守护健康：距今 <90s = 活着 ✅，90-180s = 抖动 🟡，>180s 或文件缺失 = 守护可能已死 ⚠️。

记忆琥珀 ⛔DO NOT 依赖 AI agent 的 Bash `launchctl list` 或 `pgrep` 来验证守护存活——沙箱域的进程查询不可靠，负结果不能作为守护已死的证据。

记忆琥珀 ⛔DO NOT 在心跳文件缺失时立即判定守护死了——首次部署或守护刚重启时心跳尚未产生，仅标记 ⚠️ 提醒核查。

**理论依据**：§3.4 机制代替意志力——心跳检测是"守护自证活着"的机制层方案，把"人记得查"替换为"Skill 自动读"。这也是 §4.1 递进信任模型 Level 4 的实践：Level 3 信任 launchd KeepAlive（进程存活），Level 4 信任心跳时间戳（进程在干活）。心跳把可靠性从"进程存活"推进到"进程在持续产出可验证证据"。

**历史教训**（2026-07-16）：曾试图把守护健康检查放在每日伙伴 step 8，被用户第一性原理追问否决——每日伙伴管"一天的数据一致性"，守护管"基础设施健康"，语义不匹配。正确归属是唤醒记忆系统（"记忆系统全貌体检"），且必须绕开沙箱进程查询（否则必假阴性），故推导出心跳文件方案。

---

### §4.10 常态审计类机制须脚本触发，不靠 prose（反哺自 2026-07-21）

常态审计类机制（双盲 review / 季度巡检 / 定期自检）✅DO 用脚本触发——文件计数、日期检测、状态扫描等物理信号驱动。⛔DO NOT 仅靠 prose 声明"建议定期执行"——prose 声明没有物理触发器 = 死规则，等于没写。这是本哲学"机制代替意志力"（§3.4）在审计维度的延伸：连"AI 记得审计"都不依赖，用脚本兜底。实战：双盲触发从 prose 声明改为 check_selfimprove_gate.py 检测后才真正生效。

`[来源: 成长箱反哺 | 日期: 2026-07-21 | 反哺标题: 常态审计类机制须脚本触发不靠prose]`

## 五、与其他系统机制的互动

### 5.1 与派生镜像机制的分工

| 维度 | 派生镜像机制 | 记忆琥珀 |
|:-----|:------------|:--------|
| 管什么 | 空间维度一致性（README ↔ SKILL.md） | 时间维度可追溯（今天 ↔ 昨天） |
| 触发方式 | AI 行为规则（执规-008） | 操作系统物理监听（fswatch） |
| 依赖 AI 自觉 | 是——AI 记得跑 sync_guard | 否——物理监听触发 |
| 失败模式 | AI 跳过执规 → 漂移 | fswatch 进程挂掉 → 无备份 |
| 静默死锁 | （不适用） | 孤儿 debounce 锁 → 进程在跑但全事件跳过，无备份（比崩溃更隐蔽）；守护启动自清锁可破（§4.7） |
| 互补关系 | 派生镜像保证"当前一致" | 记忆琥珀保证"历史可回滚" |

**关键设计**：两者独立运作，不相互依赖。派生镜像挂了不影响记忆琥珀备份，记忆琥珀挂了不影响派生镜像同步。这是**防御深度**——不把鸡蛋放在一个篮子里。

---

### 5.2 与成就系统的互动

| 互动点 | 说明 |
|:-------|:-----|
| **成就脚本在白名单内** | `achievement_tracker.py` 和 `achievement_data.json` 被备份 |
| **备份不触发成就** | 备份行为本身不产生番茄、不写日记成就——备份是基础设施，不是成就行为 |
| **成就数据可回滚** | 如果 `achievement_data.json` 被误改，可以从记忆琥珀回滚 |

**关键边界**：成就系统是行为反馈层，记忆琥珀是时间胶囊层。成就系统不感知记忆琥珀的存在——它不知道自己的数据被备份了。这种**单向透明**是正确的设计——消费者不需要知道备份机制的存在。

---

### 5.3 与铁律（修改前备份原则）的互动

指令编写规范 §6.6 规定："⛔DO NOT 修改任何文件前不先备份到记忆琥珀"。

**v1.0 哲学的修正**：这条铁律在记忆琥珀 v1.0 之前是"靠 AI 自觉"的检查端防错。记忆琥珀 v1.0 之后，fswatch 物理监听让备份**在设计端就发生**——AI 改不改文件，备份都会触发。

| 维度 | 旧机制（铁律 §6.6） | 新机制（记忆琥珀 v1.0） |
|:-----|:-------------------|:---------------------|
| 防错类型 | 检查端（AI 记得跑） | 设计端（物理监听自动跑） |
| 可靠性 | 中——可被跳过 | 高——物理法则 |
| 铁律是否废止 | 否——仍然有效 | 是——铁律成为**第二道防线** |

**结论**：铁律不废止，但从"第一道防线"降级为"第二道防线"。fswatch 是第一道防线，铁律是兜底——如果 fswatch 挂了，AI 仍然应该遵守铁律手动备份。

---

### 5.4 与五层记忆架构的互动

记忆琥珀不属于五层中的任何一层——它是**跨层基础设施**。

| 层级 | 是否备份 | 原因 |
|:-----|:-------|:-----|
| L1 核心层（CORE.md） | ✅ | 价值观不可丢失 |
| L2 认知层（规则文件） | ✅ | 决策偏好不可丢失 |
| L3 行为层（MEMORY.md） | ✅ | 行为模式记录不可丢失 |
| L4 情境层（动态状态快照） | ✅ | 近期目标进展不可丢失 |
| L5 状态层（每日日志） | ❌ | 日志是追加型，无回滚价值 |
| L6 潜意识层（SHADOW.md） | ✅ | 潜意识观察不可丢失 |

**设计选择**：L5 状态层不备份——日志的价值在于"记录发生了什么"，而不是"可回滚到之前的状态"。回滚日志没有意义，因为时间不可逆。

## 六、为什么它是"哲学"

记忆琥珀的核心理念是**重新划定人机责任的边界**：

- **人的工作**：改文件、升级系统、调整规则。输入端的正确性由人负责。
- **机器的工作**：监听、留底、清理、回滚。历史可追溯性由物理机制兜底。

这不是技术优化——这是**选你相信哪边的记忆和意志力**。

> **递进信任模型**：
> - Level 0：信任人——人记得备份（已证明不可靠）
> - Level 1：信任 AI——AI 遵守铁律自动备份（可被跳过）
> - Level 2：信任机制——fswatch 物理监听（不依赖任何一方自觉）
> - Level 3：信任物理法则——launchd KeepAlive 确保监听不挂（即使挂了也会重启）
>
> 记忆琥珀 v1.0 运行在 Level 2-3。

**与派生镜像 §六 的对比**：派生镜像停在 Level 1（信任 AI 按执规跑同步），记忆琥珀推进到 Level 2-3（信任物理监听）。这不是说派生镜像错了——而是两个机制的职责边界不同，派生镜像需要 AI 判断"何时同步"，记忆琥珀不需要判断，文件改了就备份。

## 七、Alternatives Considered

| 设计决策 | 选择 | 替代方案 | 为什么不选替代 |
|:---------|:-----|:---------|:--------------|
| 监听方式 | OS 原生文件监听 | AI 铁律触发（SKILL.md 写"改完跑备份"） | 铁律可被跳过、可被上下文压缩丢失；物理监听不会 |
| 跨平台实现 | macOS: fswatch + launchd / Windows: FileSystemWatcher + Task Scheduler | watchexec 跨平台单一工具 | 原生工具无依赖、用户体验开箱即用；watchexec 需额外安装 |
| 备份触发 | 文件内容变化 | 文件 mtime 变化 | mtime 会被 touch/chmod 误触发，不代表内容真的变了 |
| 去重方式 | SHA-256 前 6 位 | 完整 SHA-256 | 6 位 = 1600 万种可能，同文件冲突概率极低；文件名更短可读 |
| 版本号 | 时间戳 + 哈希 | 文件内 version 字段 | 字段可能被改、缺失、格式不统一；文件名是物理事实 |
| 清理依据 | 文件名中的日期 | 文件 mtime | `cp -p` 保留原 mtime，导致刚备份的老文件被误删 |
| 监听范围 | 白名单制 | 全量监听个人 AI 档案 | 日志/缓存/临时文件高频变化无回滚价值，全量监听产生备份风暴 |
| 同日策略 | 只留最新 1 份 | 保留全部 | 一天内 10 次修改的中间版本无回滚价值，只需"今天开始前的状态" |
| 保留期限 | 7 天 | 30 天 / 90 天 | 回滚需求的时间窗口通常 ≤ 7 天；更长保留占用磁盘且基本不会用到 |
| 服务管理 | launchd（macOS 原生） | cron / supervisor | launchd 原生支持 KeepAlive 崩溃重启，不需要额外装服务 |
| 运行平台 | macOS only | 跨平台 | 用户的主力机是 Mac，跨平台是发布包阶段的事，先解决当前问题 |

## 十、自救指南 · 安装与运行故障排查

> 以下是安装失败或"感觉没在工作"时的诊断流程。记忆琥珀的设计原则是"机制代替意志力"——但机制也需要人能看懂它为什么没跑起来。

### 10.1 架构速览：四组件协作链

```
amber-whitelist.txt          →  定义"守护哪些文件"（纯文本清单，一行一个路径）
        ↓
amber-fswatch-wrapper.sh     →  用 fswatch 物理监听白名单目录的文件变化
        ↓
amber-backup.sh              →  变化被检测到 → 3 秒 debounce → 计算哈希 → 与最新备份对比 → 内容变了才备份
        ↓
launchd / Task Scheduler     →  确保上述监听进程永不挂（KeepAlive / 注册任务重启）
```

**关键认知**：四个组件独立协作。任一组件断了，整条链就断了。排查时从最后端（心跳/备份产物）往前倒推。

### 10.2 macOS 故障排查

#### 1. 守护在跑吗？

读取心跳文件——守护每 30 秒写一次时间戳：

```bash
cat /tmp/guard-heartbeat-memoryamber.txt
```

用当前时间减去文件内时间戳：<90s = 正常 ✅ / 90-180s = 抖动 🟡 / >180s 或无文件 = 守护可能已死 ⚠️。

⛔ 不要用 `launchctl list | grep amber` 判断——沙箱域里可能查不到，但守护仍在真实会话运行。

#### 2. 监听在生效吗？

最快的验证方法：改一个白名单文件，10 秒内看是否生成 `.bak`。

```bash
echo "# test" >> ~/个人AI档案/核心层/CORE.md          # 触发一次修改
sleep 10
ls -lt ~/个人AI档案/记忆琥珀/ | head -5                # 看有没有新 .bak
```

有新 `.bak` = 全链路通。没有 → 继续往下排查。

#### 3. 改了脚本但未生效？

修改 `amber-fswatch-wrapper.sh` / `amber-backup.sh` 后，**必须手动 reload 守护**（§4.8）：

```bash
launchctl unload ~/Library/LaunchAgents/com.memoryamber.backup.plist
launchctl load ~/Library/LaunchAgents/com.memoryamber.backup.plist
```

> 不改脚本则无需 reload——只改白名单文件不需要重启守护。

#### 4. 安装失败？

检查依赖：

```bash
which fswatch     # 监听工具，未安装则 brew install fswatch
which python3     # 钩子脚本依赖，macOS 通常自带
```

#### 5. 看日志

所有备份事件记在：

```
~/个人AI档案/记忆琥珀/engine/logs/amber.log
```

搜 `已备份`、`跳过`、`警告`、`错误` 快速定位问题。

### 10.3 Windows 故障排查

#### 1. 任务在跑吗？

```powershell
Get-ScheduledTask -TaskName "MemoryAmberWatch" | Select State
```

期望输出 `Running`。若为 `Ready` 或 `Disabled`，手动启动：

```powershell
Start-ScheduledTask -TaskName "MemoryAmberWatch"
```

#### 2. Python 命令对吗？

Windows 上 Python 命令通常是 `python`，**不是** `python3`。

```powershell
python --version          # 应输出 Python 版本号
```

若 `python` 不可用，检查 Python 是否安装并加入 PATH。钩子脚本如果注册时用了 `python3`，在 Windows 上会静默失败——需手动改 settings.json 为 `python`。

#### 3. PowerShell 执行策略

首次运行 `.ps1` 脚本可能被拦截：

```powershell
Get-ExecutionPolicy         # 若为 Restricted，需放宽
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
```

#### 4. 路径占位符替换了吗？

PS1 脚本内含 `[记忆共享中心]` 占位符——安装时 step6.5b2 自动替换为实际路径。若手动拷贝脚本跳过了此步，需手动替换或重跑安装。

### 10.4 通用排查

#### 白名单路径写对了吗？

- ✅ 必须是**绝对路径**
- ✅ 目录条目（如 `~/个人AI档案/记忆规则/`）需要 `amber-backup.sh` **v1.2.1 及以上**才支持目录级递归备份
- ❌ 相对路径 `./SOUL.md` 不会生效
- ❌ 含空格路径未用引号包裹

#### 最常用的验证命令

**macOS**：
```bash
bash ~/个人AI档案/记忆琥珀/engine/amber-backup.sh   # 手动跑一次，看退出码和日志
tail -20 ~/个人AI档案/记忆琥珀/engine/logs/amber.log # 看最近日志
```

**Windows**：
```powershell
pwsh -File %USERPROFILE%\个人AI档案\记忆琥珀\engine\amber-backup.ps1
Get-Content %USERPROFILE%\个人AI档案\记忆琥珀\engine\logs\amber.log -Tail 20
```

#### 还是不行？

1. 先手动跑一次备份脚本，确认脚本本身没问题
2. 再检查监听进程/任务状态
3. 最后查 launchd / Task Scheduler 注册

> **记住**：四组件独立协作。先逐环节手动验证，不要跳步猜原因。

> **v1.1 变更**（2026-07-15）：跨平台扩展。新增 Windows 实现（FileSystemWatcher + Task Scheduler + PowerShell），设计哲学 §4.1 改为操作系统无关表述。核心原则不变——"物理级监听、不依赖 AI 自觉"——只是实现选择多了一个平台。验证：macOS 上 pwsh 跑 PowerShell 版备份脚本 + 监听脚本均通过（24 文件全处理、哈希去重正确、debounce 3秒生效）。

> **v1.2 变更**（2026-07-15）：补全失效模式与自愈合原则。① 新增 §4.7「哨兵自愈合，杜绝静默死锁」——明确"进程在跑≠机制在工作"，守护须启动自清 debounce 锁，破孤儿锁静默死锁；② §5.1 失效模式表补"静默死锁"行。来源：2026-07-15 记忆琥珀哨兵端到端排障（两层 bug：fswatch `--event` 窄过滤漏 shell `>` 改写事件 + 孤儿 debounce 锁永久死锁），实测修复后 `_amber_selftest_*.bak` 落盘、触发链复活闭环。
>
> **v1.3 变更**（2026-07-16）：新增 §4.8「修盘上 ≠ 修运行——守护改动必须手动 reload」。明确：对 amber engine 脚本的修改不会自动生效，必须在真实终端执行 unload+load。来源：2026-07-16 真机 pgrep 发现 7/15 修复从磁盘落地但未被守护加载，运行中的 fswatch 仍带 --event 窄过滤。补充假设验真：launchd KeepAlive 重启的是"内存旧副本"而非"盘上新文件"。
