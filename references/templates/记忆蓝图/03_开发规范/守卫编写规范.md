# 守卫编写规范

> **定位**：管辖所有守卫/审计/校验类脚本"职责怎么划、真相放哪、协作怎么定"的治理规范。与三大开发规范并列——改守卫前必读本规范（同"改Skill前必读三规范"纪律）。
> **诞生背景**：2026-07-26一日三案（sync_guard假绿灯 / reverse-guard 76次灌毒 / SWT双文案死循环）——同病根：守卫间无共同真相源，各拿各的尺子。经三明智L2（第一性原理+批判验证）评估定稿。
> **消费方**：①AI（新建/修改守卫时读§二§三）②sync_guard.py（自动扫描§四注册表的机械可查项）

---

## 一、目的与适用范围

**目的**：让"两个组件对同一对象持不同真相定义"这种结构性打架物理上难以发生。

**适用**：所有守卫类脚本——检测/校验/比对/自动恢复/门禁类（如 *_guard / *_check / verify_* / *-sync 的校验部分）。
**不适用**：纯功能脚本（生成器/抽取器的主逻辑）；Skill内部流程锁（归Skill架构规范Poka-Yoke节管）。

### 三·九·3 保真度 + `rc=0` 零输出（2026-10-03 反哺·「验的不是运行的那份」+「批量替换自伤」双案）

**病根① 验的不是运行的那份**：回归器/校验脚本的被测路径若**硬编码**某目录，而运行时真源指向另一处——
两份内容可完全不同，回归器却报「全过」。实测：同一套用例指向旧件判 `D3`、指向真跑件判 `D2`，**两次都报全绿**。

✅DO 验证器的被测路径必须解析自**运行时真源**（本端约定以 `runtime_paths` 之类的配置为准），⛔ 不硬编码脚本目录。
✅DO **保真三判据**：① **路径保真**（解析自真源）② **内容保真**（实测件哈希 == 运行目录同名件）③ **断言覆盖**（判据须有真阴性断言）。
⛔「全绿但无该断言」= **未覆盖**，≠ 通过。
⚠️ ①②的边界：两者本就是同一文件且**同步漂移**时无从区分。✅ 凡「同一件是否被验证」的判据，**必须配一条运行时独立留痕**（如台账记运行件自身哈希）⇒ 三方对账。⛔ **不得用「对文件取哈希」冒充「对运行时留痕」**——两者会一起变。

**病根② `rc=0` 零输出**：批量把绝对路径改成 `~/…` 时漏了 `os.path.expanduser(...)` 包裹 ⇒ 裸字符串永不展开 ⇒ 读取失败 ⇒ **输出全空而 `rc=0`**。
⛔ 它比报错更贵：报错会停在脸上，**零输出只会让下游安静地错**。

✅DO 路径字面量改 `~/` 时**逐处核对 `expanduser` 包裹层**；⛔ 不做"看起来等价"的批量替换——正确性来自核对，不来自替换本身。
✅DO 改批量路径/常量前先立**自伤负控**：跑一次全量回归，若出现「`rc` 未变但输出变空」= 包裹层被破坏。

**病根③ 较新 ≠ 较全**：两处并存同名件时，一次「归位同步」可能把**旧件**复制进真相源侧，造成**降级副本**（真相源侧独有函数=0，另一侧多出若干）；其中还可能被机械替换改了路径并**丢失真逻辑**。

✅DO 判副本真伪用**函数集合差集**，⛔ 不用 mtime/字节数——唯有"对方独有的功能节点"回答"谁更全"。
✅DO 已确立的运行时真源是**唯一真相源**，另一处定位只读；⛔ **双向同步不构成任何保护，它同时是分叉的来源**。
⚠️ 守卫豁免须**显式且窄**：脱敏/替换类工具的 `~/` 字面量（写进被处理文本·加 `expanduser` 反破坏语义）、隐私闸门自身的检测正则（那是它的**检测目标**）。⛔ 豁免不得写成"整文件跳过"。

### 三·九·2 同一产物的呈现点唯一性（2026-10-02 反哺·本端 TSL 树三连重复/缺树案）

**病根（实测·同一回合连踩三次）**：一个产物（TSL 树）**同时挂在两条呈现路径**——
`tsl_echo_hook`（UPS/pre_llm_call）注入**用户消息** ＋ 契约要求 AI 逐行 relay 进**回复** ⇒ 同一棵树必现两次。
修的过程中又两次跑偏：AI 手动跑产树脚本（覆盖树槽⇒新 stamp⇒下轮再灌⇒刷屏）；改口"不贴了"⇒ 缺树。

✅DO **同一产物在用户视野里只能有一个呈现点**。若产物已由钩子注入用户消息，⛔ 不再要求 AI 在回复里复制全文；
若契约要求 AI 呈现（如 TSL 树的逐行 relay），⛔ 该端钩子注入通道必须停用。**两条路只能留一条。**

✅DO **区分"防重复"与"防多次呈现"是两种机制**：
- **幂等/stamp 去重**（`.consumed`、session stamp）防的是「**同一份**重复投递」；
- **呈现点唯一性**防的是「**同一产物**经两条路各呈现一次」。
⛔ 不得用前者的绿灯推出后者成立——**实测 `.consumed` 一直绿，树仍每轮出现两次。**

✅DO **AI/调用方对"构造权"零持有时，呈现内容必须逐字**：
⛔ 不得摘要、⛔ 不得改写、⛔ **⛔ 不得只写一行指针代替全文**——「指针行」把呈现权交给调用方自选，与「手绘」同级违规。

⛔ **调用方不得自行重跑生产脚本**产出该产物——自跑会覆盖生产槽位、产出新版本号，使去重机制失效并制造版本漂移。

**端适配边界（守卫规范 §二·十四「接入不拥有」）**：呈现路径冲突是**端适配层**问题——
⛔ 不改共脚本本体、⛔ 不动他端（他端呈现路径不同·须按端取证）。
本条登记「什么样的呈现结构是错的」，**⛔ 不规定各端必须关哪一条**。

## 二、核心原则（两条腿·缺一不可）

### 原则1 · 真相所有权（定义权）

**每段真相（某对象该长什么样/某规则是什么）必须有且只有一个物理住所。守卫只能 import/读取真相，⛔DO NOT 在守卫代码里内联真相**——原因是内联=真相分叉=两定义并存=打架是数学必然（76次灌毒案：sync认为包=裁剪投影，guard认为包=原样投影，同一对象两定义，冲突每小时都在发生）。

| ✅DO | ⛔DO NOT |
|------|---------|
| 裁剪规则住 build_strips.py，sync/guard 都 import 它 | 每个脚本各写一份裁剪逻辑/占位文案 |
| 源路径读固化文件自声明的 source_path 字段 | 脚本里硬编码 fallback 路径（sync_guard假绿灯案根因） |
| 清空文案唯一住所=deident规则6 | 第二个模块再定义一遍清空文案（SWT双文案案根因） |

### 原则2 · 时序协议（协作权）

**多个组件共守/共写同一对象时，✅DO 显式声明协作协议（锁/防抖/单写者），并确认协议双端都真实接入**——原因是真相统一只治"定义打架"，治不了"时序打架"（SYNC_LOCK案：守卫留了排除锁的口子，但sync从不建锁，排除机制形同虚设）。

常用协议：文件锁（SYNC_LOCK）/ debounce / 单写者声明 / 有痕跳过（跳过必留痕，静默跳过=假绿灯）。

### 原则3 · 绿灯需要负例证据

**新守卫上线✅DO带至少1个负例用例（故意造错→验证守卫报警→恢复现场）**——原因是从没报过NOT OK的守卫，它的OK不可信（sync_guard报"0漂移"数周，实际漏抓2条真漂移）。

## 三、新守卫验收三问（改守卫前AI自查）

| # | 问 | 不过关的表现 |
|---|-----|------------|
| 1 | 它守的真相住在哪个文件/模块？ | 答不出唯一住所 / 真相内联在守卫代码里 |
| 2 | 有谁和它共守/共写同一对象？协作协议是什么？双端都接了吗？ | "应该没有吧"（没查注册表）/ 协议单端悬空 |
| 3 | 负例证据在哪？ | "逻辑上肯定能抓到"（没实测过） |
| 4 | 它锁得住什么？锁不住什么？ | 答不出锁不住项=误以为守卫全覆盖——C-14 实证：确定性守卫锁"格式/结构/存在性"，锁不住"内容深度/呈现形态/语义质量"（v3.13 旧形态全展示照样 exit 0 过守卫·2026-08-12） |

✅DO 四问全部过关后在§四注册表登记一行，登记完成才准上线——原因是不登记=下一个改守卫的AI查不到共守关系=验收三问的第2问对所有后来者失效。
✅DO 登记为**机器强制（enforced）**——sync_guard 自动扫描 §四 注册表，未登记守卫=脱离机器监管（08-10 实证：consistency_guard.py 重写后漏登，sync_guard 扫描零告警=盲区，08-11 反哺补登才纳入）。原因：advisory 登记不足以防脱离扫描，注册表须成为守卫上线的物理闸门。
⛔DO NOT 以"守卫很简单/只是临时的"为由跳过三问——原因是76次灌毒案的reverse-guard当初也"只是个兜底"，简单守卫与复杂守卫打起架来破坏力相同。

## 五、机器校验说明

- **扫描者**：sync_guard.py（运行时机=手动跑/loop安装包模式内）
- **扫什么**：§四表格逐行——真相源列的本地路径存在性（`~/`开头的路径展开后必须是真实文件/目录）；算法/字段类真相源（如SEAL_SALT）跳过路径校验
- **报什么**：路径失效→⚠️列入漂移报告（与固化引用漂移同格式）；表格结构损坏→⚠️"注册表不可解析"
- ⛔DO NOT 让脚本校验"职责划得对不对"——原因是职责合理性是语义判断，脚本硬测=假信号；语义层归AI验收三问+用户终审，脚本只守机械层（同skill_eval判级advisory边界，依据指令编写规范§6.6评测定位）

## 八、Hook 部署形态与脚本家族总览（v1.1.0 新增）

### 1. Hook 是什么

**Hook = 部署形态（挂 settings.json hooks.X 事件触发），不是脚本本质。** 同一脚本可以是守卫本质 + Hook 部署。判定脚本属性先问本质（守什么/算什么），再问部署（怎么被触发）——回答"它是 Hook 吗"时，准确说法是"它是 {本质}，以 Hook 形态部署"。

当前已挂 Hook（3 个，均 Stop 事件）：`route_unknown_unknown.py` / `audit_search_kb.py` / `route_audit.py`。

### 2. Hook 脚本三条纪律（从三个 Stop 脚本提炼的共性·新挂 Hook 必守）

| # | 纪律 | 原因 |
|:-:|------|------|
| 1 | **只记录不拦截**——任何情况 exit 0 放行，绝不阻断对话 | 钩子属于观测层，拦截=把对话质量押在脚本正确性上 |
| 2 | **失败放行**——解析异常/无输入/行损坏/未捕获异常→直接 exit 0 | 钩子失败不允许影响主流程（失败默认放行原则） |
| 3 | **保守判定**——宁可漏记不可误记 | 误记=审计噪音污染指标，比漏记更伤数据质量 |
| 4 | **输出形态须显式声明**——同一事件挂多条 Hook 时，全部走裸文本 stdout；⛔DO NOT 用 json envelope | **信封式合并律**：宿主对同事件多 Hook 的 `hookSpecificOutput`（json 信封）做**同key 覆盖**（后者赢），对 `stdout`（裸文本）做**拼接共存** ⇒ 同一事件挂多条时用信封＝排在前面的注入块被静默丢弃。实证（2026-10-07）：WorkBuddy 端 11 条 UserPromptSubmit 并存，童灵上岗块（排第 4）被后位信封覆盖，AI 收不到仪式块→"上岗回复不按模板"，而各脚本自测全绿 |

**第4 条的边界**：单 Hook 独占事件（如 SessionStart 只挂一条）时信封无竞争面；但**"当前只有一条"是状态不是保证**——⛔新增第二条 Hook 时必须同步核对形态。核查入口：`pkg_conflict_audit.py`（作者侧）/ 装包时 `deploy_script_center` 的冲突检测（端用户侧）。

### 2·补 同名覆盖律（2026-10-07 端用户实证·装包面）

**病根**：`install_scripts.py::deploy_script_center` 把三个源目录（`references/scripts`、`references/hooks`、`references/digital-twin/devtools`）**平铺复制到同一 `<脚本中心>/`**。同名文件**后复制者覆盖先复制者**，而遍历序 ≠ 内容新旧 ⇒ 端用户静默拿到滞后副本。

**实证**：`router.py` 端用户落地 161 行，而 `references/scripts/` 那份 329 行 ⇒ 路由引擎缺 `_self_names` 能力；全包 20 件命中，影响静默（不报错，只表现为"路由匹配不准"）。

**律条**：
1. ⛔DO NOT 让多份副本平铺进同一落点而不声明归属——**冲突即失败**，⛔ 不静默覆盖、⛔ 不自动挑边（挑边=猜；猜错=把新版丢掉·比报错更坏）
2. ✅DO 用**脱敏归一后**比对判冲突（路径形态差异不算冲突·脱敏本就不同形态）

### 5. 路由型守卫方法论（P2 双轨路由·2026-08-08）

**双轨**：硬路由（确定性规则·desc 触发词自动提取+NOT for 反过滤）兜确定场景，软路由（模型语义判断）兜语义边界——规则层加词只会增误报，语义缺口留给软路由。
**留痕**：route_reason 日志（每次命中/疑似漏判）→ 两账对账（路由"应该命中" vs 系统日志"实际做了"）→ 数据支持再开注入，不支持降级"软提示"。
**边界**：基线 88% 召回 / 11% 误报（纯子串匹配零优化），真实缺口全为语义边界类（triwich 语境限定/chrold 调X变体/meta 跨Skill竞争）。
