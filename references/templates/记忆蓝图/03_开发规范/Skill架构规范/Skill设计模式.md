## 1. Skill类型分类

> 合并旧版§八+§十 10.1（消除重复）+ 增强MUST机制列 + v5.15新增第6类"分析型"
> **重要**：6类分类仅用于Poka-Yoke机制选配矩阵，**不用于T5要求判定**。T5按攻击面5维度评估（见Skill架构规范.md §二附B）。

| 类型 | 特征 | 典型示例 | 设计重点 | MUST机制 |
|------|------|---------|---------|----------|
| **流程执行型** | 多步骤、强顺序依赖 | 唤醒记忆系统 | 产出物锁 + 熔断器 | 产出物锁+熔断器+思考检查点+完整性锁 |
| **模板编排型** | 选模板→填内容→校验→渲染→再校验→交付 | DashiAI PPT、Scriyore | 分段校验管道 + 模板默认文案残留检测 | 产出物锁+分段校验(≥2独立关卡)+模板占位符扫描+完整性锁 |
| **生成型** | 输入→处理→输出内容 | 报告生成器 | 模板约束 + 质量自检 | 产出物锁+完整性锁 |
| **查询型** | 检索→返回结果 | 知识检索 | 触发精准度 + 置信度标注 | 熔断器+完整性锁 |
| **转换型** | A格式→B格式 | PDF/Excel转换 | 格式验证 + 完整性校验 | 产出物锁+完整性锁 |
| **交互型** | 多轮对话式引导 | 每日伙伴、Shall We Talk | 状态追踪 + 节奏铁律 + 用户反馈 | 产出物锁+思考检查点+完整性锁+结论块分离 |
| **分析型** 🆕 | 输入问题→分析框架→结论 | triwich | 分析框架执行完即输出结论 | 产出物锁+思考检查点+熔断器+完整性锁+结论块分离 |

### 类型判定标准（v5.15新增）

**交互型 vs 分析型的边界**：
- 交互型：**禁止直接输出结论**，必须通过多轮追问让用户自己推（如meta-aletheia）
- 分析型：**可以直接给结论**，分析框架执行完就输出（如triwich）

**流程执行型 vs 分析型的边界**：
- 流程执行型：产出物是"执行结果"（日志/记录/文件）
- 分析型：产出物是"分析结论"（签名+结论块）

| Skill | 类型 | 归类依据 |
|---|---|---|
| daily-buddy | 流程执行型 | 有流程A/B/C，产出物是日记 |
| system-logger | 流程执行型 | 有写入/蒸馏两条路径，产出物是日志 |
| growth-box | 流程执行型 | 5个流程A-E，产出物是错误记录/蒸馏报告 |
| reading-assistant | 生成型 | 输入一本书→输出读书笔记 |
| awaken-memory-system | 查询型 | 只读记忆文件→输出情境概览 |
| shall-we-talk | 交互型 | 多轮深度对话，禁止直接给结论 |
| meta-aletheia | 交互型 | 苏格拉底追问，禁止直接输出分析结论 |
| triwich | 分析型 | L1/L2/L3分析框架，可以直接给结论 |

## 2. 设计模式目录

> 12种模式 + 何时用/何时不用 + 组合规则

| 模式 | 适用场景 | 核心机制 | 来源 | 何时用 | 何时不用 |
|------|---------|---------|------|--------|----------|
| Sequential Workflow | 多步骤流程 | 步骤产出物锁 | 已有 | 步骤间有强依赖 | 步骤可并行或无序 |
| Circuit Breaker | 任何外部调用 | 每步失败检测+降级 | Microsoft AgentFactory | 调用外部系统/API | 纯本地操作 |
| Progressive Disclosure | 内容丰富的Skill | 3级加载 | Anthropic | SKILL.md超500行（经验平衡点，详见标准规范§3） | 内容简单无需拆分 |
| Plan-and-Execute | 先规划后执行 | 规划步骤+执行步骤分离 | ReAct衍生 | 需求复杂需先规划 | 需求明确直接执行 |
| Reflection Loop | 质量保证 | 执行→自检→修正→再检 | AgentFactory | 输出质量要求高 | 简单任务无需自检 |
| Multi-Skill Coordination | 跨领域工作流 | Skill链式调用 | Anthropic | 需多Skill协作 | 单Skill可完成 |
| Verifier/Guardrail | 高风险操作 | 操作前验证+权限检查 | AgentFactory | 涉及不可逆操作 | 低风险可逆操作 |
| Description Engineering | 任何Skill | 触发精准优化 | Anthropic | 所有Skill | — |
| A/B Evaluation | 迭代优化 | 盲比测试 | Anthropic | 迭代优化阶段 | 初版Draft阶段 |
| Dual-Agent Review | 双Agent盲审 | Agent A执行 + Agent B独立审查 | Anthropic Multi-Agent | 深度分析/高可靠需求 | 简单任务 |
| **Modular Design** | 复杂多模块Skill | 模块间松耦合+输出文件衔接 | 旧版skill-design-guide.md | 任务可自然拆分为子任务 | 单步骤简单任务 |
| **Output Cache** | 调试/迭代阶段 | 每模块输出存文件→跳过已通过模块 | 同上 | 反复调试同一Skill | 一次性执行不回跑 |
| **Staged Validation** | 模板编排/复杂产出型Skill | 分独立关卡逐项校验（每关只查一件事） | DashiAI PPT | 产出物质量要求高、需多维度验证 | 简单任务单校验足够 |
| **Placeholder Scan** | 模板填充/文案生成型Skill | 交付前扫描产出物中中性占位符残留 | 同上 | 模板有默认文案需替换的场景 | 无默认模板文案的Skill |

### 组合规则

| 组合 | 效果 | 典型应用 |
|:-----|:-----|:---------|
| Sequential Workflow + Circuit Breaker | 多步骤+每步防错 | 流程执行型标配 |
| Reflection Loop + Dual-Agent Review | 自检+独立审查 | 交互型深度对话 |
| Progressive Disclosure + Plan-and-Execute | 分层加载+先规划 | 复杂生成型 |
| Verifier/Guardrail + Circuit Breaker | 双重防护 | 高风险操作 |
| Staged Validation + Placeholder Scan | 分段校验+残留检测 | 模板编排型标配 |

### 2.1 模块化设计实践

> 来源：旧版 skill-design-guide.md v2.0——合并入此规范后原文件已删除

**核心原则**：模块间松耦合，模块内高内聚。模块之间只通过输出/输入文件衔接，不共享内部状态。

| 对比 | 坏的设计（耦合紧） | 好的设计（松耦合） |
|:----|:-----------------|:-----------------|
| 状态管理 | 模块A和B共享同一个全局变量 | 模块A产出 `parsed_data.json`，模块B声明 `depends_on: parsed_data.json` |
| 依赖声明 | 模块B隐式假设模块A做了什么 | 模块B显式声明输入来源 |
| 调试成本 | 改模块B需要重跑A和B | 只要 `parsed_data.json` 不变，只跑B |

**输出缓存/断点续跑机制**：

| 规则 | 说明 |
|:----|:------|
| 缓存是会话级 | 任务完成后可清理，不是永久状态。永久状态由记忆系统维护 |
| 断点规则 | 执行模块N前先检查 `steps/step-N-output.json` 是否存在——存在则跳过读缓存，不存在则执行并写入 |
| 调试后清理 | debug完成后记得清理 `steps/` 目录，避免缓存过期干扰正式执行 |
| 数据一致 | 上游模块输出格式变更时，下游模块的缓存自动失效 |

## 3. Skill生命周期

```
Draft → Test → Iterate → Validate → Deploy
v0.x    触发≥70%  触发≥85%   跨2平台    发布
```

**Deploy阶段强制操作：版本记录归档**
旧版本行从SKILL.md头部移至 `references/CHANGELOG.md`。SKILL.md只保留当前版本行 + `历史变更：详见 references/CHANGELOG.md` 指针。

**版本号声明纪律**：版本号只出现在1处——YAML `version:` 字段。H1标题和正文元数据行不得包含版本号。变更历史统一查阅 `references/CHANGELOG.md`。

## 4. 质量分级与成熟度

> 合并旧版成熟度模型L1-L3 + 新增质量分级S/A/B/C（来源：Kubernetes graduation criteria）

### 4.1 成熟度模型（自动化等级）

| 成熟度 | 特征 | 防出错方式 | 示例 |
|:----:|:---|:----------|:----|
| **L1 文档型** | 规则指引+描述 | 依赖AI自己理解、自己执行、自己检查——三环中任一出错即失败 | 早期的三明智SKILL.md |
| **L2 工作流型** | 明确步骤顺序+产出物锁+检查点+熔断器 | 执行路径固定，但AI仍可能在执行中出岔子 | 三明智v3.4.0 |
| **L3 自动化型** | 程序强制验证+系统级指令+外部检查脚本 | 不让AI判断是否执行——强制执行 | 暂无（当前系统所有Skill均处于L1-L2） |

**进化路径**：L1→L2→L3，与生命周期协同——Deploy后持续通过Error驱动升级成熟度。

### 4.2 质量分级（设计质量等级）

> 与成熟度正交——成熟度是"自动化程度"，质量分级是"设计质量"

| 等级 | 定义 | 防错层 | 防误层 | Alternatives | 质量标准 | 典型示例 |
|:----:|:-----|:-------|:-------|:------------|:---------|:---------|
| **S级** | 防误为主+防错为辅+设计端约束完整 | ✅完整 | ✅完整 | ✅有 | 触发≥95%/完成≥99%/成功≥95% | 三明智v3.4.0 |
| **A级** | 防错为主+有检查端约束 | ✅完整 | 🟡部分 | — | 触发≥90%/完成≥97%/成功≥88% | Shall We Talk v0.6.0 |
| **B级** | 基本机制+依赖AI自觉 | 🟡部分 | ❌无 | — | 触发≥85%/完成≥95%/成功≥80% | 多数Draft阶段Skill |
| **C级** | 仅有模板填空 | ❌无 | ❌无 | — | 未达标 | 初版Draft |

### 4.3 升级路径

```
C级 → B级：加产出物锁+熔断器+自检清单通过
B级 → A级：加完整性锁+思考检查点+防错层完整
A级 → S级：加防误层（设计端约束）+Alternatives记录+质量标准达标S线
```

**关键升级**：A级→S级的分水岭是**从检查端转向设计端**——不是加更多检查，是让错误无法发生。

### 4.4 100分制评分标准（skill_eval.py）

> ⚠️ **本体论声明**：评分的目的不是测量质量，是引导改进。100分 = "当前标准下无异常信号"，≠ 完美。
> 扣分 = 审视请求，不是质量审判。评分标准与Skills共演化。详见《Skill架构规范》§1.2。

> ☑SHOULD配合`skill_eval.py`脚本使用——脚本自动化检测，本表定义权重与判定逻辑。

| 检查项 | 分值 | 权重层级 | 判定规则 |
|:-------|:----:|:--------:|:---------|
| **T1 · S级核心（40分）** | | | |
| Poka-Yoke防误层 | 20 | S级核心 | 三方法覆盖0/1/2/3种→0/5/12/20分 |
| 五级标注覆盖 | 10 | S级核心 | DO/SHOULD/MAY/SHOULD NOT/DO NOT出现次数，min(10, 次数) |
| Alternatives Considered | 10 | S级核心 | 段存在=10分，不存在=0分 |
| **T2 · 质量保证（30分）** | | | |
| 触发条件段 | 15 | 质量基�� | 应该触发5分+不应该触发5分+触发词数≥3加5分 |
| Token预算合规 | 10 | 质量保证 | SKILL.md≤400行（梯度分界点，非精确阈值）+ 梯度扣分(400-600行8分/600-800行5分/>800行0分) |
| 位置风险 | 5 | 质量保证 | 关键指令前置（YAML+铁律声明段）→ 5分；中部有强制指令→2分；无关键指令→0分 |
| **T3 · 结构完整（15分）** | | | |
| 跨文件一致性(S5) | 5 | 结构完整 | reference文件步骤序列与SKILL.md对齐，含强制步骤标记 |
| 熔断器机制 | 5 | 结构完整 | 关键词存在=5分 |
| 产出物定义 | 5 | 结构完整 | 关键词存在=5分 |
| **T4 · 清理项（15分）** | | | |
| YAML元数据完整性 | 5 | 清理项 | 必填字段全齐=5分 |
| 旧版NEVER/MUST残留 | 5 | 清理项 | 无残留=5分，有残留=2分（需人工复核） |
| 文件杂乱 | 5 | 清理项 | 根目录无无关文件（README/CHANGELOG等按规则管理）=5分；有杂乱文件=0分 |
| **合计** | **100** | | |

**⛔DO NOT 闯关制**（不进分数，存在即降级）：

> 以下问题不通过权重扣分处理——因为它们会导致Skill无法解析、无法读取关键内容、或不符合基本Skill标准。**闯关不通过，分数无效，直接降级。**

| 闯关项 | 后果 | 原因 |
|:------|:----:|:------|
| 未闭合代码围栏 | 直接B级 | 文件无法解析，基础功能丧失 |
| 内部链接失效 | 降一级（S→A, A→B） | AI读不到关键内容 |
| YAML必填字段缺失 | 直接B级 | name/description/version缺一都不构成标准Skill |

**等级判定**：

| 百分比 | 等级 | 说明 |
|:------:|:----:|:-----|
| ≥90% | S | 防误为主+设计端约束完整 |
| ≥75% | A | 防错为主+有检查端约束 |
| ≥60% | B | 基本机制+依赖AI自觉 |
| <60% | C | 仅有模板填空 |

### 4.5 T5对抗成熟度分级（独立维度）

> T5是独立于T1-T4主维度的对抗性防御评估。T1-T4 = "该有的写了没"（正面评估，满分100）。T5 = "攻击面的防御声明到位没"（负面评估，满分20）。
> 理论基础：OWASP LLM Top 10 2025 / Agentic Top 10 2026 / MITRE ATLAS / NIST AI 100-2。详见Skill架构规范§二附。

| 等级 | 得分 | 含义 |
|:----:|:---:|:-----|
| 🟢 **S** | 18-20 | 对抗防御完整，所有11项攻击面均有防御声明 |
| 🟡 **A** | 14-17 | 轻微缺口，1-2个攻击面无防御 |
| 🟠 **B** | 8-13 | 明显缺口，3-5个攻击面无防御 |
| 🔴 **C** | 0-7 | 严重脆弱，6个以上攻击面无防御或一票否决 |

**T5评估维度（四象限）**：

| 象限 | 攻击入口 | 测试项数 | 理论来源 |
|:----|:---------|:------:|:--------|
| Q1 直接对抗 | 用户通过对话绕过 | 4项(8分) | OWASP LLM01/LLM06 + MITRE ATLAS |
| Q2 语义欺骗 | 第三方内容/间接渗透 | 2项(4分) | MITRE AML.T0051.002 + ATLAS 侦察 |
| Q3 系统利用 | 工具/上下文/循环攻击 | 3项(6分) | OWASP ASI01/ASI02/LLM10 |
| Q4 持久化投毒 | 多轮/记忆攻击 | 2项(4分) | MITRE ATLAS 持久化 + OWASP ASI06 |

**T1-T4 × T5 双维度画像**：

| T1-T4等级 | T5等级 | 画像 | 行动建议 |
|:--:|:--:|:-----|:---------|
| S | S | 🏆 全面领先 | 维护 |
| S | A | 写好但防御一般 | 加强防御声明 |
| A | S | 防御好但写不达标 | 升写作质量 |
| A | A | 中等 | 双线提升 |
| B+ | C | ⚠️ 高危组合 | 优先修T5缺口 |

---


**分值设计逻辑**：
- T1 S级核心三项（防误层+五级标注+Alternatives）= 40分——S级门槛，缺任何一项S级直接泡汤
- T2 质量保证（触发条件+Token预算+位置风险）= 30分——运行时质量的核心保障
- T3 结构完整（跨文件一致性+熔断器+产出物）= 15分——工程规范底线
- T4 清理项（YAML+旧版残留+文件杂乱）= 15分——卫生规范
- 闯关制独立于分数——未闭合code fence/内部链接失效/YAML缺失 → 不计算分数，直接降级
- 基础项+清理项（YAML+旧版残留）= 15分——结构规范+历史清理

## 5. 自检清单

> 独立成节——修复旧版§九表格被成熟度模型截断的问题

**Draft完成后必须先跑自检清单：**

| # | 检查项 |
|---|--------|
| 1 | description含"做什么+何时用+排除场景"？ |
| 2 | 四层契约全定义？ |
| 3 | 每个步骤有产出物锁📦？ |
| 4 | 每个外部调用有熔断器🔌？ |
| 5 | 有思考检查点？ |
| 6 | 有完整性锁🔒？ |
| 7 | 有判断标准表？ |
| 8 | 有禁止行为表？ |
| 9 | 有与其他Skill的关系段？ |
| 10 | YAML字段齐全 + name kebab-case格式 + 版本号一致性（YAML/H1/版本行一致）？ |
| 11 | `references/CHANGELOG.md` 存在且非空占位符（Deploy阶段归档完成）？ |

**⛔DO NOT 闯关检查**（B/A级不要求，S级一票否决）：

| # | 闯关项 |
|---|--------|
| G1 | 未闭合代码围栏 = 0？ |
| G2 | 内部链接全部有效（SKILL.md中相对链接指向的文件存在于包内）？ |
| G3 | YAML必填字段（name/description/version）齐全？ |

三项全通过 → 进入分数制评分。任一项 ❌ → 直接降级，不计分。

**S级附加检查**（B/A级不要求）：

| # | S级检查项 |
|---|--------|
| S1 | 防误层有至少1个Poka-Yoke接触式防错机制？ |
| S2 | 每个设计决策有Alternatives Considered？ |
