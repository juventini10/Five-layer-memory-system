## 1. YAML Frontmatter 元数据

### 必填字段

字段 | 说明 | 示例
-----|------|------
`name` | Skill名称，与目录名一致（中文或英文） | `每日伙伴`
`emoji` | 1个emoji标识 | `📅`
`trigger` | 触发此Skill的用户输入模式 | `"日记/复盘/周报/月报"`
`description` | 1-2句功能描述 | "自动同步日记数据→..."
`author` | 作者署名 | `皮叔`
`source` | Skill来源身份 | `self-built` / `skillhub` / `fork` / `ai-generated`

**检查项：**
- [ ] `author`字段已填写
- [ ] `source`字段已填写（自建Skill必填）
- [ ] SKILL.md 末尾有 `设计者` 和 `开源协议` 声明

| 字段 | 约束 | 说明 |
|------|------|------|
| `name` | kebab-case `[a-z0-9-]+`，max 64字符。⛔DO NOT含 `claude` 或 `anthropic` 前缀 | 唯一标识符 |
| `description` | max 1024字符。✅DO同时包含 ①做什么 ②何时用 ③排除场景 ④⛔DO NOT用XML标签 `<` `>` | 推动触发+防止过触发 |
| `source` | Skill来源身份 | `self-built`（自建）、`skillhub`（市场安装）、`fork`（复制）、`ai-generated`（AI生成） |
| `compatibility` | 平台列表 | 声明兼容性（攻击面声明） |
| `allowed-tools` | 工具名白名单 | 最小权限 |

### 推荐字段

| 字段 | 说明 |
|------|------|
| `version` | semver语义化版本 |
| `dependencies` | 依赖的其他Skill |
| `conflicts` | 互斥的Skill |
| `license` | 协议 |
| `upstream` | 更新来源路径或URL | 自建=本地路径，SkillHub安装=registry URL，fork=原始repo |
| `role` | 复杂度类型声明（engine/host/leaf/methodology，默认 leaf）——D5 角色维度解耦用（见Skill架构规范§2.3 D5） |
| `modifiable` | AI是否可修改此Skill | `true` / `false` / `ask` |

### Description 工程学

| 原则 | 说明 |
|------|------|
| **Pushy**描述 | 积极声明使用条件——防止欠触发 |
| **显式排除** | 声明"NOT for X"——防止过触发 |
| **关键词覆盖** | 用户可能说出的多种表达 |
| **文件类型提示** | 涉及特定格式时明确 |

**反向触发标准写法**：`NOT for simple file operations, NOT for general Q&A, only when user explicitly mentions X.`

✅**DO — 每个Skill的YAML description必须包含NOT for子句**，明确声明不触发场景。⛔DO NOT只有正向触发描述无负样本——原因是缺少负样本会导致过触发（不该命中时命中）。

**检查方式**：YAML description字段包含`NOT for`或`不适用于`。缺少任一则为不通过。

### 1.1 描述优化参考（命中率提升四方法）

> Skill数量增长后，命中率会自然下降。以下四种方法按推荐优先级排列：

| # | 方法 | 推荐时机 | 说明 |
|:-|:-----|:--------|:-----|
| **1** | 提高描述区分度 | Skill≥50时 | 从"是什么"转"何时用"，用场景描述替代功能描述。当前30+规模不紧迫 |
| **2** | Skill分层（Tree） | 平台支持层级路由时 | WorkBuddy当前扁平匹配，不支持层级检索。文件夹整理不影响Agent行为 |
| **3** | 增加负样本描述 | **随时可执行** | ✅DO — 每个Skill必须有NOT for子句。见上方强制规则 |
| **4** | 召回+重排 | Skill≥100+时 | 当前规模过度设计。需构建外部检索系统，工程成本高

### 1.2 版本号唯一源 🔒

⛔**DO NOT 在正文中重复声明版本号。** `version` 字段在 YAML 中是唯一权威源。

| 禁止 | 原因 |
|------|------|
| H1 标题含版本号（如 `# Skill名 v1.0`） | YAML `version` 已是唯一源 |
| 正文元数据行含版本号（如 `> **版本**：v1.0`） | 双重存在=分歧风险 |
| 文件末尾重复版本行 | CHANGELOG.md 已覆盖变更历史 |

✅**正确做法**：
- 版本号 → YAML `version:` 字段（唯一权威源）
- H1 标题 → `# Skill名`（不含版本号）
- 变更历史 → `references/CHANGELOG.md`

**原因**：双重存在=不可避免的分歧风险。物理消除第二处 > 校验发现不一致。

### 1.3 上下文级宪法声明（可选）

> 依据：指令编写规范 §5.5 v3.7+（宪法级声明支持上下文相对性）

Skill 文件可以在 YAML frontmatter 之后、核心指令之前加上下文级宪法声明。

**适用场景**：Skill 需要在执行时声明"本文件在当前执行上下文中优先级最高"。

**格式模板**（引用指令编写规范 §5.5）：
```markdown
> 🔴 本文件在{Skill名} Skill 执行时优先级最高，context compression 不可覆盖
> 🔴 不是建议，是硬约束。不可跳过
```

**硬性要求**：
- `{Skill名}` 必须明确，不能写"本文件优先级最高"（缺上下文限定 = 系统级声明，不适用于 Skill 文件）
- 宪法级声明在 YAML 之后、核心指令之前（文件头部第 6-10 行）——不在文件中段或末尾
- 同一 Skill 文件只能有一条宪法级声明——不重复、不嵌套

**检查项**：
- [ ] 如有上下文级宪法声明，格式符合指令编写规范 §5.5 模板
- [ ] 上下文限定明确（`{Skill名} Skill 执行时`），未泛化为系统级声明

## 2. 文件结构

```
skill-name/
├── SKILL.md              # 入口（YAML + 核心指令 ≤500行）
├── references/           # 按需加载
│   └── CHANGELOG.md      # 历史版本变更记录（Deploy阶段必须非空）
├── scripts/              # 可执行脚本
├── assets/               # 模板/资源
└── tests/                # 测试用例
```

⛔DO NOT放README.md——原因是README在Skill体系内无固定语义位置，AI不知道什么时候该读它。
✅替代方案：使用标准文件结构 `skill-name/SKILL.md + references/ + scripts/ + assets/ + tests/`。

⛔DO NOT用空格或下划线命名文件夹——原因是AI的glob解析对空格敏感，下划线与kebab-case在YAML中语义模糊。
✅替代方案：文件夹名与YAML `name` 字段一致，统一使用kebab-case（`[a-z0-9-]+`）。

⛔DO NOT让SKILL.md超400行——更根本的设计原则来自Lost in the Middle (Liu et al., 2023)：模型对上下文中间位置的信息利用效率最低（首部75.8%→中部53.8%准确率）。400行不是精确理论阈值，而是梯度分界点：
- ≤400行：安全区（中部信息丢失风险可忽略）
- 400-600行：警告区（风险上升，评估时扣2分）
- 600-800行：危险区（风险显著，评估时扣5分）
- >800行：不可接受（中部关键指令大概率被忽略，评估0分）

✅替代方案：超400行时拆分到references/，SKILL.md保留核心指令（关键指令放头部）。

> 🔒 **字数优先级铁律（v5.11新增 · 来源：布洛陀重构实战）**：**保障全流程100%执行 > 符合最严格字数标准（≤400行）。**
> 拆到 references/ 是手段不是目的——目的是让核心指令常驻、关键路径不丢。⛔DO NOT 为凑 ≤400 行而拆掉/弱化核心护栏（防误层、熔断器、禁止行为、T5声明等）导致 Skill 退化。行数进入警告区(400-600)/危险区(600-800)时，先确认**核心护栏完整 + 全流程可100%执行**，再决定是否继续瘦身。
> 实例（来源：clock-loop 缺口3 实测 · 2026-07-11）：clock-loop 956 行合规外置仅降 57 行（899）仍 >800、token_budget 零改善、≤400 必经删功能——维持 956 行现状即符合本铁律（保障全流程100%执行 > ≤400行），"为达标而瘦身"为负收益。

☑SHOULD 多路径Skill的reference文件中路径声明格式须与SKILL.md铁律声明段定义的格式一致——原因是多路径Skill有多个reference文件，每个都可能独立编写，格式容易漂移。示例：三明智SKILL.md铁律声明写"三明智 {L1/L2/L3} 路径：{路径名}"，L2的dual-routes.md写的是不同格式（已修复）。

**路径策略：自用 vs 发布**

| 场景 | 推荐路径方案 | 示例 |
|:----|:----------|:----|
| **自用（个人 Skill）** | 绝对路径 `~/` 开头 | `[记忆共享中心]/记忆蓝图/XXX.md` |
| **发布（跨平台分发）** | 变量占位，在YAML或正文头部声明映射表 | `[记忆共享中心]/记忆蓝图/XXX.md` + 映射表 |
| **混合（自用但保留跨平台可能）** | 绝对路径 + `references/路径映射.md` 声明 | 绝对路径，注释标注"跨平台时统一替换" |

## 3. 渐进披露（三级加载 + 注意力预算）

### 三级加载

```
第一级：YAML frontmatter → 始终加载（~100 tokens）
第二级：SKILL.md body → Skill被判定相关时加载（≤500行）
第三级：references/ → 按需导航（详细文档/模板/示例）
```

**规则**：
- SKILL.md ≤ 500行。超则拆分到 `references/`
- 核心指令放第二级，不放references/
- YAML description 是"该不该加载"的判断依据，不是摘要

### 注意力预算原则

**每个新增的注入 token 都消耗注意力——Skill 体系应最小化常驻注意力消耗。**

| 约束 | 原因 |
|------|------|
| 关键指令前置或末置 | U型曲线——中部内容回忆准确率最低（Lost in the Middle, Liu et al. 2023） |
| 优先拆分为独立文件而非超长单文件 | 多个短文件 > 一个长文件（位置可预测性更高） |
| **Token主动停止机制** | 任务接近Token预算时→生成摘要→超出预算→主动停止。⛔DO NOT让Agent在超额Token中重复处理错误信息 |

## 4. 执行层机制（七个）

> 每个机制标注Poka-Yoke三方法归属

### 4.1 步骤产出物锁（Poka-Yoke动作步序法）

每个步骤必须有 `📦 产出物`。下一步依赖上一步产出物——缺产物=中止。

⛔DO NOT定义不可验证的产出物（如"完成分析"）。

#### 三级级联锁

| 锁级别 | 名称 | 做法 | 目的 |
|:---:|------|------|------|
| **1️⃣** | 产出物锁 | 每步执行前声明产出物，完成后确认已生成 | 防单步跳步 |
| **2️⃣** | 上步校验锁 | 关键合并步骤前读取前一步产出物文件，缺失→回溯补齐 | 防跨步遗漏 |
| **3️⃣** | 报告终检锁 | 最终输出前运行完整性检查清单，不通过→不能输出 | 防输出残缺 |

#### 三段验证

对于输出内容涉及数据的Skill，建议在最终输出前嵌入三段校验：

```
⏳ 数据一致性校验 → 数值逻辑自洽
⏳ 格式完整性校验 → 所有Section齐全
⏳ 假设验证校验 → 未经验证的推断标注了来源
```

### 4.2 思考检查点

关键节点插入：

```
🧠 思考检查点
├─ 数据完整：[全部信息已获取？]
├─ 执行合规：[有无跳步？]
├─ 钩子有效：[对当前任务有帮助？]
├─ 安全合规：[越权/注入/泄露风险？]
└─ 预算合理：[Token是否可控？]
```

### 4.3 熔断器（Poka-Yoke控制型=Fail-Fast）

⛔DO NOT在不设熔断器的步骤上调用外部系统——原因是无熔断=外部调用失败时AI找不到退出路径，会无限重试或编结果。

**设计原则**：结构硬约束 + 内容按场景适配。字段名不可改、顺序固定、核心字段不可缺；简单熔断不需要"—"填充扩展字段。——原因是固定结构让AI零解析成本；按需省略扩展字段避免强制填充浪费注意力。

#### 模板（按场景选择）

**全量场景**（外部调用：读文件/调API/跑脚本）：

```
🔌 熔断器
├─ 成功条件：{必须为一个可验证的真假判断}
│  ⛔DO NOT只描述动作而不说明判定标准——原因是AI需要知道"什么算过"而非"要做什么"
│  正确示例："Read返回非空内容"、"脚本exit code==0"
│  错误示例："读文件"、"运行脚本"（只说动作没说标准）
├─ 失败处理：{必须从 [重试 | 跳过 | 中止 | 降级] 四选一}
│  ⛔DO NOT写自由文本替代判定词——原因是自由文本让模型无法程序化判断下一步
├─ 可修正参数：{当前值 → 建议值，无可修正时写"—"}
│  ✅DO 写具体参数名，不可只写"参数"
│  示例："target_path: /tmp/xxx → ~/skill/scripts/"
├─ 重试次数：{正整数，如1}
│  ⛔DO NOT写"若干次"、"视情况"——原因是模糊次数=无限循环漏风
└─ 降级方案：{必须写具体执行步骤或路径，不可仅写"跳过"}
   ⛔DO NOT只写"跳过""降级"等笼统词——原因是无路径=AI不知道降级后该去哪
   正确示例："跳过本步，继续步骤3校验"
   错误示例："降级处理"、"走备用路径"
```

**简量场景**（内部校验/纯跳步——不涉及外部调用，只有"过/不过/换个方式过"）：

```
🔌 熔断器
├─ 成功条件：{同上，必须为可验证的真假判断}
├─ 失败处理：{同上，从四选一}
└─ 降级方案：{同上，必须写具体路径}
```

✅DO — 简量场景的三个字段（成功条件/失败处理/降级方案）不可缺——原因是这三项是熔断器的基本功能：定义什么算成功、不成功怎么办、去哪里
☑SHOULD NOT — 扩展字段（可修正参数/重试次数）在简量场景中无意义时强制填写——原因是填"—" = 浪费AI注意力 = 降低对真正有用字段的关注度

#### 判定规则

| 场景 | 必填字段 | 判定条件 |
|:-----|:---------|:--------|
| 外部调用（读文件/调API/跑脚本） | 成功条件 + 失败处理 + 可修正参数 + 重试次数 + 降级方案 | 五字段不可缺 |
| 内部校验（检查值/格式） | 成功条件 + 失败处理 + 降级方案 | 三字段不可缺 |

✅DO — 所有熔断器的字段名必须与模板一致（"成功条件"不叫"成功标准"、"失败处理"不叫"失败时"）——原因是不同名称 = 增加AI解析开销
✅DO — 字段顺序必须与模板一致（成功→失败→参数→重试→降级）——原因是固定顺序 = AI不重新组织信息

⛔DO NOT — 用管道符`|`替代树状`├─`结构——原因是树状结构用形状区分层级，管道符平坦了层次
⛔DO NOT — 熔断器外部调用步骤上省略熔断器——原因是无熔断器=无退出路径

### 4.4 完整性锁（Poka-Yoke定值法）

```
🔒 完整性锁
- [ ] 所有要求的产出物已生成
- [ ] 签名/摘要中声称的范围与实际执行步骤一致
      （反例：签名说"L2双思维"但实际跑了三个思维模块 → 锁失败）
- [ ] 所有引用的前置步骤证据齐全
- [ ] 结论类产出物有明确判定（✅/🟡/❌），不留给读者猜
```

### 4.5 行动倾向声明

| 策略 | 适用场景 |
|------|---------|
| `default_to_action` | 可逆操作多的Skill（如Skill-creator、代码生成） |
| `do_not_act_before_instructions` | 高风险Skill（如生产环境操作、批量修改） |

### 4.6 结论块分离（来源：三明智v3.4.0实战）

**核心机制**：在签名步骤前强制插入独立结论块，将"结论呈现"和"执行确认"两个职责分离。

| 步骤 | 产出物 | 职责 |
|:---:|------|:---:|
| 结论块 | ✅/🟡/❌ 判定 + 关键发现≤3条 | 结论呈现 |
| 结论块门禁锁 | 3问自检通过（结论明确+依据可追溯+签名一致性） | 结论质量验证 |
| 签名 | [🧠 Skill ✅ \| 结论块浓缩版 \| 日期] | 执行确认 |

### 4.7 自爆机制（Poka-Yoke定值法变体 · 来源：三明智v2.0实战）

**核心问题**：定值法（固定数量评估条目）能确保"填满格子"，但不能确保"填进去的不是假话"。当全部条目都是正面/低风险/绿灯时，说明AI在说好话而不是做评估——需要强制复检。

**触发条件**：固定数量评估条目全部为"正面/低风险/绿灯/全员通过"时触发。

**执行流程**：

```
🛡️ 自爆触发：N项全员绿灯 → 强制复检≥2条非正面发现
├─ 复检后仍有N项全员绿灯 → 签名标❌（不输出结论）
└─ 复检后找到≥2条非正面发现 → 正常签名
```

**适用场景**：
- 8要素评估全员绿灯（三明智8element.md）
- 3条隐含假设风险等级全部🟢（三明智Step0.5）
- 任何固定数量评估表中AI只能填"好"不会填"差"的场景

**与熔断器的区别**：
| 机制 | 防什么 | 触发条件 |
|:----|:-------|:---------|
| 熔断器 | 防缺/空/格式错误 | 数量不足或格式不符 |
| 自爆 | 防全员正面/说好话 | 全部正面评估但实际有风险 |

## 6. 评估与测试

### 6.1 评估集门禁（P0强制）

**EVALUATION GATE — 无固定eval_set的Skill不得发布。**

✅**DO — 评估集必须以独立文件 `references/eval-set.md` 存在**（渐进披露：评测/自检时按需 Read，不常驻 SKILL.md 头部）。⛔DO NOT 把完整评估集内联在 SKILL.md 正文——原因是内联评估集会占用注意力预算、推高行数、挤占核心指令位置（system-logger v3.5.4 实战：内联13条→外置后既过 P0 门禁又脱危险区）。SKILL.md 正文仅保留「评估集见 references/eval-set.md」指针 + 简要摘要即可。

### 6.2 三层测试

| 层 | 测什么 | 方式 |
|:---:|------|------|
| 触发测试 | 该触发时触发、不该触发时不触发 | 10-20个应触发query + 不应触发query |
| 功能测试 | 输出正确、API调用成功、错误处理生效 | 3-5个核心场景 |
| 基线对比 | Skill比裸用AI好 | 开关对比 |

**测试≠通过测试**：测试的目的是验证任务意图是否达成，不是证明能运行。写测试前先问："这个测试暴露了什么可能失败的情况？"

### 6.3 质量标准

| 指标 | 及格线（B级） | A级 | S级 |
|------|:---:|:---:|:---:|
| 触发精准率 | ≥ 85% | ≥ 90% | ≥ 95% |
| 步骤完成率 | ≥ 95% | ≥ 97% | ≥ 99% |
| 首次成功率 | ≥ 80% | ≥ 88% | ≥ 95% |
| 证据可追溯率 | ≥ 70% | ≥ 85% | ≥ 95% |
| 防误层完整 | — | 部分 | 完整 |
| 防错层完整 | 部分 | 完整 | 完整 |
| Alternatives记录 | — | — | ✅有 |

> 质量分级定义见 `Skill设计模式.md` §4

**证据可追溯率**：输出中每条价值判断附带可验证依据的比例。评估方法：随机抽取10条输出，逐条检查"是否有证据支撑"。每缺少一条依据扣10%。

### 6.4 技能行为评测

> 来源：Superpowers v6.0.3（Jesse Vincent / Prime Radiant）——修改Skill后必须运行行为验证

修改Skill后必须运行验证流程，确保行为不退化：

| 步骤 | 做什么 | 通过标准 | 对应Poka-Yoke方法 |
|:----|:------|:--------|:----------------|
| 1. 流程完整性 | 运行1轮完整Skill流程 | 所有步骤按序执行，无跳步 | 动作步序法 |
| 2. 输出合规性 | 检查输出格式和质量 | 产出物结构完整，路径声明正确 | 接触法 |
| 3. 证据验证 | 随机抽3条价值判断检查证据 | 每条都有可追溯依据 | 定值法 |
| 4. 回归对比 | 对比改前改后的关键指标 | 质量不下降（触发率/完成率/证据率） | 定值法 |

⛔**DO NOT**在未运行评测流程的情况下发布Skill更新。

> **评测流程使用方式**：修改Skill后，手动或通过脚本触发验证。验证失败→回溯修复→重新评测→通过后发布。

### 6.5 T5对抗性测试（v2.0 — 独立维度，满分20）

> T5是独立于T1-T4主维度（满分100）的对抗性成熟度评估。T1-T4评估"该有的防御写了没"，T5评估"攻击面的防御声明到位没"。两者评分逻辑统一（加法制），但分数独立报告。

**测试范围**：四象限×11项攻击面（+1项可选记忆投毒），满分20分。

| 象限 | 攻击入口 | 分值 | 测试项 |
|:----|:---------|:---:|:------|
| Q1 直接对抗 | 用户绕过/权限冒充/CoT污染/语义伪装 | 8 | T5-01~04 |
| Q2 语义欺骗 | 间接诱导/旧格式残留 | 4 | T5-05~06 |
| Q3 系统利用 | 多Skill冲突/Context溢出/工具滥用 | 6 | T5-07~09 |
| Q4 持久化投毒 | 循环调用/渐进侵蚀 | 4 | T5-10~11 |

**等级**：≥18 S级 / 14-17 A级 / 8-13 B级 / 0-7 C级。

**理论来源**：OWASP LLM Top 10 2025 / OWASP Agentic Top 10 2026 / MITRE ATLAS / NIST AI 100-2。详见Skill架构规范§二附。

**检测局限性**：基于关键词匹配（非运行时攻击模拟）。有防御声明 ≠ 实际防御有效。未来版本计划引入LLM-based红队测试。

### 6.6 产出物残留扫描（可选，适用于模板编排型/填充型Skill）

> 来源：DashiAI PPT 实战（dashiai-ppt·placeholder 哨兵模式）

✅DO — 在模板填充类Skill的交付前增加一步「产出物中性占位符残留扫描」：
▶ 定义中性占位符列表（如 `['请输入文本', '请输入', '请输', '默认文案']`）
▶ 遍历最终产出物的可见文案区域，发现列表中任意字符串 → 标记 FAIL，拒绝交付
▶ 示例输出：`validate-goal-copy 检测到文案残留: "请输入文本"(slide 3 headline)`

⛔DO NOT 将"占位符残留检测"与"内容正确性校验"合并为一个步骤——原因是两件事检测的是不同方向的漂移：
- 内容正确性校验：检测填进去的内容是否准确（有没有填错）
- 占位符残留扫描：检测是否有内容漏填（模板默认值是否遗忘）
两者正交，合并则遗漏不可被另一项覆盖。

——根因：AI 填充模板最常见的幻觉是漏填——有内容但没替换默认值，正确性校验检查不出来。

**检查方式**：参见 Skill设计模式.md §2「模板编排型」的验证管道定义。

### 6.7 评测脚本治理原则（v5.11反哺 · 来源：skill_eval.py 重构实战）

skill_eval.py 是规范的**可执行镜像**，其自身设计受两条硬约束：

- **满分=100 不可动**：新增维度必须在 100 内重分配权重（集中权重字典 + `assert sum(WEIGHTS)==100` 物理防超），⛔DO NOT 简单加总导致满分溢出（v2.2 曾因 +5 分变 105，已修）。
- **评分只反映文件设计端（幂等）**：流程类规则（如 §6.6 修改前备份）属**开发者行为层**，其真值不在文件内、而在操作历史上。✅DO 由**改前自动备份钩子（hook）** 强制拦截，而非由评测维度扣分——否则评分非幂等（同文件不同时间得分不同）。若评测仅作提醒，降级为「非计分警告」。
- **评估集门禁（§6.1）以 `references/eval-set.md` 为唯一判定对象**，内联评估集不计入门禁通过。

## 7. 多Skill共存规则

⛔**DO NOT假定本Skill是唯一活跃的Skill。Skill可能同时与其他Skill共存，指令不能冲突。**

在 `## 与其他Skill的关系` 段声明与其他Skill的依赖/协作/互斥。

### 7.1 管辖权重叠声明（铁律 · v5.6新增）

**每个Skill在`## 触发条件`段必须声明与其他Skill的重叠处理规则。**

| 重叠类型 | 处理规则 | 示例 |
|:---------|:---------|------|
| **触发词重叠** | 优先级声明：谁先处理 | "唤醒记忆"和"每日伙伴"都匹配"早上好"→唤醒记忆优先 |
| **功能重叠** | 分工声明：各管什么 | 读书助手管输入流，Shall We Talk管对话流 |
| **退出条件** | 每个Skill必须声明何时停止 | 三明智：用户说"好了"或连续3轮无新视角→自然退出 |

未声明重叠处理规则的Skill → 对抗性测试T5-07（多Skill冲突，占2/20分）扣分项。
