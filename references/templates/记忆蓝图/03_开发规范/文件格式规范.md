# 文件格式规范 v1.0.0

> 本文件自身即遵守本规范（见上方 YAML 头），作为活样板。

---

## 一、目的与适用范围

**目的**
1. 为今后所有**新建 Markdown 文件**提供统一样板（开头 YAML 含什么、正文怎么排、结尾怎么收）——**不限记忆蓝图，适用整个个人AI档案**（设计依据、改造计划、项目文档、说明类文件皆可用）。
2. 为**现有文件整改**提供可执行条款——不靠感觉，逐条对表即可。

**适用范围（通用）**
- 个人AI档案下所有"需被 AI 稳定读取、理解、引用"的 Markdown 文件：
  - 记忆蓝图的设计依据 / 规范 / 哲学类文件
  - 各类**改造计划 / 方案文档**
  - 架构说明、设计依据、说明类文档
- 本质是：**任何"被 AI 当知识源"的文件**都建议遵守。

**不适用**
- Skill 的 `SKILL.md`：已有专属规范（skill-creator / Skill架构规范），不在此重复。
- 系统日志流水、纯数据表、临时草稿（归 `归档/` 或日志体系）。

> 📌 本规范的"通用性"来自一个判断：YAML 头的目的是**让 AI 在打开文件的头几秒，无需读正文就能回答"这是什么、讲什么、现在是否有效、信不信得过"**。这个目的对任何被 AI 读取的文件都成立，故规范本身不绑定记忆蓝图。

## 二、核心原则（设计依据）

### 原则 1 · 首因高地（AI 可读性第一原则）
文件**开头是注意力最贵的高地**。开头只放"身份 + 定位 + 权威源"；变更史、寒暄、背景回溯一律后置（见原则 4 · 变更史后置）。

- **依据**：Liu et al. 2023《Lost in the Middle》实证 LLM 上下文呈 **U 型注意力曲线**——开头（首因）与结尾（近因）关注最高、中间最低；MIT 2025 从架构层证实（causal attention masking 使早期 token 累积更多注意力权重 + RoPE 位置编码衰减使中间 token 落入"dead zone"）。
- **推论**：长文件常按 token 截断。若变更史占开头，真正的"第一章 / 铁律声明"会被推到截断边界外，AI **读不到核心**。

### 原则 2 · 关注点分离（"数字集装箱"隐喻）
YAML 上部给**机器/AI**做结构化抽取（标题、类型、时效、权威源）；Markdown 下部给**人类/语义理解**读自然语言。二者用 `---` 物理分隔。

- **依据**：YAML Frontmatter 行业惯例（mdedit.ai / 腾讯云"数字集装箱" / esdora 文档体系）。

### 原则 3 · 单一文档类型（Diátaxis）
每文件只属**一种**类型，不混写：

| 类型 | 导向 | 回答的问题 | 例子 |
|---|---|---|---|
| 参考 Reference | 信息 | "X 是什么/怎么定义" | 五层记忆系统、Skill架构规范 |
| 说明 Explanation | 理解 | "为什么这么设计" | 成就系统/用户基本规则设计哲学 |
| 指南 How-to | 任务 | "怎么做 X" | 指令编写规范、发布包编写规范 |
| 教程 Tutorial | 学习 | "教我 X" | （较少） |
| 计划 Plan | 规划 | "要改什么/怎么做" | 各类改造计划、方案文档 |

### 原则 4 · 变更史后置
所有 `vX.X变更` 叙述**不占开头**，移至文末或独立 `CHANGELOG.md`（见 §四）。

### 原则 5 · 高频文件独立成夹（关注点不污染平级）
更新频率高、被多 Skill/多文件引用的文件，**不为它散落一个平级更新文件**，而是**单独建一个文件夹**，把"正文 + 更新文件"收进同一夹内（见 §四 规则 2）。

## 三、三段式文件结构

```
┌─────────────────────────────────────┐
│ 段1 · YAML Frontmatter（机器/AI读）   │  ← 文件绝对第一行起
├─────────────────────────────────────┤
│ 段2 · 正文（人类/语义读）             │  ← 首段=定位锚点，不寒暄
├─────────────────────────────────────┤
│ 段3 · 结尾/附录（按需）              │  ← 变更记录后置
└─────────────────────────────────────┘
```

### 段 1 · YAML Frontmatter（必须）

**格式硬约束**
- ⛔DO NOT 在 YAML 前留任何字符或空行——三短横线 `---` **必须位于文件绝对第一行**。
- 闭合 `---` 后**必须空一行**再写正文标题（Obsidian 结构规则）。
- 全文**仅一个** YAML 块——⛔DO NOT 出现第二个 `---` 包裹块。
- 字段名全库**一致**——⛔DO NOT 混用 `date`/`created_date`/`d1` 等同义字段。

**字段集：从第一性原理推导**

> 一个陌生文件被 AI 打开时，前几秒（首因窗口）必须能回答 5 个问题，否则会误读或误信。每个问题对应一个字段——这就是"必填字段"的硬依据，不是拍脑袋定的。

| # | AI 必须回答的问题 | 字段 | 必/选 | 说明 | 示例 |
|---|---|---|---|---|---|
| 1 | 这是什么？（身份） | `title` | 必 | 文档标题（与正文 H2 首节不重复） | `五层记忆系统` |
| 2 | 它属于哪类文档？（决定怎么读、信多少） | `type` | 必 | 文档类型（见原则 3：reference/explanation/how-to/tutorial/plan） | `reference` |
| 3 | 现在还有效吗？（时效/可靠度） | `status` | 必 | `active` / `draft` / `deprecated` | `active` |
| 3 | 同上 | `version` | 必 | 语义版本 `vM.N.P`（可选语义标签后缀 `vM.N.P[-tag]`，如 `-S` S级深度报告 / `-draft` 草稿态；例 `v2.2-S`、`v0.2.1-draft`） | `v4.17.0` |
| 3 | 同上 | `date` | 必 | 最新**实质**更新日，ISO `YYYY-MM-DD` | `2026-07-11` |
| 4 | 一句话核心是什么？（要不要深读） | `summary` | 必 | **首因锚点**，≤40字，给 AI 快速判断 | `布洛陀五层记忆结构的权威总览入口` |
| 5 | 信不信得过？谁定的？（权威） | `source` | **必** | **权威源路径/出处**，防 AI 误信非权威副本 | `~/个人AI档案/记忆蓝图/...` |
| 5 | 同上 | `author` | 选 | 维护者/作者 | `用户` |
| — | 检索/归类 | `tags` | 选 | 主题标签列表 | `[格式, 规范]` |
| — | 知识网络 | `related` | 选 | 相关文件路径列表（构建系统关联） | `见本文件头` |
| — | 归属领域 | `area` | 选 | 文件归属的项目/领域（通用化后替代原记忆蓝图分类号） | `记忆蓝图` / `改造计划-某项目` |
| — | 规范遵循版本 | `complies_with` | 选(新建建议必含) | 声明本文件按"文件格式规范"哪一版撰写；跨版本老文件凭此被 AI 正确识别，防误套新版规则 | `文件格式规范 v1.0.0` |

> ⚠️ **`source` 升为必填的理由**：你刚踩过 skill_eval.py 双副本（v2.4 化石 vs v2.8.8 活源）的坑——AI 若读非权威副本会得出不同结论。YAML 头显式声明 `source`，等于给 AI 一条"信这个、不信那个"的硬指令。

### 段 2 · 正文

- **首段即锚点**：第一段（或第一个 H2 后首段）必须是"这篇是什么 + 核心定位"；变更史、寒暄、背景回溯不得占用首段，一律后置。
- **标题层级**：从 `##`(H2) 起（frontmatter 已含 `title`，无需 H1）；不跳级（H2→H3→H4）。
- **内容组织 summary-first**：先概览后细节。
- **按 Diátaxis 类型组织章节**：参考类用一致格式、说明类用论述式、计划类用"目标→范围→步骤→风险"骨架，不混。

### 段 3 · 结尾 / 附录

- 视需要含 `## 变更记录` 或 `## 参考来源` 或 `## 相关文件`。
- **变更记录不前置**（见原则 4）。

## 四、变更记录策略（回答"是否每个文件自带更新文件"）

**结论：不强制每个文件自带长变更史。按"更新频率 / 被引用度"分级；高频者独立成夹。**

### 规则 1 · 分级

| 级别 | 适用文件 | 做法 |
|---|---|---|
| ① 小文件 | 低频、单人维护 | 文末 `## 变更记录` 写 1~3 行摘要即可，或无 |
| ② 高频核心 | 被多 Skill 引用、权威定义（如三大思维白皮书、Skill架构规范） | **独立 `CHANGELOG.md`** |
| ③ 跨文件 | 同一主题多文件 | 变更不重复记，统一收口到主文件 CHANGELOG |

⛔DO NOT 在文件开头堆 `v3.7变更 / v3.4变更 / ...` 一长串（本次整改要消除的反模式）；变更史按 §四 分级后置。

### 规则 2 · 高频文件必须独立成夹（不让更新文件污染平级目录）

当某文件属于级别 ②（更新频繁、被多方引用），**不为它散落一个平级 `XXX_CHANGELOG.md`**，而是**单独建文件夹**，把正文与更新文件收进同一夹：

```
某高频文件/
├── 某高频文件.md      ← 正文（开头只留"版本+定位+历史见 CHANGELOG"一行）
└── CHANGELOG.md       ← 独立更新文件（变更史全收这里）
```

**示例**（你举的情形）：同级有 1~5 五个文件，其中 1、2 更新快 →
```
1_高频主题A/           2_高频主题B/           3.md  4.md  5.md
├── 1_高频主题A.md     ├── 2_高频主题B.md
└── CHANGELOG.md       └── CHANGELOG.md
```
即：**只有高频的 1、2 各自成夹**，3/4/5 仍是平级普通文件（按级别 ① 文末简短或无）。不要求所有文件都成夹。

> 📌 这条规则的收益：平级目录不被 `文件名 + 文件名_CHANGELOG` 成对污染；AI 读到 `某高频文件/` 夹时，一眼知道"这是个需持续维护的实体"，更新文件天然内聚。

## 五、与现有文件兼容性（过渡条款）

1. **新建文件**：本规范发布（定稿）后必须 100% 遵守。
2. **现有文件整改**：按"最高频读取优先"排序，逐条对表：
   - 第一批（重灾+高频）：`01_思维方法论/三大思维白皮书.md`（开头 13 行变更史）、`03_开发规范/Skill架构规范/Skill架构规范.md`（开头单行堆 v5.9→v5.14 摘要）。整改后若属级别 ②，按 §四 规则 2 为其建夹 + 独立 CHANGELOG。
   - 其余文件：开头仅"版本行+简短来源"的暂不动，待巡检。
3. **整改有条款可依**：每条改动引用本规范对应段/条（如"违反 §三·段1 首因高地"）。

> ⚠️ **Skill架构规范特殊约束**：它有一份被 clock-loop 固化的副本 `skill-arch-standard.md`，同步规则要求"改本规范后须重新固化并升版本号"。整改其头部格式时须先对齐消费方，否则评估失准。

## 七、待用户拍板的决策点汇总

| 编号 | 问题 | 当前建议 / 状态 |
|---|---|---|
| A | YAML 选填字段集（`author`/`tags`/`related`/`area`/`complies_with`） | ✅ 已定稿：`review_cycle` 据用户意见去除（现状无定时复审消费者、与 `date`/`status` 重叠）；定稿选填集为 `author`/`tags`/`related`/`area`/`complies_with` |
| B | 变更记录：分级 + 高频独立成夹 | ✅ 已据用户意见落定（§四 规则 1+2） |
| C | 配套 **frontmatter schema 校验脚本**，纳入反方向的钟巡检 | 建议做；但需明确触发方式（见下） |
| D | 校验脚本在反方向的钟里何时启动 | 见下说明 |

### 决策点 C/D 说明 · 校验脚本与反方向的钟的关系

- **反方向的钟的启动条件**：仅当用户以 **"循环 "/"loop "** 前缀，或说 **"循环工程"/"loop工程"/"自主跑"** 时才进入 Loop 模式。**它不是文件保存监听器**——你改完文件不会自动触发。
- **校验脚本的落点**：若做，作为 **Phase X（脚本增强检查 / 机械验证段）的一个新检查项** 嵌入。即：你用"循环 检查某Skill/某文件质量"启动 Loop 时，Phase X 会跑 skill_eval.py 确定性扫描 + **新增的 frontmatter 合规校验**。
- **含义**：校验是"**按需巡检**"，不是"实时强制"。若你要"每个新文件一保存就校验"，那是另一条技术路线（git pre-commit hook / 文件监听），不在反方向的钟的 Loop 模型内——需另议。
- **防退化价值**：纳入 Phase X 后，每次 Loop 评估都会机械守住格式门槛，避免文件随改随退化（与 skill_eval 守住 §4.3 熔断器格式同理）。
