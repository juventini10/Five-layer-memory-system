# 文件格式规范 v2.7.0

> 本文件自身即遵守本规范（见上方 YAML 头），作为活样板。

---

## 一、目的与适用范围

**目的**
1. 为今后所有**新建 Markdown 文件**提供统一样板（开头 YAML 含什么、正文怎么排、结尾怎么收）——**不限记忆蓝图，适用整个个人AI档案**（设计依据、改造计划、项目文档、说明类文件皆可用）。
2. 为**现有文件整改**提供可执行条款——不靠感觉，逐条对表即可。

**适用范围（通用）**
- 个人AI档案下所有"需被 AI 稳定读取、理解、引用"的 Markdown 文件：
  - 记忆蓝图的设计依据 / 规范 / 哲学类文件
  - 各类**改造计划 / 方案文档**
  - 架构说明、设计依据、说明类文档
- 本质是：**任何"被 AI 当知识源"的文件**都建议遵守。

**不适用**
- Skill 的 `SKILL.md`：已有专属规范（skill-creator / Skill架构规范），不在此重复。
- 系统日志流水、纯数据表、临时草稿（归 `归档/` 或日志体系）。

> 📌 本规范的"通用性"来自一个判断：YAML 头的目的是**让 AI 在打开文件的头几秒，无需读正文就能回答"这是什么、讲什么、现在是否有效、信不信得过"**。这个目的对任何被 AI 读取的文件都成立，故规范本身不绑定记忆蓝图。

### 触发条件（何时必须 consult 本规范）

✅ **DO** 当 AI 要执行以下任一动作前，**先读本规范**：
- 在个人AI档案下**新建**任何 Markdown 知识文件（按本规范 YAML 头 + 三段式搭骨架）；
- **修改/整改**现有文件的结构、frontmatter 字段、或标题层级；
- **校验**某文件是否符合格式标准（跑 §3.5 符合性自检清单）；
- 不确定"该用哪个 schema / 哪些字段"时（查 §八 Schema 注册表）。

⛔ **DO NOT** 在未经本规范约束的情况下凭习惯写 frontmatter——无约束=各文件字段漂移=AI 检索失效（见 §二 原则 1 首因高地）。

## 二、核心原则（设计依据）

### 原则 1 · 首因高地（AI 可读性第一原则）
文件**开头是注意力最贵的高地**。开头只放"身份 + 定位 + 权威源"；变更史、寒暄、背景回溯一律后置（见原则 4 · 变更史后置）。

- **依据**：Liu et al. 2023《Lost in the Middle》实证 LLM 上下文呈 **U 型注意力曲线**——开头（首因）与结尾（近因）关注最高、中间最低；MIT 2025 从架构层证实（causal attention masking 使早期 token 累积更多注意力权重 + RoPE 位置编码衰减使中间 token 落入"dead zone"）。
- **推论**：长文件常按 token 截断。若变更史占开头，真正的"第一章 / 铁律声明"会被推到截断边界外，AI **读不到核心**。

### 原则 2 · 关注点分离（"数字集装箱"隐喻）
YAML 上部给**机器/AI**做结构化抽取（标题、类型、时效、权威源）；Markdown 下部给**人类/语义理解**读自然语言。二者用 `---` 物理分隔。

- **依据**：YAML Frontmatter 行业惯例（mdedit.ai / 腾讯云"数字集装箱" / esdora 文档体系）。

### 原则 3 · 单一文档类型（Diátaxis）
每文件只属**一种**类型，不混写：

| 类型 | 导向 | 回答的问题 | 例子 |
|---|---|---|---|
| 参考 Reference | 信息 | "X 是什么/怎么定义" | 五层记忆系统、Skill架构规范 |
| 说明 Explanation | 理解 | "为什么这么设计" | 成就系统/用户基本规则设计哲学 |
| 指南 How-to | 任务 | "怎么做 X" | 指令编写规范、02-发版执行手册（原发布包编写规范·已归拢） |
| 教程 Tutorial | 学习 | "教我 X" | （较少） |
| 计划 Plan | 规划 | "要改什么/怎么做" | 各类改造计划、方案文档 |

### 原则 4 · 变更史后置
所有 `vX.X变更` 叙述**不占开头**，移至文末或独立 `CHANGELOG.md`（见 §四）。

### 原则 5 · 高频文件独立成夹（关注点不污染平级）
更新频率高、被多 Skill/多文件引用的文件，**不为它散落一个平级更新文件**，而是**单独建一个文件夹**，把"正文 + 更新文件"收进同一夹内（见 §四 规则 2）。

### 原则 6 · 填值权归脚本（AI 只回显不自填 · 反哺自 2026-08-12 假阴性疲劳实锤）
凡验证类/状态类"值"（验证块结果、日志时间戳、概览计数、守卫报警、评级判定依据），**必须由脚本机械产出、AI 只能回显**——AI 物理接触不到填值权。

N/A 等降级值**只允许脚本在"前置条件不成立"时产出**；AI 无权自行选用降级值掩盖真实状态。

- **依据**：8/12 误填 N/A 掩盖 changelog_guard 报警（candidates=12 被隐藏）——AI 手工填值的环节=错误必然发生的环节；今日四坑（组头重复/晚写漏抽/N/A 误填/填值权在 AI）同根因：AI 认知依赖路径必漂，且失误无感知（误填后每次看都"以为正常"=假阴性疲劳，漏记永久存在且无人知晓）。
- **推论**：设计任何含"值"的输出环节时，先问"这个值谁产出？"——答案是"AI 根据命令输出手工填"的设计=已埋雷，应改为脚本机械产出 + AI 只回显。
- **哲学源**：本原则为脚本本质（机械执行）的直接推论，完整哲学论述见 `记忆蓝图/04_系统文件设计/布洛陀脚本架构设计哲学/01-脚本架构设计通用规范.md` §一 推论（主落点·单一真源）；本处为应用场景之一（文档/格式输出设计时引用）。

[来源: 成长箱反哺 | 日期: 2026-08-12 | 反哺标题: AI 认知依赖路径必漂→填值权归脚本]

### 原则 7 · 显示层与代号层分离（反哺自 2026-07-27 v0.7.2 改名实施）

多端共享系统中，同一对象常同时存在「人看的名字」与「机器用的代号」。✅DO 两者物理分离：代号层（ID/key/path/enum 值）单一真源且⛔永不改名；显示层（标题/别名/渲染名）可随时改，改显示名必须声明「仅显示层」。⛔DO NOT 在代码/脚本/守卫判据里硬编码显示名——显示名一改守卫全哑（判据应锚代号或 ID）。改名操作前先问：「这个字符串出现在几个层？」——跨层字符串一律先分层再改。

[来源: 成长箱反哺 | 日期: 2026-07-27 | 反哺标题: 显示层/代号层分离]

### 原则 8 · 数字状态写「数据截止日」不写「冻结」（反哺自 2026-09-07 eval 根治实战）

文档中的状态数字（条目数/评测分数/基线值/计数）⛔DO NOT 写「冻结/基线已冻结=此版本」——冻结暗示永久准确，而实盘持续增长，冻结措辞已被实证两次误导后续读者把「账实脱钩」误判为「存量漂移」。✅DO 写「数据截止日：YYYY-MM-DD」或「核实于 YYYY-MM-DD」——截止日诚实（读者知道可能过期、可复验），冻结误导（读者以为是终值）。判别口诀：`写截止日，不写冻结；数字会老，日期不骗`。可机械检测性：弱（grep 可命中「冻结」但判定是否误导需语义），故以规范约束为主、不做机械门禁。

[来源: 成长箱反哺 | 日期: 2026-09-07 | 反哺标题: 文档数字冻结基线改数据截止日 | 重要度: 高]

**扩展（2026-10-10·覆盖类自动断言侧）**：凡账面写「N端/N处 + 自动（日检/定时/巡检）」类**覆盖面承诺**，⛔以代码挂载点计数充当——✅DO 句子内附调度面实扫值与日期（形如「自动承载=N（实扫于YYYY-MM-DD）」），无法实扫则降格为条件句（「跑任意一端时会核查」），⛔不写成覆盖句。判别口诀沿用：`数字会老，日期不骗；「挂」不等于「在跑」，覆盖必附实扫`。可机械检测性：中（收窄短语口径可 grep——宽语义口径假阳率 12/12 实证过高弃用，先量假阳再上尺）；已配抗体见 成长箱/免疫抗体历史.md 2026-10-10 行（QCN-20261010-004 案）。


### 原则 9 · 备份文件不入原目录（工作目录只留活跃文件 · 反哺自 2026-10-05 全目录清理实证）

所有 `.bak` / `.bak-*` 备份文件**⛔不得留在原工作目录**，必须统一归档到 `[记忆共享中心]/记忆琥珀/` 对应目录下，**保持原目录结构**（如原路径 `记忆蓝图/04_系统文件设计/XX哲学/01-规范.md.bak-xxx` → 归档路径 `记忆琥珀/记忆蓝图备份/04_系统文件设计/XX哲学/01-规范.md.bak-xxx`）。

- **依据**：2026-10-05 全目录清理实证——仅 `记忆蓝图/` 一个目录就清出 **152 个** `.bak` 文件，散落在 20+ 子目录中，造成：①目录视觉污染（活跃文件与备份混在一起，分不清哪个是当前版本）②AI 检索干扰（备份文件被误读为权威源，导致结论基于过期版本）③磁盘空间浪费（同一文件多版本重复存储）。
- **推论**：备份的意义是"可回滚"，不是"放在旁边随时看"。放在原目录=既污染当前工作区，又无法被统一管理（不知道哪些备份还需要保留、哪些可以删除）。归档到记忆琥珀=备份集中管理、可追溯、不干扰当前工作。
- **机械落点**：AI 在任何目录下操作时，若产生 `.bak` 备份，操作完成后必须立即移至记忆琥珀对应目录；发现已有 `.bak` 文件留在原目录时，应主动归档（保持目录结构）。可机械检测性：强（`find . -name "*.bak*"` 可命中），建议纳入 loop 巡检。

[来源: 全目录清理实证 | 日期: 2026-10-05 | 反哺标题: 备份文件不入原目录·统一归档记忆琥珀 | 重要度: 高]

## 三、三段式文件结构

```
┌─────────────────────────────────────┐
│ 段1 · YAML Frontmatter（机器/AI读）   │  ← 文件绝对第一行起
├─────────────────────────────────────┤
│ 段2 · 正文（人类/语义读）             │  ← 首段=定位锚点，不寒暄
├─────────────────────────────────────┤
│ 段3 · 结尾/附录（按需）              │  ← 变更记录后置
└─────────────────────────────────────┘
```

### 段 1 · YAML Frontmatter（必须）

**格式硬约束**
- ⛔DO NOT 在 YAML 前留任何字符或空行——三短横线 `---` **必须位于文件绝对第一行**。
- 闭合 `---` 后**必须空一行**再写正文标题（Obsidian 结构规则）。
- 全文**仅一个** YAML 块——⛔DO NOT 出现第二个 `---` 包裹块。
- 字段名全库**一致**——⛔DO NOT 混用 `date`/`created_date`/`d1` 等同义字段。

**字段集：从第一性原理推导（分层·非一刀切）**

> 一个陌生文件被 AI 打开时，前几秒（首因窗口）必须能回答核心问题，否则会误读或误信。每个问题对应一个字段——这就是字段层级的硬依据。但**不同文件特性不同**（文件名是否已含标题、有无迭代史、脚本是否读它），故按"删除是否影响现有流程"裁剪：无消费者 / 正文已覆盖 → 可省。

| 层级 | AI 要回答的问题 | 字段 | 判定 | 说明 | 示例 |
|---|---|---|---|---|---|
| ① 检索必留 | 哪类文档？多新？一句话核心？ | `type` / `date` / `summary` | ✅DO | type 见原则 3 五类之一；date=最新实质更新日 ISO；summary=首因锚点 ≤40字 | `reference` / `2026-07-11` / `五层记忆结构权威总览` |
| ② 合规建议 | 信不信得过？谁定的？遵循哪版规范？ | `source` / `author` / `complies_with` | ☑SHOULD | source=权威源路径防误信副本（新建必含）；author=维护者；complies_with=新建建议必含 | `[记忆共享中心]/...` / `皮叔` / `文件格式规范 v2.3.0` |
| ③ 按特性可省 | 身份 / 时效 / 版本 / 归类 / 关联 / 领域 | `title` / `status` / `version` / `tags` / `related` / `area` | MAY | 判据=删了不影响现有流程：文件名或正文 H2 已含标题→`title` 省；一次性/定稿无语义→`status` 省；无迭代史→`version` 省；标签被文件名覆盖→`tags` 省；恒定值→`related` 省（存模板）；与 type/tags 重复→`area` 省 | — |
| ⛔ DO NOT | 内容副本 | 正文数据 / 长文本 | 禁 | YAML 是检索索引**非内容副本**：正文已有数据（评级理由 / 统计数值 / 里程碑 / 阻塞等）不重复入 YAML——周报教训：把正文抄进 YAML=双本账 | — |

**可信/时效元数据（可选扩展 · OKF 借鉴 · 2026-08-13）**：以下字段为可选，不设不影响一致性判定；消费者对未知键必须宽容保留、不得拒绝（对齐 OKF v0.2 宽容一致性）。

| 字段 | 含义 | 何时用 |
|---|---|---|
| `generated: { by, at }` | 内容生产者 + 时间（actor 约定见下） | AI 蒸馏/生成条目自动携带 |
| `verified: [{ by, at }]` | 人工/过程确认事件列表（可单映射） | 人工复核后补充；`human:` 前缀者升 human-reviewed |
| `sources: [{ id, resource, title, ... }]` | 溯源：条目派生自哪些材料（含 credibility 信号 author/usage_count/last_modified） | 声明-来源映射需要时 |
| `status` / `stale_after` | 生命周期：draft/stable/deprecated；绝对日期过期判定（today >= stale_after） | 外部知识条目建议携带；内生沉淀可不设 |

**Actor 约定**：`<producer>/<version>`（agent/工具）、`human:<id>`（人）、`process:<id>`（自动过程）。信任分层判定以 `human:` 前缀为键。

**键控引用（按声明归属）**：`sources` 条目带稳定 `id`，正文 footnote 标签 = 该 id（如 `[^ga4-schema]`），⛔ 不用位置索引（sources[0]）——文档被 AI 重写/重排时位置会静默错配，稳定 id 在重排后存活。

> ⚠️ **`source` 升为必填的理由**：你刚踩过 skill_eval.py 双副本（v2.4 化石 vs v2.8.8 活源）的坑——AI 若读非权威副本会得出不同结论。YAML 头显式声明 `source`，等于给 AI 一条"信这个、不信那个"的硬指令。

### 段 2 · 正文

- **首段即锚点**：第一段（或第一个 H2 后首段）必须是"这篇是什么 + 核心定位"；变更史、寒暄、背景回溯不得占用首段，一律后置。
- **标题层级**：从 `##`(H2) 起（frontmatter 已含 `title`，无需 H1）；不跳级（H2→H3→H4）。
- **内容组织 summary-first**：先概览后细节。
- **跨文件节锚 = 抄目标标题原文，⛔自造位置式编号**：指向另一文件的某一节时，锚串✅DO 复制目标文件该节**标题原文的可定位片段**（推荐形态 `→ 目标文件名 · 标题「<原文>」`），⛔DO NOT 自造 `§N / 第N节 / N.N节` 这类位置式编号——原因是编号是**位置**、标题是**身份**：位置随章节插删漂移，且同一含义存在四种书写方言（`§3` / `3.` / `第三节` / `第五节`），机器与后来读者都要猜；标题随条目本身走，改到哪都还能字面检索到。口诀：`引编号会漂，引标题会跟`。**边界**：①目标为运行时生成物（无稳定标题）时不适用，改指其生成规则；②同文件内跳转 MAY 用 §N（读者看得见上下文，漂移面小）；③标题过长时取**可唯一定位的片段**而非全文，⛔为省字改用编号。
  实证（2026-10-01 全域一次性实测·1620 个 .md / 跨文件节锚 144 处 / 解析到实体 129 / 形态错位 15 / **硬悬空（目标实体真缺）0 例**）：病灶是书写方言，不是引用烂尾——最典型的误判面是拿"扫不出"当"不存在"（本轮首版匹配器即把 12/15 处形态错位误报成幽灵引用，据此会去建一个没有病灶的守卫）。反例自陈：本条立项当日，作者端自己写的「→详解存档版 第五节」正属自造编号（目标标题实为`五、🔒 AI执行铁律`），已改抄原文复测归零。
- **按 Diátaxis 类型组织章节**：参考类用一致格式、说明类用论述式、计划类用"目标→范围→步骤→风险"骨架，不混。

### 段 3 · 结尾 / 附录

- 视需要含 `## 变更记录` 或 `## 参考来源` 或 `## 相关文件`。
- **变更记录不前置**（见原则 4）。

### §3.4 AI 执行程序（读后做什么·怎么做）

✅ **DO** 创建/整改文件时按以下顺序执行（因果链：步骤错序=AI 不知用哪套字段）：

1. **读规范**：读本规范全文（重点 §一触发 + §三结构 + §八注册表）。
2. **判类型**：用 §二 原则 3（Diátaxis）判定文件属于 reference/explanation/how-to/tutorial/plan 哪类 → 决定正文组织方式。
3. **查注册表**：查 §八 Schema 注册表，确认本类文件有无专属 schema 文档（如读书卡片→读书卡片 schema）；有则按专属 schema 填字段，无则按本规范 §三 分层字段（① 检索必留 type/date/summary + ② 合规建议 + ③ 按特性可省，⛔DO NOT 正文数据塞 YAML）。
4. **填字段**：YAML 头按对应 schema 填（三短横线在绝对第一行；`source` 必填；`complies_with` 声明遵循版本）。
5. **跑自检**：跑 §3.5 符合性自检清单，逐条勾选，全绿方可提交。
6. **提交**：交付文件，并在变更记录注明所遵循规范版本。

⛔ **DO NOT** 跳过第 3 步直接套通用字段——跨类文件（如读书卡片）有专属必填字段，套通用必留字段会丢结构化信息（见 §八）。

## 四、变更记录策略（回答"是否每个文件自带更新文件"）

**结论：不强制每个文件自带长变更史。按"更新频率 / 被引用度"分级；高频者独立成夹。**

### 规则 1 · 分级

| 级别 | 适用文件 | 做法 |
|---|---|---|
| ① 小文件 | 低频、单人维护 | 文末 `## 变更记录` 写 1~3 行摘要即可，或无 |
| ② 高频核心 | 被多 Skill 引用、权威定义（如三大思维白皮书、Skill架构规范） | **独立 `CHANGELOG.md`** |
| ③ 跨文件 | 同一主题多文件 | 变更不重复记，统一收口到主文件 CHANGELOG |

⛔DO NOT 在文件开头堆 `v3.7变更 / v3.4变更 / ...` 一长串（本次整改要消除的反模式）；变更史按 §四 分级后置。

### 规则 2 · 高频文件必须独立成夹（不让更新文件污染平级目录）

当某文件属于级别 ②（更新频繁、被多方引用），**不为它散落一个平级 `XXX_CHANGELOG.md`**，而是**单独建文件夹**，把正文与更新文件收进同一夹：

```
某高频文件/
├── 某高频文件.md      ← 正文（开头只留"版本+定位+历史见 CHANGELOG"一行）
└── CHANGELOG.md       ← 独立更新文件（变更史全收这里）
```

**示例**（你举的情形）：同级有 1~5 五个文件，其中 1、2 更新快 →
```
1_高频主题A/           2_高频主题B/           3.md  4.md  5.md
├── 1_高频主题A.md     ├── 2_高频主题B.md
└── CHANGELOG.md       └── CHANGELOG.md
```
即：**只有高频的 1、2 各自成夹**，3/4/5 仍是平级普通文件（按级别 ① 文末简短或无）。不要求所有文件都成夹。

> 📌 这条规则的收益：平级目录不被 `文件名 + 文件名_CHANGELOG` 成对污染；AI 读到 `某高频文件/` 夹时，一眼知道"这是个需持续维护的实体"，更新文件天然内聚。

## 八、Schema 注册表与分发（AI 如何知道"哪类文件要哪些字段"）

> **背景**：本规范定义通用检索必留字段（type/date/summary），但不同类文件（如读书卡片、笔记）有专属必填字段。AI 若只背通用必留字段，遇到专属文件会丢结构化信息。故需**注册表**把"文件类型 → 专属 schema 文档"显式列出。

✅ **DO** 填字段前**先查本表**；对应类型有专属 schema 文档的，按该文档填，不套通用字段。

| 文件类型 | 专属 schema 文档 | 状态 | 说明 |
|---|---|---|---|
| 通用文档（reference/explanation/how-to/tutorial/plan） | 本规范 §三 | ✅ 已覆盖 | 检索必留 3 + 合规建议 + 按特性可省（分层·非一刀切） |
| 读书卡片（reading-card） | `schemas/读书卡片schema.md` | ✅ 已建（v1.0.0，2026-07-27） | 与 Obsidian 原子卡片约定对齐；物理落点见 `schemas/` 文件夹（层3） |
| 笔记（note） | `schemas/笔记schema.md` | ✅ 已建（v1.0.0，2026-07-27） | 与 Obsidian 笔记约定对齐；物理落点见 `schemas/` 文件夹（层3） |
| 其他类型 | 按本规范通用字段 + 类型判定 | — | 新建类型时须同步补本表行 + 建专属 schema 文档 |

⛔ **DO NOT** 在无专属 schema 时强行套通用必留字段应付专属文件——丢结构化字段=知识图谱节点属性缺失（见跨项目哲学"表头严谨=图谱 schema 地基"）。

> 本注册表即"三层分发机制"的层 2：层 1=本规范（通用+注册表），层 2=本表（类型→文档指针），层 3=各专属 schema 文档。AI 据此从"通用必留字段"精确落到"该类专属字段"。

> 层 3 的物理落点为 `schemas/` 文件夹：所有类型专属 schema 文档（笔记、未来读书卡片等）统一收于此，与 `Skill架构规范/` 同构——目录即"注册表可视化"，读规范者一眼知"类型专属规则在哪"。

## 九、生成合规保证机制（v2.x·反哺自读书助手三件套实战）

> **来源**：成长箱反哺 | 日期：2026-07-27 | 反哺标题：「三件套」生成合规保证模式
> **背景**：本规范 §3.5 定义了提交前自检清单，但"如何保证生成物**必然**合规"的设计模式此前未定义。以下三件套架构经读书助手 S 级改造全网实证（真跑验证 14/14 PASS + 故意造错卡片 lint 抓取 13 项缺失）。

任何需产出符合本规范文件的 Skill 或生成脚本，☑SHOULD 采用以下三件套保证架构：

| 件 | 机制 | Poka-Yoke 层级 | 防什么 |
|:--:|------|:---:|------|
| ① 规则单源 | 字段集 + 必填 + 约束**只存一处**（如 Python dict / YAML schema），生成器不硬编码字段集 | 防误层 | 改规则只动一个文件，消除人肉同步漂移 |
| ② 生成即自检 | 构建 frontmatter 后立即 validate，**不合规即 raise 物理阻断**（不写脏文件） | 防误层 | 设计端消除——错误无法落盘 |
| ③ 产物机检兜底 | 扫描产出目录，按 `type` 派发校验（lint_path），脏文件必被抓 | 防错层 | 检查端兜底——②漏掉的③必抓到 |

✅ **DO** 新建生成类 Skill 或脚本时，优先用此三件套而非仅依赖 §3.5 手工自检——原因是手工自检依赖自觉，三件套是物理保证。
⛔ **DO NOT** 只建 schema 不建自检——②是连接 schema(规则) 和 产物(文件) 的物理接触点。无自检=schema 是纸上规范、无牙。

> 实例见 `note_validator.py`（读书助手规则单源，NOTE_FIELDS/CARD_FIELDS/STANCE_FIELDS 全部字段只此一处定义 + validate_note/validate_card/lint_path 完整三件套）。反哺管道由成长箱维护（详见 `[记忆共享中心]/成长箱/experience/规范反哺日志.md` 2026-07-27 条目）。
