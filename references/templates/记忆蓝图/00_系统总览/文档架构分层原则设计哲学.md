# 文档架构分层原则设计哲学 — 信息组织的二分法与交叉引用机制

> 本文档是布洛陀记忆系统**文档分层机制的顶层设计哲学**。记录"什么时候该把内容拆成两层、两层之间怎么建立引用、什么情况不该分层"，不重复"特定文档的清单和命令"（那是各登记簿的职责）。

## 一、文档定位

文档分层原则是布洛陀系统的**信息组织元规则**——它不定义具体文件内容（那是各设计文档/Skill 的职责），不规定写作风格（那是指令编写规范的职责），只回答一个问题：**这条内容该放在抽象层（哲学/为什么）还是具体层（实践/怎么用）？**

### 本文约束的范围

- 分层的判定标准（二分法）
- 交叉引用的规范格式
- 什么情况下应该合并（不分层）

### 本文不涵盖

- 派生镜像机制的具体操作命令（那是 `技能与工具登记簿.md` 的职责）
- AI 指令的写作格式（那是指令编写规范 §五 的职责）
- 特定文件的目录结构和存放位置

---

## 二、什么是文档分层

**文档分层** = 把原本可能混在一起的内容，按认知目标拆成两层——抽象层和具体层。

不需要什么精密的模型。你只需要问自己一个二分问题：

> **读这份文件的人是想理解"为什么"，还是想找到"怎么用"？**

- 想理解"为什么" → **抽象层**（哲学/概念/原则/边界）
- 想找到"怎么用" → **具体层**（实践/清单/命令/示例）

---

## 三、为什么需要分层

混在一起的文件会导致两层阅读冲突：

```
你翻开一页想理解设计理念 → 却被技术细节缠绕，思路断了
你翻开一页想查某个工具怎么用 → 却被"哲学三段论"挡住，找不到命令在哪
```

**混文件的两个典型问题：**

| 问题 | 表现 | 后果 |
|------|------|------|
| **抽象层被稀释** | 设计原则混在实操清单里，"为什么"被"怎么按三步走"淹没 | 读者记不住核心理念，只记得操作步骤 |
| **具体层被掩埋** | 命令/参数/路径藏在长论述中，查询者要翻半天 | 效率低，读者放弃查找，转而猜/试/忘 |

---

## 四、分层标准（二分法）

### 两个问题决定一切

| 问题 | 选抽象层 | 选具体层 |
|------|---------|---------|
| **读者的目的** | 理解概念、决策参考 | 查找信息、执行操作 |
| **内容的本质** | 为什么、原则、边界、设计意图 | 是什么、怎么用、列出来、试一试 |

### 什么时候合并（不分层）

合并也是选择——不是所有文件都需要分层。两个条件**同时满足**才合：

1. **单层满足全部需求**——读者不需要"为什么"，只需要"怎么用"（或反过来）
2. **内容总量可控**——一页/一屏内读完，不滚动几轮找不到了

---

## 五、交叉引用机制

分层不是割裂。分层的两个文件必须**双向引用**，形成认知闭环：

```
┌──────────────────┐         ┌──────────────────┐
│   抽象层          │   →→→   │   具体层          │
│  （哲学/为什么）   │ 指向    │  （实践/怎么用）   │
│                   │  ←←←   │                   │
│ §结尾 "实践指引"   │  指引   │ 开头 "设计哲学参考"│
└──────────────────┘         └──────────────────┘
```

**引用规范：**

| 位置 | 抽象层 → 具体层 | 具体层 → 抽象层 |
|------|----------------|----------------|
| 位置 | §结尾或独立节："实践指引见 XXX" | 开头或顶部："设计哲学参考见 XXX" |
| 格式 | 绝对路径引用（如 `个人AI档案/技能与工具登记簿.md`） | 同左 |
| 频次 | 一个（一处指引即可） | 一个（顶部声明即可） |
